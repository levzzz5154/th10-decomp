## The answer in one paragraph

The two regions are one body written twice - their 591 bytes differ in exactly
four bytes, the displacement of the two direct calls - so only one body had to be
solved. The body is the rotated sibling of the already-recovered `0x00443B60`
projected-quad builder, and it transferred *idiom for idiom*: the same
`float px, py, pz, width, height; float xs[4], ys[4];` locals, the same two
`(flags >> 18/20) & 3` anchor switches with a three-store case body whose second
element stays in an x87 register, the same eight `xs[i]*ca - ys[i]*sa + px` /
`xs[i]*sa + ys[i]*ca + py` corner stores in the same order, and the same
descending `quad[3].z .. quad[0].z` tail. The `fsincos` pair is the original
source's own `__asm` block (no C++ spelling on this toolkit emits FSINCOS), and
everything after it fell out of the plain `/O2` model unchanged. The only two
things the plain translation unit could not spell were the two callee ABIs, and
both are *definitions* in the batch cluster: `0x00443290` is the cluster's
existing anchor (entity in EAX, manager on the stack) and `0x00444CE0`'s sibling
`0x00442670` (`AnimationManager::SubmitSpriteQuad`) is a recovered body, so
`manager->SubmitSpriteQuad(entity, 0)` emitted retail's `mov eax,edx; push 0;
call` with no help. **The dispatcher's cases 1/3 lose their `__fastcall`
declaration shim**: with both callees in the link as bodies, the whole-program
pass derives (ECX manager, EDX entity) and emits retail's `mov edx,eax; jmp`,
and the dispatcher is still EXACT with no convention written anywhere.

## The source

`src/render/quad_build_rotated.cpp` (both functions; the second is the same body,

// rotated sprite quad builders.
//
// The entity's in-plane angle (rotation.z) turns its two sprite extents into the
// four corners of the shared sprite quad, which the submit pipeline then
// finishes; an angle of exactly zero hands the quad to the unrotated anchored
// builder instead.  The two regions are one body written twice - their bytes
// differ only in the displacement of the two direct calls - and the dispatcher
// 0x004451C0 reaches both with the manager in ECX and the entity in EDX, tail
// jumping to them (see src/render/anm_vm_draw_dispatch.cpp).
//
// The field names follow the shared entity layout in include/th10/game/entity
// .hpp: rotation at +0x24 (a Vector3, so the in-plane angle is its z),
// scale_x/scale_y at +0x3C/+0x40, sprite_width/sprite_height at +0x4C/+0x50,
// base_position/position/render_offset at +0x334/+0x340/+0x34C, and the flag
// word at +0x35C.  The extents are sprite_width * scale_x and sprite_height *
// scale_y; the placement is render_offset + position + base_position, in that
// term order.  The two anchor fields of the flag word select the edges:
// (flags >> 18) & 3 for x and (flags >> 20) & 3 for y, each with cases
// centred (-half / +half), left-anchored (0 / size) and right-anchored
// (-size / 0), and the same value used for the two corners of an edge.
//

        return EntityDraw_00443290(entity, manager);

    __asm {
        fld angle
        fsincos
        fstp ca
        fstp sa

    px = entity->render_offset.x + entity->position.x + entity->base_position.x;
    py = entity->render_offset.y + entity->position.y + entity->base_position.y;

    height = entity->sprite_height * entity->scale_y;

        xs[1] = xs[3] = 0.0f;
        break;

        ys[2] = ys[3] = height * 0.5f;
        break;

        ys[2] = ys[3] = height;
        break;

    data_004978c0[3].y = xs[3] * sa + ys[3] * ca + py;

## Levers that turned out to matter (all measured)

1. **The family idiom transferred unchanged.** `0x00443B60`'s landed model
   (`src/render/projection_quads.cpp`) is the same shape at a different address:
   the same `float ca, sa;` + `angle` + `__asm { fld angle; fsincos; fstp ca;
   fstp sa }` head, the same `px/py` placement sums, the same `xs[4]/ys[4]`
   anchor switches, the same eight corner stores, the same descending z tail.
   Writing this body in that idiom reproduced retail instruction for instruction
   on the first build; the only work was decoding *which* argument each slot
   holds.
2. **The x87 switch shape is three stores, not four, and the fourth element
   lives in a register.** Each `case` writes `xs[0] = xs[2] = value` and
   `xs[1] = xs[3] = other`, but only three slots are stored: the second store of
   each chain leaves its value in the x87 register, and the corner expressions
   read it with `fld st(1)`. That is why the retail frame holds 11 floats and why
   the dead `default` path carries a "phantom" `fld` of an unwritten slot - the
   merge needs the depth to agree.
3. **Read the argument push before believing an `[esp+…]` slot.** The first
   `fld [esp+0x20]` of the store block sits *before* the `push 0` that sets up
   the tail call, so it reads E+0x1C; after the push the same spelling reads
   E+0x10. Misreading the first one as E+0x18 makes the body look like a crossed
   rotation in corner 0 and sends the search after a non-existent source quirk.
4. **`__asm` blocks containing a `push`/`call` cost the frame pointer.** A tail
   written as `__asm { push 0; mov eax,edx; call ... }` compiles to
   `push ebp; mov ebp,esp; ...` in a plain translation unit, which shifts every
   frame slot and destroys the match; the `fsincos` block alone is fine. The tail
   must be a real call - `manager->SubmitSpriteQuad(entity, 0)` - and in the
   cluster it emits retail's `mov eax,edx; push 0; call` because
   `SubmitSpriteQuad` is a definition there.
5. **Two pooled literals had to be rebound.** The body reads the shared float
   pool: `0.0f` at 0x00470B04 and `-0.5f` at 0x00470B78 are compiler-pooled
   copies in the cluster's own layout, so both are `constant_aliases`; `0.5f`
   at 0x00470B0C was already aliased by the cluster.
6. **One body buys two regions.** The twins differ in exactly four bytes - the
   two call displacements - so the second is a copy of the first, not a
   re-derivation. The plain-TU oracle
   (`compile one source with the maintained flags, diff the function body
   against the retail bytes`) settled each shape in ~0.6 s against the cluster's
   ~10 s, and an instruction-level diff that normalises relocation operands is
   what made "only the two call conventions differ" visible.
