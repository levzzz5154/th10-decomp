## The wave-11 blocker was not the entry convention

Wave 11 reported 437 bytes and blamed the entry: "retail enters with the mode in
EBX and the frame state read from the stack into EBP with RET 4".  There is no
`mode`: `src/platform/window.cpp:341` pushes exactly one argument
(`push 4924F0h`) and the callee ends `ret 4`, so `0x00439390` is a plain
one-stack-argument function and EBX is simply never touched.  Dropping the
invented second parameter and the invented `0x0043DDF0` EBX/EDI/ESI anchor (the
real dispatcher is `sub esp,0Ch; push ebp; mov ebp,[esp+14h]` - one stack
argument, `ret 4`, and it *saves* EBX/EDI/ESI itself) took the model to 425
bytes with 11 bytes out, and three measured levers closed the rest.

## The four deltas and what closed them

| delta | retail | model before | what fixed it |
| --- | --- | --- | --- |
| prologue | `push ebp; mov ebp,[esp+8]; push esi; push edi; call` | load after the call | **kept alive by the driver's synthetic call, not by `roots`** |
| catch-up loop | `fld [48]; fadd [0x470c90]; fstp [48]; fld [48]; fcomp [38]` | `fld [0x470c90]; fadd [48]` + register-folded loop | the step is the **literal `1.0 / 60.0`**, rebound to retail's own pool copy by a `data_aliases` entry |
| tick reset test | `mov al,[ebp+14]; inc al; mov [ebp+14],al; movzx ecx,[0x491d66]; movsx edx,al; inc ecx; cmp ecx,edx; jg` | `movzx ecx,[0x491d66]` hoisted, store sunk, `inc cl`/`jle` | the threshold is read through a **`const unsigned char& limit` local** and the test is written **`limit + 1 <= frame->tick`** |
| Sleep thunk | `push 0; fstp st(0); call [0x4660ac]` (no `add esp,4`) | `__cdecl` pointer, `add esp,4` | declare `0x004660AC` **`__stdcall`** |

### The prologue lever in detail

Pinned as an `/INCLUDE:` root the whole-program pass leaves the frame state in
its stack home and loads it into EBP *after* the timer call
(`push ebp; push esi; push edi; call; mov ebp,[esp+0x10]`, 11 bytes out at
0x00439391..0x0043939B).  Reached from the cluster driver's synthetic call the
pass loads it in the prologue exactly as retail does.  The same effect is
visible in the landed `0x0040B480` asset loader, which is kept alive by its
caller context and whose stock parameter is loaded in the prologue.

### The 1/60 step constant

`frame->next_tick_time += 1.0 / 60.0` pools an 8-byte literal
(`__real@3f91111111111111`); the layout's `data_aliases` binds that symbol to
retail's own copy at `0x00470C90` (bytes `111111111111913f`), which is exactly
`1.0/60.0`, and the link's `/FORCE:MULTIPLE` discards the pooled duplicate.
Written as a bound global the pass emits `fld [0x470c90]; fadd [ebp+48]`
instead of retail's `fld [ebp+48]; fadd [0x470c90]`.

### Three further measured facts

* the Sleep thunk declaration is `void (__stdcall*)(int)`: retail cleans the
  argument, so there is no `add esp,4` after the call;
* `0x00420CD0`'s state stays live across `0x00442F50` and `0x0044C150`'s object
  across its wait/sleep/close calls; those are the pressures that earn their
  EDI / ESI receivers, and no declaration can name them, so both are compiled
  as layout `anchors` (53 and 95 bytes) and never exported;
* `0x0043DDF0` needs no anchor at all: `extern "C" void __stdcall
  f(void* parameters)` bound at `0x0043DDF0` reproduces `push 492590h; call`
  and the value stays in ESI across it, because ESI holds the decoder's result
  and the dispatcher saves it.

## What this unblocks

* retires the last *use* of the `asm_Camera_ApplyRetail_00421480` stand-in
  (its declaration in `asm_symbols.hpp` is now unreferenced);
* the region was the only remaining caller the wave-11 note named for
  `0x00438AD0`'s recovery, and that dependency is now gone: `window.cpp`'s
  `push 4924F0h; call` is satisfied by a normal `__stdcall` body, so the
  frame-advance does not need the WinMain region recovered first;
* it proves the cluster path can express a *one-stack-argument* function whose
  parameter is loaded in the prologue, which the "root everything" habit
  cannot: worth copying for the remaining `mov ebp,[esp+8]` regions
  (0x00420870, 0x00434DD0, 0x00418930, 0x00421300 and the other 15 listed by
  `grep "mov ebp,dword ptr \[esp+8\]"`).
