# Score and stage entry ABI screen

Screened live Ghidra boundaries and call paths for the four unpromoted rows
`0x00417040`, `0x004172E0`, `0x00417660`, and `0x00417870`. The existing
`Path_DecodeXor` and manager-teardown notes cover different entries and were
left unchanged.

## Conversion: `0x00417660`

The former 16-byte naked fragment now has a small ordinary C++ member model in
[`unassigned_00417660.cpp`](../../msvc/src/unidentified/unassigned_00417660.cpp).
The retail instructions read the receiver's first dword, compare it with the
one stack argument, return the inequality in `AL`, and use `ret 4`. That maps
to `bool UnidentifiedIntField_00417660::IsNotEqualTo(int)`: on x86 MSVC the
member receiver uses `ECX`, the argument stays on the stack, and the callee
removes it.

Ghidra has no Function object at this address and reports no references to
`0x00417660`. The implementation therefore keeps the owner and field meaning
explicitly unidentified. The older M2803 exact-code attempt recorded 13/16
matching bytes for a readable member form; this semantic conversion does not
claim byte identity. The manifest now marks the 16-byte row as semantic and
preserves its previous assembly record. Its C++ method symbol is bound at the
same address. No shared declaration is needed because Ghidra reports no code
or data references to this fragment. No build, probe, or test was run.

## Remaining private-entry blockers

### `0x00417040` — score HUD update

Live Ghidra reports a 671-byte body, one caller (`0x00418190`), and no stack
parameters. Its first instruction reads the score-state receiver from `ESI`;
the only call site is the naked stage-update body at `0x004186DD`. The
high-level update is recoverable, but an ordinary standalone function cannot
receive that `ESI` input. Promoting it requires migrating the call site and
the coupled stage-update/helper cluster together. The current
`score_hud_update.cpp` D3603 blocker already records this dependency.

### `0x004172E0` — result overlay update

Ghidra reports a 668-byte body with an implicit `ECX` receiver and two stack
arguments, but its switch selector is read from incoming `EAX`. The sole call
site at `0x00409CBD` in `spell_card_end.cpp` pushes the two stack values, clears
`EAX`, then calls the entry. A typed C++ member prototype cannot express this
selector at the callee boundary; conversion requires migrating the
`0x00409C00` caller and overlay together. The existing D3202 blocker and
schema-2 next-lever note in `result_overlay.cpp` are current.

## Strong ordinary-entry candidate: `0x00417870`

Ghidra reports a 1009-byte function with one stack argument, `ret 4`, and
return values `0` on success and `-1` on failure. Its only direct xref is the
call from the existing semantic wrapper at `0x00417C76`; that wrapper passes
the global object at `0x00477810` through a `__stdcall(void*)` declaration and
does not consume the result. This is a conventional call path for
`int __stdcall StageEntry(void*)`, so the entry itself is suitable for an
ordinary C++ semantic implementation.

Its work is stage startup: it waits for the game-state manager, prepares score
state, registers two callbacks, copies thirteen words into the context,
creates stage managers and resources, then either clears the starting flag or
marks failure and retires created callbacks. Most reachable helpers have
conventional `__stdcall`, `__thiscall`, or `__fastcall` interfaces, and several
already have semantic C++ definitions (including the scheduler, path reset,
timer/resource setup, callback retirement, queued animation cleanup, and score
setter).

One helper creates a real cluster dependency: the call at `0x00417AFB` enters
`0x0042A6A0` with the score manager in `EBX`. Ghidra identifies that helper's
manager as `unaff_EBX`, and its current source records the private-EBX blocker.
A C++ translation of `0x00417870` cannot express this call with an ordinary
signature while `0x0042A6A0` remains an asm entry. The viable route is a joint
semantic migration of the stage entry and spell-data helper (or equivalent
semantic inlining of that helper's state update); the wrapper call itself
needs no adaptation.

No source conversion was made for this larger entry in this screen: despite
the conventional external entry, its private-EBX helper dependency needs a
cluster migration outside this range. Its current translation unit includes
the shared declaration
`void __cdecl asm_FUN_00417870_00417870()` while the manifest binds that asm
symbol at the entry. Converting the caller-facing symbol cleanly requires the
parent-owned manifest/header update together with that cluster's semantic
source. The ordinary signature and direct caller are established for that
integration. No build, probe, or test was run.
