# 0x0042A3E0 — wave 16: the four bytes are *not* source-controllable

2026-09-19, wave 16, agent `ReturnBlockPlacement`. Region
`asm_FUN_0042a3e0_0042a3e0`, `src/unidentified/FUN_0042a3e0_0042a3e0.cpp`,
`0x0042A3E0..0x0042A423` (68 bytes). Explored in the throwaway copy
`/tmp/ReturnBlockPlacement/msvc` (plain-flag oracle in `/tmp/ReturnBlockPlacement/{sweep,flags,w*}`
and the native-LTCG cluster in `/tmp/ReturnBlockPlacement/ltcg*`); the maintained
tree was not touched and **nothing was registered**.

Wave 15 ended on 68/68 bytes with four differing `rel8` displacements and left
open the question "is there a source shape that flips MSVC's exit-block
placement". This wave answers it: **no.** Roughly 2,200 compiled variants across
the source, the flags, and the whole-program (native-LTCG) path all reproduce
the *same* 68-byte body with the *same* four bytes differing.

Instruction-level delta — the whole function is byte-identical except the four
displacement bytes of the four early `return 1` branches (the fifth return-1
site, the null path's `je`, already targets `+0x3E` in both), and **both `ret`
blocks exist in both layouts at the same offsets**:

```
off     retail                        model
0x12    75 29   jne 0x42A41D           75 2F   jne 0x42A423
0x17    75 24   jne 0x42A41D           75 2A   jne 0x42A423
0x21    74 1A   je  0x42A41D           74 20   je  0x42A423
0x36    74 05   je  0x42A41D           74 0B   je  0x42A423
0x38    B8 06 00 00 00  mov eax,6       identical
0x3D    C3               ret            identical
0x3E    B8 01 00 00 00  mov eax,1      identical
0x43    C3               ret            identical
```

So the difference is only *which of the two identical `ret` blocks inherits the
shared "return" label*: retail shares the `ret` that the `mov eax,6` arm falls
into (`+0x3D`) and gives the null path a private epilogue at `+0x43`; the model
shares the `ret` after the null path's `mov eax,1` (`+0x43`) and duplicates an
epilogue for the `mov eax,6` arm at `+0x3D`.

## Why this is a negative result and not a missing spelling

Two measurements say the four bytes are decided *before* any of these levers can
act, i.e. by the compiler's block-ordering for this instruction stream:

1. **The merge is not value-based.** Changing the null return's value (`1` → `2`
   → `3`) and the mid returns' spelling (`return result` vs `return 1`, all eight
   mixes) leaves the branch target set *identical* (`+0x43`). So MSVC does not
   merge the five "return 1" sites by their constants; it sends every
   non-materialising return to the one labelled epilogue and puts that epilogue
   after the **last return-statement block**, which for this instruction stream
   is always the null materialisation. Retail's arrangement needs the epilogue
   *before* that block, and nothing in the source moves it.
2. **The nearest 63-byte shape proves the target assignment is available.** The
   `&&`-chain / nested-if single-return form (`if (scene && … ) { … } return result;`)
   emits the *same* branch assignment as retail — every branch, the null path
   included, to one shared `ret` — but hoists `mov eax,1` above the null test
   (`mov edx,[scene]`, `mov eax,1`, `je`, 63 bytes, all five checks targeting the
   single `ret`). Adding the second `result = 1;` def back — the thing that pins
   the 68-byte schedule — also pins the labelled epilogue to the end of the block
   list. The two requirements are mutually exclusive in this compiler.

Everything cross-checks: the whole function except those four bytes, both
`dir32` relocations, both `ret` offsets, the modulo's branch shape and both
entry/exit conventions are already retail's, so this is a return-block placement
residual of exactly the kind the brief describes — not a body or extent error.

## Conclusion for this region

The body and extent are proven, nothing can be registered (a non-exact layout must
never be), and I do not believe any further spelling of this body will move those
four bytes: ~2,200 variants across the plain compilation path, the flag space and
the whole-program (native-LTCG) cluster all landed on the same targets. What a
future attempt would need is a lever on MSVC 13.10.6030's
*exit-block ordering* rather than on the source: a per-TU flag the project cannot
adopt (only `/Os` moves the layout, and it rewrites the whole schedule), a
different toolkit, or a source construct that changes the compiler's block
*order* without changing the emitted instructions — none of which this sweep,
the flag sweep, or the whole-program path exposed. Recommend leaving the region
as assembly and spending the effort elsewhere.

Nothing is unblocked by this region either way. Two findings are worth carrying
forward to sibling work: the family clone `0x00429A30` (same body without the
`flags_58 & 4` check, 64 bytes) is a *different* shape (one shared epilogue, with
`mov eax,6` scheduled before the modulo test) and is not governed by this result;
and any region whose recovery wants the shared epilogue placed after the value
join while a cold block sits at the end should be expected to show the same
4-byte residual.

## 2026-10-05: what c2 does with the return blocks (traced, still not recovered)

Traced with `reference/compiler_traces/flowgraph/trace_lateflow_cl.py` (plain
`cl /O2` under gdb; dumps the tuple list around `FgDoLateFlowOpts`,
`FgCodeMotion` and `MscClean` and logs the merge/retarget calls).

Before the late flow passes the model is, in order:

    jcc cont ; mov eax,1 ; jmp EXIT          flags path
    cont: mov eax,1 ; cmp ... ; jne JOIN ... the three other tests
    mov eax,6 ; jmp EXIT                     (falls into JOIN with a result variable)
    JOIN: mov eax,eax ; jmp EXIT
    NULL: mov eax,1
    EXIT: ret

* The no-op `mov eax,eax` is deleted at the end of the first
  `FgDoLateFlowOpts` call.
* In the second call `FgDoLateFlowOptsOnce` finds `JOIN:` directly followed by
  an unconditional jump and forwards every reference to `EXIT`
  (`FgTransferLabelRefs`, c2 0x107b7407). This is unconditional for a label
  followed by a plain jump; whether the previous block falls into it does not
  matter.
* `FgCodeMotion` then replaces the remaining `jmp EXIT` after `mov eax,6` with
  a copy of the epilogue.

Retail's four branches point at that copied epilogue, so in retail the join
label was *not* forwarded: when the second pass reached it, something other
than a jump followed the label, and that something no longer exists in the
final code (it must have been removed in or after `MscClean`). A narrower
result type shows the shape (`unsigned char r` gives `JOIN: movzx eax,dl; ret`
with all four branches on JOIN and the null path last), but with a real
instruction. Narrow return types, inlined inner helpers and about 60 further
statement shapes (rig `build/experiments/check_42a3e0_claude`) do not produce
it. Open question: which source construct leaves a tuple in the join block
that survives late flow optimisation and emits no bytes.
