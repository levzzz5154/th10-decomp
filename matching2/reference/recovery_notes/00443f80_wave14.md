## The recovery

`0x00443F80..0x00443FA0` (33 bytes) is the short sibling of `0x00443FB0`
(643 bytes): project the entity's billboard quad, reject with `-1` when the
centre fell outside the normalized depth range, otherwise submit the shared
quad with mode 0. Its two callees are both private-convention:

| callee | retail entry | how it is reached |
| --- | --- | --- |
| `0x00443B60` (`BuildProjectedQuad`) | entity in EAX, no other argument | compiled ABI anchor at its retail address (`.text$06b04z01anchor`, 12 bytes) |
| `0x00442670` (`AnimationManager::SubmitSpriteQuad`) | entity in EAX, manager in ECX, mode on the stack, `RET 4` | already a definition of this cluster |

The body itself enters with the entity in **ESI** and the manager on the stack
(the callee pops it) - the dispatcher marshals `push ecx; mov esi,eax; call` -
so it is modelled as a **member of the entity**: `this` is the receiver the
pass re-homes into ESI because it is live across the first call, and the
manager argument stays in its stack home until the submission, which is what
retail's `mov ecx,[esp+4]` is. The first build of that shape was byte-exact.

### What was measured about the ordering (so the next attempt starts here)

Retail's y case 1/2 sums start with `render_offset.y` (0x350) and then use
`base_position.y` (0x338) before `position.y` (0x344); this compiler emits the
first two of that pair in the *other* order, whatever the source says. The
shapes tried through the cluster, all with the rest of the body unchanged:

| shape for the y case 1/2 sums | emitted first two loads | differing bytes |
| --- | --- | --- |
| `(R + B) + P` (baseline) | `B, R` | **8** |
| `(B + R) + P` | `B, R` | 8 |
| `R + B + P` linear (all six permutations) | `P, R, B` | 12 |
| `R + B + P + H` / `(R + B + H) + P` / `((R + B) + P) + H` | `B, R, …` | 12 |
| `R + (B + P)`, `P + (B + R)` | inner pair first, `B` first | 8-12 |
| two statements (`top = R + B; top += P;`) | `B, R` | 8 |
| three statements (`top = R; top += B; top += P;`) | reused | **466-byte body**, wrong |
| `volatile float base = R + B;` reused per case | frame change | 63 |
| `*(const float*)((const char*)this + 0x350) + B + P` | `B, R` | 8 |
| `R * 1.0f + B + P` | `B, R` | 8 |
| chained assignment to the quad globals instead of a local | `B, R` | 8 |
| case bodies written in the order 2,1,0 / expression order permuted | `B, R` | 8 |
| y case 0 written `B + P + R - half` (its own bytes unchanged) | `B, R` | 8 |
| x case 1 written `(R + B) + P` (diagnostic - breaks the x switch) | `B, R` | 8 + x |
| the body as the anchor's *free function* (`entity` a parameter, not `this`) | `B, R` | 8 |
| the same model in the cross-landing link (0x00443FB0/0x00444580 definitions present) | `B, R` | 8 |

Measured rules this produced: a **parenthesised pair** `(X + Y) + Z` emits the
pair in **ascending struct offset** order whatever the source order; a **linear**
three-term sum emits `last, first, middle`; the only shapes that preserve source
order are the two whose sum is the left operand of a subtraction (`... - w*0.5f`
in the x switch's case 0 and `... - half_height` in the y switch's case 0), which
is why those two match. Retail's case 1/2 chains are plain sums (no subtraction,
no register operand), so under those rules their order is unreachable from any
spelling of `R + B + P` tried here; the next attempt should look for the
construct that makes the *first* operand the accumulator - a live register
operand in the y switch, or the real original expression - rather than another
permutation of the same three loads.

The model and its wiring are kept in the scratch copy
(`/tmp/DispatchHelperC/msvc/src/render/anchored_quad_build_00443290.cpp`); it is
**not** part of the package, because a non-exact layout must never be
