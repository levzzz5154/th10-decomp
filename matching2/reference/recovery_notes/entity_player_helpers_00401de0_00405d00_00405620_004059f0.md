# Entity/player helper cluster recovery (0x00401DE0, 0x00405D00, 0x00405620, 0x004059F0)

The `0x00405D00` block in `src/game/entity.cpp` now has an ordinary C++ semantic implementation with the retail ECX/EAX ABI expressed as a one-argument `__fastcall` function. Its manifest row is promoted to semantic and records the decorated fastcall symbol; the old raw assembly label is retained as a linker fallback. No build, probe, or test was run. The other three regions remain their assembly implementations.

## Recovered behavior and ABI

- `0x00401DE0` (273 bytes), `InitializeEntity`: custom fastcall with the entity in EDX and unused ECX. It preserves position at `+0x340..+0x348` and render bucket `+0x20`, clears `0xEB` dwords, restores those values, installs the identity transform/default scales and color, initializes the timer sentinel and animation marker, and creates two empty self-owning list nodes.
- `0x00405D00` (215 bytes), entity runtime reset: member-shaped entry with the object in ECX and the same pointer returned in EAX. A one-argument `__fastcall` C++ entry has the same register and stack contract. Retail first clears bit zero in nine words at `+0x74`, `+0xB8`, `+0x104`, `+0x130`, `+0x17C`, `+0x1B8`, `+0x204`, `+0x230`, and `+0x380`; all nine are then covered by the following zero-fill of `0x3AC` bytes from `+8`. It writes `0xFFFF` at `+0x38C`, clears bit zero in the outer words at `+0x408` and `+0x41C`, and clears **nine** late flags at `+0x624 + n*0x34` for `n = 0..8` (last offset `+0x7C4`). The archived semantic source stopped at eight late flags; the current source model includes all nine.
- `0x00405620` (137 bytes), `ReleaseRawPairAndReset`: stdcall, pair on the stack, `RET 4`. It conditionally removes callbacks at `+8` and `+0xC`, surrounding each `Scheduler_Remove` with the retail critical-section/depth bookkeeping, then clears only global `0x004776EC`. The archived source's null/device guard and callback-slot clearing are not present in retail.
- `0x004059F0` (202 bytes), player hit test: player in ECX and tested position in EAX, plain return. It performs the direct-hit squared-radius test and returns the focus/game-state/config-dependent hit codes; the non-hit path applies the graze-state result rules.

## Focused 0x00405620 caller/callee follow-up

Retail xrefs identify four direct callers:

- `0x004056B0`, allocation/initialization with release-on-install-failure;
- `0x00405730`, null-checked release followed by heap free;
- `0x0040A1A0`, manager teardown;
- `0x00417C80`, global game-state teardown.

The large `0x00417C80` caller also contains an inlined two-callback removal sequence at `0x00418000`. That sequence is decisive ABI evidence: it keeps the scheduler in EDI, EnterCriticalSection in EBX, LeaveCriticalSection in EBP, and emits `mov ecx,esi` before `mov edx,edi` at both calls to `0x00449F60`.

A focused native-LTCG topology compiled semantic `0x00405620` with the concrete adjacent `0x00405730` caller and source-level `__declspec(dllimport)` declarations for the Win32 critical-section APIs. It retained the exact 137-byte release extent and the exact 18-byte caller extent. The caller matched retail completely. The release helper matched through `+0x2E`, then emitted:

```text
candidate +0x2E: 8B D7 8B CE   mov edx,edi; mov ecx,esi
retail    +0x2E: 8B CE 8B D7   mov ecx,esi; mov edx,edi
```

The same mismatch repeats at `+0x62`/`+0x64` for the second callback.

To distinguish an opaque external-call lowering issue from a missing callee graph, a task-local profile implementation of the read-only `Scheduler_Remove` semantics was compiled at `0x00449F60` under native LTCG. Its complete 114-byte body matched retail exactly, and `0x00405730` remained exact, but `0x00405620` still produced the same two reversed register moves. The maintained `scheduler_tasks.cpp` and its layout were never modified or merged.

No focused candidate was promoted. The remaining blocker is the precise original source expression or compiler scheduling context that orders the two independent custom-ABI register materializations as ECX then EDX. Caller visibility, source-level Win32 imports, exact callee semantics, register ownership, extent, and all surrounding instructions are now ruled out independently. A next attempt should investigate an original class/member declaration or front-end expression shape for the removal call, not another scheduler-body or caller-layout variant.

## Focused Ghidra recheck of 0x004059F0

The connected `th10.exe` program identifies the leaf as `TestPlayerHit` and returns pseudocode for its squared-radius direct-hit test, state-dependent hit codes, and graze-state result. Ghidra reports `int __fastcall TestPlayerHit(int param_1)`, but its decompilation also has a phantom `float *in_EAX`: the input coordinate pointer is an unmodeled register input, not a second declared parameter. The disassembly confirms direct reads from `[EAX]` and `[EAX+4]`, while the player fields are read through ECX; the integer result is returned in EAX.

Ghidra finds one caller, `FUN_00428630`, at 0x00428891. The exact call-site sequence is:

```text
00428889  MOV ECX,dword ptr [0x004776ec]
0042888F  MOV EAX,EDI
00428891  CALL 0x004059f0
```

The EAX value is therefore live as the tested position at the actual call boundary. This confirms the prior 202-byte semantic candidate's main issue is structural, not missing caller evidence: ordinary MSVC `__thiscall` and `__fastcall` signatures cannot name an explicit input in EAX. The previous native-LTCG attempt also emitted 223 bytes and first diverged at `+0x36`, where the direct-hit state branch schedule differed. No source was changed and no build, probe, or test was run for this recheck.

## Retained exact caller at 0x00405730

The adjacent lifecycle caller is retained as readable semantic C++. Its behavior is expressed by the inlined `PlayerRuntime_ReleaseAndFree` helper: ignore a null runtime; otherwise call the `0x00405620` contents-release routine and then free the runtime allocation. The compiler-owned entry keeps its established symbol for ABI/layout compatibility and receives the runtime in ESI through the existing native-LTCG context.

Focused proof with `layout/ltcg/player_runtime_release_and_free_00405730_proposal.json` verifies the complete `0x00405730..0x00405741` extent: 18 of 18 bytes exact, including both relative call targets. The proposal changes only the manifest display name to `semantic_PlayerRuntime_ReleaseAndFree_00405730`; `regions.json` was not edited. The existing `fun_00405730.json` and `fun_00405730_context.cpp` remain the required exact native-LTCG layout and compiler context.

## Sibling constructor 0x0040A040: same store-grouping wall

`0x0040A040` (234 bytes, `_DWORD* __fastcall(int, _DWORD*)` — object in EDX,
unused first argument in ECX) is the full-construction twin of the `0x00405D00`
reset: it writes the type marker `0x4703E4` at `+0x10` and twenty scalar defaults,
clears bit 0 of nine flag words inside the `0x3AC`-byte block at `+0x2C8`
(`+0x6C + n` up to `+0x378`), `memset`s that block, writes `0xFFFF` at its
`+0x384`, `memset`s the whole `0x688`-byte object, raises bit 1 of `+0x00` and
publishes the object through `data_004776F8`, returning it in EAX. The first
nine defaults are dead — retail zeroes the object afterwards.

A complete reconstruction (flattened struct with a nested block type, statements
written in retail's emitted order) compiles to **292 bytes against retail 234**,
differing in 190 bytes: MSVC sinks the immediate type-marker store below the
zero-store run, hoists the `1`/`0x3E7`/`~1` constants differently, and emits
load/and/store for the nine flag clears where retail uses in-place
`and [esi+disp],eax`. The `+0x2C8` block base, the offsets and the dead-store
order are confirmed; the construct that prevents the store regrouping is not
found, exactly as for `0x00405D00` and `0x00418D40`.
