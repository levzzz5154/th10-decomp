# DAT interleaved-XOR cipher pair

2026-09-26. `reference/semantic_candidates/dat_crypt.cpp` contains tested,
assembly-free models of decryption at `0x0044B0D0` and encryption at
`0x0044B220`. Both maintained regions remain assembly: the private calling
convention and MSVC byte match are still outstanding.

## Retail evidence

The saved Ghidra `.c` and `.asm` files under
`decompiled/ghidra_augmented/functions/0044B0D0.*` and `0044B220.*` identify
the rolling-key input in AL, five stack arguments, malloc/free calls, signed
division, and signed loop comparisons. The complete maintained intervals are
323 bytes at `0x0044B0D0` and 307 bytes at `0x0044B220`. Decryption includes
the three alignment bytes before its second inner loop at `0x0044B1C0`.

Both retail routines take, in stack order, data pointer, signed size, byte
step, signed block size, and signed byte limit. Key is an additional AL input.
They return the original data pointer and execute **RET 20**, so the earlier
note calling this a cdecl convention was incorrect. The candidates expose key
as a sixth ordinary stdcall argument for semantic testing. Their resulting
RET 24 entries are not drop-in replacements for the retail entries.

Direct call-site evidence also recovers these key/step/block parameters:

| Use | Key | Step | Block | Evidence |
| --- | ---: | ---: | ---: | --- |
| DAT header | `1B` | `37` | `10` | Call at `0x00434FCA` |
| DAT index | `3E` | `9B` | `80` | Call at `0x00435050` |
| Score payload | `AC` | `35` | `10` | Calls at `0x0042B064`, `0x0042B335` |
| Replay inner layer | `3D` | `7A` | `80` | Calls at `0x0042A2FF`, `0x00429E7D` |
| Replay outer layer | `AA` | `E1` | `400` | Calls at `0x0042A2E8`, `0x00429E91` |

The byte limit equals payload size at these sites (the header uses 16 for
both). DAT file contents instead select one of eight twelve-byte records at
`0x00474BD8`, containing key/step bytes and block/limit words. The differential
test reads this actual table from the retail image and exercises its limits.

## Recovered behavior

The routine first computes `size % block_size` with signed division. It drops
that remainder when it is smaller than `block_size / 4`, and independently
subtracts one byte for an odd total size. Thus the remaining transform count
can be negative even for a positive input size: size 1 and block size 16 yield
-1 and skip transformation.

Allocation requests `min(size, byte_limit)` bytes using a signed comparison.
Failure returns the original data pointer unchanged. Success copies that many
bytes to a temporary snapshot, even when the transform loop will do nothing.
The temporary is freed on every successful allocation path.

Decryption reads the snapshot sequentially and fills each destination block
backwards in two passes: last byte, last-minus-two, and so on, then
last-minus-one, last-minus-three, and so on. Encryption reverses that
permutation, reading the two descending interleaved sequences and writing
sequentially. Each byte is XORed with a key that advances by the step modulo
256. The key continues across block boundaries.

The byte limit only controls whether another block begins. The current block
is clipped by the remaining transform count, **not** by the byte limit. The
limit then decreases by the complete block length, and the signed loop stops
if it becomes nonpositive. The legacy semantic implementation used an unsigned
limit counter, which could wrap and continue into further blocks. For example,
size 32, block 16, limit 1 starts one block in retail; the unsigned model can
start a second block after wrapping. The new models preserve the signed stop.

For limits that end partway through a block, retail can read past the requested
snapshot allocation. The test supplies identical initialized backing arenas
to both executions to make these reads comparable. It does not clamp them or
claim these parameter combinations are memory-safe. Positive block sizes are
the supported/tested transform domain; division by zero, negative block sizes
and signed-overflow cases are not given invented C++ behavior.

## Verification

`matching2/tests/dat_crypt_differential.py` compiles both candidates with native
Clang to x86 Windows COFF, resolves their relocations to known retail symbols,
and emulates the original and recovered functions independently. The test
supplies AL plus five stack arguments to retail and six stack arguments to
the candidate, then verifies the corresponding stack cleanup and preserved
registers. It checks the complete output, ordered destination writes and
snapshot reads, allocation/free events, copied snapshot contents and trailing
guards. The conventional `memcpy` call in Clang output binds to the original
retail memcpy at `0x0045BFC0`.

The fresh-build run passed **1666 retail comparisons**, **596 round trips**,
and **232 boundary configurations** that reproduce reads past the requested
snapshot size. Round trips are asserted only when the complete transformed
data fits within the snapshot. Cases cover:

- Zero/one/two bytes, quarter-block thresholds, block boundaries and two-block
  boundaries for eleven block sizes, including odd sizes.
- Zero, short, aligned and unaligned limits, key wraparound and zero step.
- One hundred seeded random configurations.
- All eight actual DAT parameter rows at their limit boundaries, and the five
  header/index/score/replay parameter sets above.
- Ten allocation failures, including signed negative size or limit values;
  the data remains unchanged and no free occurs.

Reproduce with native `clang++`, the project MSVC headers and Python's
`unicorn` package:

```sh
python3 matching2/tests/dat_crypt_differential.py
```

The local run used
`matching2/build/lzss-compressor-recovery/venv/bin/python`. Each Clang function
is 368 bytes with the test flags. This is not an MSVC byte comparison.
