## What the region is

0x00448E80 is the second member of the animation manager's four-flavour
positioned-create family (documented in
`src/render/fun_00449950_00449950.cpp`); it is the *primary-front* flavour:

| region | flavour | list call |
|---|---|---|
| 0x00448D50 | primary back (landed wave 10) | 0x004489D0 RegisterPrimaryBack, tail insert |
| **0x00448E80** | **primary front** | **0x00448A50 RegisterPrimaryFront, head insert** |
| 0x00448FB0 | secondary back | 0x00448AC0 RegisterSecondaryBack, tail insert |
| 0x004490E0 | secondary front | 0x00448B40 RegisterSecondaryFront, head insert |

The body takes an object from the manager's animation pool, marks it positioned
(bit 30 of +0x35C), clears its render bucket at +0x20, copies the caller's
12-byte position record into +0x340, loads the script for the requested index,
and hands the object to the primary-front registration, which assigns the handle
and stores it through the caller's out slot; the out slot is what the function
returns. Retail enters it with the position record in **EDI** and the other
three arguments on the stack, and leaves with `ret 0xC`.

The only difference from the wave-10 region 0x00448D50 is the final call: this
body's bytes are 0x00448D50's bytes with the last `e8` displacement retargeted
from 0x004489D0 to 0x00448A50.

## The lever: an anchor's *body shape* decides the caller's entry registers

This is the one transferable finding of the landing, and it is why the region
needed the cluster path. The three callees read their arguments from registers no
declaration can name

* 0x00449950 manager in **ESI**,
* 0x0043E710 resource in **ECX**, object in **EAX**, index in **EBX**,
* 0x00448A50 manager in **EDX**, entity in **EBX**, handle record in **EAX**,

so each is carried as a compiled ABI anchor in the cluster driver. The 0x00448A50
anchor is the delicate one: a *semantically identical* head-insert body whose
node is provably fresh has the node's outgoing link folded away, and the /LTCG
pass then hands that callee **EDI** for the entity. The caller has nowhere left
to keep the incoming position but EAX, which does not survive the pool-allocator
call, so the pass copies it into a callee-saved register and adds a fourth push:
the caller grows to 97 bytes with the position in EAX and the object in EDI.

| anchor body for 0x00448A50 | emitted entity register | caller | differing |
|---|---|---|---:|
| head insert, node provably fresh (successor read folded away) | EDI | 97 bytes, position in EAX, object in EDI | 75 |
| head+tail read up front, successor still folded | EDI | 97 bytes | 75 |
| successor kept live with a spurious `prev` store | (pass re-conventioned the caller) | 91 bytes | 88 |
| **head insert, the node's existing successor captured before the zero stores** | **EBX** | **95 bytes** | **0** |
| head insert, successor read through a `volatile` lvalue | EBX | 95 bytes | 0 |
| wave 10's tail-insert body (the 0x004489D0 shape) | EBX | 95 bytes | 0 |

Retail's own 0x00448A50 does exactly this: it reads `node->next` at 0x00448A77
*after* it has already cleared it at 0x00448A56 (its `head->next` store at
0x00448A7E therefore writes the value it just read), which is why the anchor
keeps that read. Keeping it is what earns EBX; the two EBX rows are the two
measured spellings (`capture first` and `volatile read`) and the landed driver
uses the first.

The second, smaller lever is the driver's **shape**: the synthetic context emits
82 bytes under the fold shape and 92 bytes under the EBX shape. The layout
therefore declares 92, and the first registration attempt with 82 failed with
`function is not its entire declared compiler contribution`.

## Does this unblock anything?

Measured, not assumed:

* **No region flips as a direct consequence.** The 73-byte creators
  (0x00448E30), the 118-byte offset creators (0x00448EE0) and the manager's
  other methods remain assembly, and none of them is a region the manifest
  currently reports as differing.
* **The two remaining positioned creators now have one recipe each.** 0x00448FB0
  and 0x004490E0 are this same 95-byte body with the registration call swapped
  for 0x00448AC0 and 0x00448B40. Each needs its own single-source cluster with
  the same two anchors plus one anchor for its own registration callee, whose
  body only has to earn `(manager in EDX, entity in EBX, handle in EAX)`: the
  *tail-insert* body does it for the back flavours and the *successor-captured-
  first* head insert does it for the front ones - both measured here.
* **0x00448A50 and 0x00449950 are now anchored twice** (here and in wave 10's
  `positioned_primary_00448d50_wave10.json`), confirming that the duplicate
  anchor is the cheap reuse path for the rest of the family.
* **The transferable lever** is that an ABI anchor must be judged by the
  register it *earns*, not by how faithful its body looks: two bodies that
  compute the same function differ by a folded load and hand the callee
  different registers, which moves the caller by two bytes and three registers.
