## What the region is

`0x00448980` is `AnimationManager_00442F50::RenderBucket(int)`: it indexes the
manager's 0x3AC-stride animation-bucket array at `manager + 0x72DB00`, walks the
bucket's entity list through the `+0x1C` next link, skips a node whose flag word
has bit 26 set, offers each remaining node to its own `+0x39C` callback and then
hands it to the per-kind dispatch at `0x004451C0`. It returns 1. The scheduler
registers it as the frame task of every bucket wrapper (`0x004485F0`..`0x00448810`),
which is why its receiver is the animation manager the wrappers hold in ECX.

## The three load-bearing shapes

All measured against retail's own 67 bytes in the throwaway copy.

| shape | emitted | differing |
| --- | ---: | ---: |
| member declaration, **rooted** (`/INCLUDE`) | 84 | 82 — the declared `__thiscall` ABI is pinned: `mov eax,[esp+4]`, `mov edi,ecx`, `ret 4` |
| `extern "C" __cdecl` free function, **rooted** | 84 | 82 — the declared `__cdecl` ABI is pinned: both arguments from the stack |
| member, not rooted, anchor declared `(entity, manager)` | 67 | 2 — `mov ecx,edi / mov eax,esi`, retail wants `mov eax,esi / mov ecx,edi` |
| **member, not rooted, anchor declared `(manager, entity)`** | **67** | **0** |

1. **The modelled function is a `__thiscall` member and is deliberately not in
   `roots`.** The whole-program pass only assigns a custom convention to a
   function it can rewrite; `/INCLUDE:<symbol>` pins the declared public ABI, so a
   rooted member keeps `ret 4` and a rooted free function keeps the stack. This is
   the opposite of what the sibling task landed: `0x00448740` and the three stage
   tasks *are* rooted, because retail enters them in ECX, which is exactly their
   declared convention. Rooting is only needed to keep an ABI that the pass would
   otherwise change; here the pass has to change it. The function survives
   `/OPT:REF` because the synthetic context calls it.

2. **The synthetic context is what makes the pass choose retail's registers.** It
   walks an array of managers and calls the member in a loop; the manager is live
   across the hook call inside the callee, which is the pressure that earns EDI,
   and the index is read once, which leaves it in EAX. No declaration names either
   register.

3. **`0x004451C0`'s entry has to be earned, and its parameter order is
   load-bearing.** The dispatch is entered with the entity in EAX and the manager
   in ECX — before this landing its anchor passed both on the stack because this
   link had no body for it, which is the one byte that made the sibling anchors 68
   and 4 bytes off retail. The anchor's body here is a compiled body placed at
   `0x004451C0` (`0xDC` bytes, `0x4451C0..0x44529C`) whose shape is retail's own
   dispatch: the flag word at `+0x35C` gates bits 0/1, the visible byte at `+0x2FF`
   gates the rest, and a jump table on `(flags >> 22) & 0xF` selects the ten
   pipelines. Only the register assignment matters, and its *parameter order*
   decides the order in which the caller materialises the arguments: declared
   `(entity, manager)` the caller emits `mov ecx,edi / mov eax,esi`, declared
   `(manager, entity)` it emits retail's `mov eax,esi / mov ecx,edi`. The
   registers come out (EAX entity, ECX manager) either way — the
   declaration order only reorders the setup, which is exactly the "an anchor's
   parameter order decides the caller's argument-setup order" lever.

`case 7` of the anchor calls the *recovered* `DrawStrip` through its real
declaration (`?DrawStrip@AnimationManager_00442F50@@QAEHPBURenderEntity@@PBXI@Z`,
bound `relative_code` at `0x00444CE0`); the other nine pipelines are opaque
bindings at their retail addresses. The anchor's own bytes are never exported.

## Does this unblock anything?

Measured, not assumed.

* **All 19 caller regions of `0x00448980`** — 20 call sites: the 929-byte
  `0x00402CA0` (two sites), the twelve-byte wrapper `0x004485F0` (the
  `xor eax,eax` form) and the twelve fifteen-byte wrappers

  landed ones `0x00448620`, `0x00448740`, `0x00448770`, `0x004487C0`,
  `0x00448810`.
* **None of them can drop its anchor while it stays in its own cluster.** An
  anchor is not a model of the callee — it is the only spelling of the call, and
  a cluster that merely binds the recovered symbol gets the declared convention
  and emits a stack-passing call. The five landed callers keep the anchors the
  camera cluster and `fun_00448740_wave11.json` already carry.
* **What the recovery does change is where the fourteen unlanded callers land.**
  The body is now in this cluster's link, so a wrapper modelled here calls
  `RenderBucket(n)` directly and needs no anchor. Measured in the scratch copy: the
  `0x004485F0` shape, `AnimationManager_00442F50::RenderSlot0() { return

  anchor in the link, reproduces retail's twelve bytes exactly

  the layout's gap for `0x448980` bakes. That is the shape all fourteen remaining
  wrappers have, so they land anchor-free by being added to this cluster's
  `additional_sources`.
* The five landed callers can follow only if their spans are retired into this one:
  `load_clusters` requires distinct maintained sources, so
  `src/render/animation_manager_render_bucket_00448980.cpp` can live in exactly one
  cluster and the camera span cannot co-compile it alongside its own source set.
* A control experiment worth recording: dropping the anchor and co-compiling the
  body is not by itself enough for a *larger* caller whose own register plan
  depends on other callees. Re-building `0x00448770` in a two-function

  opaque `__thiscall` binding instead of the co-compiled body the camera cluster
  has, the caller came out 68 bytes and 61 bytes off — the caller's allocation is a
  property of the whole link, not of the `0x00448980` declaration alone. The
  wrapper shapes above have no other callee, so the measurement is clean there.
