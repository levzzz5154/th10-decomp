# 0x0044C2A0 (171 bytes) - the x87 sum rule where it should apply: NOT EXACT

2026-09-19, worker `PoolLeverX87`, wave 15. Region
`0x0044C2A0..0x0044C34A`, 171 bytes,
`src/game/recovery_advance_polar_motion_0044c2a0.cpp`. All work in
`/tmp/PoolLeverX87/msvc` (a `cp -a` of the maintained tree); the throwaway
layout/driver pair `layout/ltcg/polar_advance_0044c2a0.{json,_context.cpp}` was
registered only for the measurement and **unregistered again** - the maintained
tree is untouched, no `make`/`build_msvc.sh`/`build_msvc.py` was run, and a
non-exact layout is not registered anywhere.

Chosen deliberately as the sum-rule target: it is the one non-semantic region
whose disassembly is full of `fld [reg+off]` / `fadd [reg+off]` pairs *over
struct fields of the same base* - three `position += velocity` pairs at
`(0x00,0x0C)`, `(0x04,0x10)`, `(0x08,0x14)` - so both halves of the wave-14 rule
are testable here, unlike in the landed `0x00418810` (whose sums are one field
plus a pooled literal).

## Disposition

Registered, built and compared through the native-LTCG path:

```text

MAP:      .text$01advance  000000a0H   -> emitted 160 bytes, retail 171
          81 of the 160 emitted bytes differ from retail
```

So: **the model emits 160 bytes against the declared 171**, 81 differing bytes,
and the difference is *structural* (three sites), not a single wrong operand.
The pass did choose retail's register (the motion state in ESI, no prologue copy)
and the whole head and tail of the body come out retail's, including:

* `mov al,[esi+0x28]; sub esp,0x18; test al,0x1; jne 0x44c2c5` - the flag byte
  loaded into AL, the frame set up *before* the test, and the branch polarity -
  all exactly retail, where the same source through a plain `/O2` TU emits
  `sub esp,0x18; push esi; mov esi,ecx; test byte ptr [esi+0x28],1`. This is the
  LTCG pass's allocation, not a source shape;
* the polar call marshalling `mov eax,[esi+0x20]; mov ecx,[esi+0x1c]; push eax;
  push ecx; lea ecx,[esp+0x14]; call 0x44c5d0` (angle `+0x1C`, radius `+0x20`,
  receiver = the local vector at `[esp+0xc]`);
* the two-local spill pattern with the float sums stored to the frame slots and
  reloaded as dwords (`fstp [esp]; mov ecx,[esp]; mov [eax],ecx`), including
  `mov eax,esi` as the destination pointer;
* the quantisation tail `sub esp,8; fmul [0x470b44]; fstp QWORD [esp]; call
  0x452ff0; fmul [0x470b00]; fstp [esi]` - the pooled `100.0f`/`0.01f` pair with
  the cast bound to `floor` and not to the product.

* **1** is the x87 pair order in the *linear* branch (same size, so it does not
  move the extent on its own). Retail's `x` pair is destination-first while its

* **2** is 7 bytes: retail keeps a *dead* `offset.z = 0.0f` store - the polar

  original source read the local's z into the result (a whole-struct addition
  whose z term folds to `velocity.z`), so the compiler could not drop it.
* **3** is 3 bytes: retail restores the call argument area between the two
  `floor` calls (`add esp,8` at `0x44c341`) where the model keeps one frame
  adjustment to the end.

## The sum-rule answer

**The rule did not predict this body, and the reason is now measured rather than
guessed.** The wave-14 rule is about a *three-term / parenthesised* expression:
`(X+Y)+Z` emits its addends in ascending struct-offset order whatever the source
says, and only a sum that is the left operand of a subtraction keeps source
order. A bare two-term `a += b` is outside that rule, and here the emitted pair
order:

* is **not** controllable by the source - all six spellings of the three
  statements (destination-first, velocity-first, member-qualified, `+=`, full
  assignment) compile to the *same* velocity-first pair in the same translation
  unit, in the plain build and in the LTCG build;
* is **not** a pure function of the offsets either - retail emits
  destination-first (`fld [esi]; fadd [esi+0xc]`) for the first pair and
  velocity-first for the other two, in the same three statements, and the two
  callers `0x00425730`/`0x0040DC80` show the same mix in their own adjacent
  pairs;
* therefore it is an allocator/scheduling artifact of the surrounding body - the
  same residual class the 2026-09-13 reconnaissance recorded for `0x00443290`
  ("the 94-byte shortfall is structural"), and it is why this region stops at a
  delta rather than at retail.

The rule's *first* half was confirmed where it does apply: in the landed
`0x00418810` the rule's prediction held for `field + pooled literal` in either
source order (see `00418810_wave15.md`). What this body adds is the boundary:
**a two-term sum is not a rule case at all**, and in this image it is decided by
the schedule.

## What is left here

The 171-byte body is a good cluster candidate for a later wave: the callee
bindings are known and cheap (`_floor` -> `0x00452FF0`,
`?SetPolar@<type>@@QAEXMM@Z` -> `0x0044C5D0`, `__ftol2` -> `0x00463B2C`, all

`__real@3c23d70a` -> `0x00470B00`, and the driver that earns the ESI receiver is
an array walk whose receiver stays live across the two calls. The remaining work
is the linear path's first pair, the polar path's kept `offset.z` store (a
whole-struct addition reading the local's z), and the tail's `add esp,8`
placement - none of which any spelling tried here moved.
