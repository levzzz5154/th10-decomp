# D3D initialization recovery (`0x00439890`)

## Disposition

No semantic source was promoted. The production region remains its original
1159-byte exact assembly implementation in `src/render/d3d_init.cpp`; no
manifest or shared-tooling file was changed. The legacy registry's 1168-byte
extent includes the nine bytes of padding at `0x00439D17..0x00439D1F`; the live
function itself ends with the `ret` at `0x00439D16`.

## Caller-visible ABI

The live caller at `0x00438C2C` calls the function without arguments and tests
only `EAX`. The function is a plain `__cdecl`/plain-`ret` boundary returning
zero after successful setup and one after the terminal device-creation failure.
Its retail body owns a `0x70`-byte frame and preserves `EBX`, `EBP`, `ESI`, and
`EDI`.

## Recovered device flow

The retail stack contains a typed 16-byte display mode and a 56-byte
`D3DPRESENT_PARAMETERS`. The parameters are cleared with `rep stosd`, then
`IDirect3D9::GetAdapterDisplayMode` (vtable `+0x20`) supplies the current mode.
Configuration bytes at `0x00491D62`, `0x00491D65`, and `0x00491D78` select
back-buffer format `0x16` or `0x17`; replay/vsync state at `0x00492518` and
`0x00491FDC` selects refresh rate 60 or 0 and presentation interval one or
immediate. The common fields are width 640, height 480, swap effect one,
automatic depth/stencil enabled with format `0x50`, and flags one.

Device creation uses the window at `0x004924F0`, output slot `0x00491C30`, and
`IDirect3D9::CreateDevice` (vtable `+0x40`) in this order:

1. HAL (`DeviceType=1`) with hardware vertex processing (`0x40`). Success logs
   `0x0046F4A8` and sets status bit 0 at `0x00491FF4`.
2. HAL with mixed vertex processing (`0x20`). Success logs `0x0046F4C4` and
   clears status bit 0.
3. Reference device (`DeviceType=2`) with `0x20`. Success logs `0x0046F4D8`,
   clears status bit 0, and clears the stack byte that later gates the HAL-only
   format-capability check.

On failure, the routine can retry after clearing the fullscreen refresh rate,
or change an immediate interval to interval one and swap effect three. If that
fallback is already exhausted it appends the fatal message at `0x0046F514`,
calls `IDirect3D9::Release` through vtable `+0x08`, clears `0x00491C2C`, and
returns one.

After creation, the 14 presentation dwords are copied to `0x00491D0C`. The
camera is built from eye/target `(320,-560,0)`, up `(0,1,0)`, and target Z
`-(float@0x00470BFC / tan(double@0x00470C00))`. It calls the D3DX look-at and
perspective helpers, then device `SetTransform` twice (`+0xB0`) and
`SetViewport` (`+0xC0`).

The legacy semantic source mislabeled two COM calls. Device vtable `+0x1C` is
`GetDeviceCaps`, writing the caps block at `0x00492000`; the subsequent tests
read `+0x90` bit `0x40` and compare dword `+0x58` with `0x100`. D3D9 vtable
`+0x28` is six-argument `CheckDeviceFormat`, called for HAL, the selected
adapter format, usage zero, resource type three, and format `0x15`. Success
sets status bit 2; failure sets configuration bit 0, clears status bit 2, and
logs `0x0046F3C0`.

Finally the routine calls the already-semantic device-default setup at
`0x00439D20`, applies the default viewport through `0x0043BCD0` with bit pattern
`0xFF000000`, clears `0x004924F4` and `0x00491FE4`, and returns zero.

## Candidate and mismatch evidence

A readable VC7.1 `/O2 /Gz /G6` candidate used typed `Direct3D9Vtable`,
`Direct3DDevice9Vtable`, display-mode, presentation-parameter, and vector
aggregates. Its first form was 1193 bytes. Replacing the compiler-expanded
clear loop with intrinsic `memset` recovered the retail `rep stosd` shape and
produced the best 1153-byte body, six bytes shorter than retail.

The best candidate matches the first four bytes and diverges at `+0x04`:

```
candidate: 83 EC 70 53 56 57 33 C0 8D 54 24 34 ...
retail:    83 EC 70 53 55 56 57 33 C0 8D 54 24 38 ...
```

The missing `push ebp` reflects different long-lived register allocation:
retail keeps zero in `EBX`, one in `EBP`, retry state in `ESI`, and the
immediate-interval constant in `EDI`. The typed candidate keeps only three of
those values in preserved registers. Later, its explicit copy loop also does
not become retail's `rep movsd` without another source-shape change.

The decisive bounded-topology blocker is logging. Retail calls
`0x0044B810` repeatedly with the log object in `ECX`, the message on the stack,
and caller cleanup (`add esp,4`). An ordinary external `__thiscall` declaration
uses callee cleanup and changes both the instruction stream and register
liveness. That 201-byte logger has many unrelated callers and was outside this
lane, so it was not modified or absorbed into an LTCG experiment.

## Focused logger follow-up

The logger dependency at `0x0044B810` was recovered independently as readable
`TextLog_0044b810::Append`. It is a variadic member compiled in a task-local
native-LTCG context whose synthetic caller fixes the singleton log object in
`ECX` while leaving the format argument on the caller-cleaned stack. The
resulting contribution is exactly 201 bytes with zero differences (SHA-256
`e656c1d4e04a4fe1113db4f817c541683da7b711b7a93fbe82fb20b8fdf2cbbb`).
It reproduces the `0x2004` stack probe, security cookie, IAT critical-section
calls, depth byte, variadic argument address, bounded append loops, and plain
return. The semantic source, reusable layout/context, and proposal are retained
for primary integration.

Compiling D3D initialization and that exact logger as one native-LTCG cluster
fixed the register topology requested by retail. The combined D3D prologue and
first 57 bytes became exact, including preserved `EBP`, `EBX=0`, `ESI` retry
state, and `EDI=0x80000000`. Caching display-mode index `0x00491D62` in a local
then improved the candidate from 1196 bytes / 57-byte prefix to 1191 bytes /
96-byte prefix. Retail remains 1159 bytes.

The final first mismatch is at `+0x60`:

```
candidate: C7 44 24 50 16 00 00 00 68 40 F6 46 00 B9 70 4F ...
retail:    68 40 F6 46 00 B9 70 4F 47 00 C7 44 24 54 16 00 ...
```

Both streams assign back-buffer format `0x16` and call the same exact logger,
but retail begins call setup first and schedules the format store afterward,
using the post-push stack offset. Equivalent scheduling differences recur
around later presentation-parameter stores and account for the remaining
32-byte excess. D3D itself was therefore rejected and remains its exact
assembly source.

The next D3D dependency is no longer the logger ABI. It is an exact VC7.1
source expression topology that interleaves presentation-parameter assignments
with variadic call argument setup (starting with the `0x0046F640` branch), then
rechecks the same scheduling at the vsync and retry logs. Keep the proven logger
layout unchanged while iterating that caller expression shape.

## Presentation scheduling retry

A focused retry kept the exact `TextLog_0044b810::Append` implementation as an
unchanged LTCG dependency and retained the retail long-lived register topology:
`EBX=0`, `EBP=1`, `ESI` as retry state, and `EDI=0x80000000`. Two equivalent
source forms were tested for the first configured-format log: an explicitly
named message local and a force-inlined behaviorally named format-selection
helper. Both generated the same 1191-byte contribution and the same 96-byte
exact prefix.

The unchanged first mismatch remains `+0x60`: VC7.1 emits the stack-local
`pp.format = 0x16` store before `push 0x0046F640`, while retail begins the
variadic call setup and then emits that store at the post-push stack offset.
Because the very first call-site schedule did not move, applying analogous
helpers to the vsync/retry logs could not establish an exact candidate and was
not pursued. All retry candidates and combined-cluster artifacts were removed;
the 1159-byte production region remains assembly.

The next bounded experiment needs a caller representation whose compiler IR
matches the original logger call expression—not another ordering of ordinary
member-call statements. In particular, compare a legacy free-function-style
variadic declaration linked to the exact logger IR, or recover original class
declarations from adjacent TU/type evidence, while preserving the already
proven logger bytes and register allocation.
