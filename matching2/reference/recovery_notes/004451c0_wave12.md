## Levers that turned out to matter (all measured)

1. **Case 9 must be a real body *in the dispatcher's link*, and it is what pins
   the entry pair.**  With DrawStrip as an anchor wanting (entity EDI, manager
   ESI), three cases want the entity in ESI against two that want EAX and the
   pass re-homes the dispatcher's entity in ESI: the prologue becomes
   `push esi; mov esi,eax`, the guard reads `[esi+35C]`, and every case body
   marshals from ESI (`mov edx,esi` in cases 1/3).  With DrawStrip's definition
   the count is 3 ESI / 3 EAX and the pass keeps retail's EAX home.  Caller-side
   pressure does not substitute for this: contexts with two to four call sites
   whose entity argument is a call result left the ESI home in place, exactly as
   wave 10's note found for a different cluster.
2. **A `__fastcall` declaration only works in the batch link.**  In the
   dispatcher's own single-source cluster (wave 9's layout, one synthetic
   caller) the same two declarations make the pass re-home the *dispatcher's*
   entity in EDX - the caller pays one 2-byte move for two saved moves, so the
   entry becomes `mov eax,[edx+35C]` and the region grows to 216 with every case
   body wrong.  In the batch link, where the entry pair is anchored by the
   recovered family, retail's `mov edx,eax; jmp` appears with the entry intact.
3. **The declared parameter order is the caller-side lever for the ESI/EDI
   pair.**  Wave 9 declared 0x00444580/0x00443FB0 `(entity, manager)` and the
   pass emitted `mov esi,ecx; mov edi,eax` - the right homes, the wrong order.
   Declaring them `(manager, entity)` and calling them `(manager, entity)`
   emits retail's `mov esi,eax; mov edi,ecx`: the pass gives the declared first
   parameter the second register of the pair (here EDI) and emits the moves in
   reverse declaration order.
4. **The anchor body decides which register pair the callee gets.**  Measured
   for 0x00443FB0 with the swapped declaration, keyed on the resulting case-6
   marshalling:

   | anchor body | case-6 marshalling |
   |---|---|
   | `entry_free(entity); entry_free(manager); …` | `push ecx; mov esi,eax` (manager on the stack) |
   | `entry_free(entity); entry_free(manager); entry_free(entity); entry_free(manager);` | `mov esi,eax; mov edi,ecx` (that is retail's *case 5*) |
   | loop over the entity, manager only in the return | `push ecx; mov edi,eax` (entity EDI, manager spilled) |
   | loop over the entity, manager dereferenced and passed *inside* the loop | **`mov edi,eax; mov esi,ecx`** (retail's case 6) |

   The same loop shape applied to 0x00444580 breaks the entry pair, so case 5
   uses the four-call body: the two callees need *different* shapes, not one
   general one.
5. **Case 6 is what makes the dispatcher save ESI *and* EDI.**  With only case 5
   writing EDI the pass saves it inline inside that case body
   (`push edi; … pop edi`) and the prologue is one push short (204 bytes);
   with case 6 writing EDI as well the save is hoisted to the prologue and every
   case epilogue becomes retail's `pop edi; pop esi; ret`.
6. **The guard's tail-merge follows from the case sizes.**  Wave 9's duplicated
   rejection block (first difference at 0x004451CA, +2 bytes) disappears once
   the ten bodies are retail-sized; the three early returns merge into retail's
   single `or eax,-1; ret` at 0x004451DC, and the byte at 0x004451CA is retail's
   `74 11`.
7. **The head of the file is untouched from wave 9**: the `mov edx,[eax+35C]`
   load, the two flag tests, the `push ebx`/`mov bl,[eax+2FF]`/`pop ebx` guard
   pair, `shr edx,16h`, `and edx,0Fh`, `cmp edx,9`, `push esi; push edi`, the
   `ja` and the ten-entry table with its three-byte `8d 49 00` pad.

## What this unblocks

`release_flagged_entities_00409230_cluster.md` and the wave-9 note both asked for
this region as a *definition* with retail's convention so that `0x00409230`
(50 bytes) and its sibling `0x004091C0` can compile byte-exact; both call the
dispatcher as `mov ecx,[data_00491c10]; lea eax,[entity+0x10]; call 0x004451C0`.
The definition now exists in the link, with the entry pair, the plain `RET` and
the exact ten-entry table, so those two regions should be re-probed against this
cluster rather than against an absolute binding.

`RenderBucketLeaf` landed `0x00448980` EXACT in its own cluster whose anchor for
`0x004451C0` is a 220-byte compiled body - 4 bytes off retail precisely because
the dispatcher's convention was not nameable there.  With this landing the region
has a definition in the batch link, so that anchor can be replaced by a
definition (the batch cluster already binds `_asm_FUN_004451c0_004451c0` for its
own `0x00448980` anchor).

`0x004436C0`, `0x00443910`, `0x00443FB0` and `0x00444580` remain assembly.  Their
entry conventions are now *measured*: `(manager ECX, entity EDX)`,
`(manager ECX, entity EDX)`, `(entity EDI, manager ESI)` and
`(entity ESI, manager EDI)`.  Recovering any of them as C++ makes the tail-jump
or the two-move marshalling a definition-to-definition call.

## Dead ends (measured, so they are not retried)

* Anchoring all ten cases and keeping the dispatcher in its own single-source
  cluster: 216 bytes, 5/10 case bodies exact, 147 differing bytes - wave 9's
  result, reproduced exactly from the wave-9 note.
* `__fastcall` for cases 1/3 in that cluster: the entry pair flips to
  `(EDX entity, ECX manager)` and the region goes to 216 bytes with no case
  exact.
* `__fastcall` plus the decl-swap for case 5 in that cluster: 216 bytes, cases
  0/1/2/3/4/6/7/8/9 exact, case 5 emitted `mov edi,ecx` only (the entity stayed
  in EAX) - still one case short.
* Applying the case-6 loop shape to 0x00444580 as well: the entry pair flips,
  every case wrong.
* `extern "C" int __cdecl` + inline `__asm` marshalling, and calling through a
  function pointer cast, were not attempted: both would replace a direct REL32
  call with an indirect one, and the region's last instruction before the table
  is a relocated direct call in every case.
* Caller-shaped contexts (2-4 sites, entity from a call result, a local live
  across the call) are inert for the entry pair, matching wave 10's finding.

## For whoever picks this up

The batch cluster is the right home for the region while nine of its ten callees
are assembly: only a link that already contains the render family earns
`DrawStrip`'s (ECX, EAX) entry, and that entry is what keeps the dispatcher's own
entity in EAX.  If those four helpers are recovered later, replace their anchors
and the `__fastcall` declarations with definitions and re-probe: the region's
bytes should not move, but the cluster's whole-program analysis is what decides
that, so measure rather than assume.
