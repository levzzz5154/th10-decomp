## 1. The wall wave 10 left, and what actually moved it

Wave 10 settled the body and every internal register; the model `g1` matched 173
of 203 bytes under a single 3-byte shift and differed only in the entry head plus
the artefacts that head shifts. Wave 10's conclusion was that the *entry triple*
(object in EAX, resource in ECX, index in EBX) is a whole-program agreement the
pass re-decides from the callee's own IR, and that no lever it measured moved it.

It did not move this time either, for the two levers the brief named:

| experiment | emitted | entry |
|---|---:|---|
| wave-10 `g1` body (volatile flags clear) as the callee of the landed `0x448D50` cluster | 198 | EAX / **ESI** / EBX |
| same body plus a hoisted `scripts` local (4 live values) in that same link | 199 | EAX / **ESI** / EBX |
| both, in a standalone cluster | identical bytes to the above | — |

So the caller side and the composition are **inert**, confirming wave 10: the
landed `0x448D50` body plus its three anchors re-shape themselves around whatever
the callee wants (the modelled caller emits 99 bytes against the wrong callee and
95 against the right one) and never drag the callee to retail's triple.

What moved it was one statement in the body. Wave 10's rule
("the flags clear must be a `volatile` read-modify-write") reproduces retail's
*load / and / store* shape but forces the pass to coalesce the resource's
incoming register with its home (ESI). Replacing the `volatile uint32_t*` with a
**plain `uint32_t*`** keeps the same load/and/store shape *and* keeps retail's
entry: the resource stays in ECX at entry and the prologue emits retail's own
`push esi / mov esi,ecx`.

Bisection, all measured in the throwaway copy against the retail window:

| body shape (final clear) | emitted | differing | entry head |
|---|---:|---:|---|
| `volatile uint32_t* p = &flags; *p &= ~1u;` (wave-10 `g1`) | 198 | 195 | `55 57 8b f8` (no `push esi`) |
| **`uint32_t* p = &flags; *p &= ~1u;`** | **203** | **0** | **`55 56 8b f1 57 8b f8`** |
| `flags &= ~1u;` | 199 | 197 | `55 57 8b f8`, folds to `and ecx,~1` + in-place store |
| `uint32_t f = flags; flags = f & ~1u;` (same, written out) | 199 | 197 | as above, MSVC re-folds it |
| `flags = (flags & ~1u);` one statement | 199 | 197 | as above |

The last three all still lose retail's `mov esi,[edi+0x35C] / and esi,~1 /
mov [edi+0x35C],esi` scheduling, and the first three lose retail's entry; only
the plain pointer does both.

The second load-bearing detail is **parameter order**. The pass hands the first
parameter ECX and the second EAX, so the resource must be declared first:

| declaration order | emitted | differing |
|---|---:|---:|
| `(object, resource, index)` | 203 | 10 — prologue `push ebp / push esi / mov esi,eax / … / mov edi,ecx` |
| **(resource, object, index)** | **203** | **0** |

Everything else from the wave-10 note still holds: the first mask is a named
local stored later (`mask = flags & 0xFFFFF9FFu; … flags = mask;`), the call to
`0x0043EE30` is `__stdcall` (retail is `push edi / call` with no cleanup), and
the dead leading slot of `Entity_Init` is given the already-live script pointer
so no `xor ecx,ecx` is materialised.

Two other late experiments, for the record: giving the flags-word *address*
(`res + 0x11C`, `obj + 0x35C`) a live range across the call changes nothing (the
allocator folds it), and hoisting the script table into a local does move the
entry to ECX/EAX/EBX — but by taking EBP for the table pointer, which costs
retail's zero register and 4 bytes of body (207/199 emitted), so it is the wrong
lever even though it reaches the right triple.

// `resource` into `object`.
//
// The body zeroes the object and returns when the slot is empty or the resource
// is still loading; otherwise it initialises the entity, records the script
// resource, the resource's id and the index, clears two bits of the +0x35C flag
// word, installs the script base and cursor, re-seeds the frame state (frame 0,
// elapsed 0, previous frame -1, and the 0xFFF0BDC1 / 0x476F78 pair when the
// +0x6C flag word has not been primed yet), clears bit 0 of +0x35C through a
// pointer and finally runs the script once (0x0043EE30) and advances the
// manager's script tick counter.
//
// Retail's entry convention is object in EAX, resource in ECX and index in EBX:
// the resource is copied to ESI and keeps that home for the rest of the body,
// the object is copied to EDI, the index stays in EBX and the shared zero lives
// in EBP.  That is a whole-program decision made from this body's own IR - the
// declaration names no register, and only the *parameter order* matters: the
// pass hands the first parameter ECX and the second EAX, so the resource must
// be declared first.
//
// Two statement shapes are load-bearing (both measured against the image):
//
//  * The first flag mask is a named local stored afterwards
//    (`mask = flags & 0xFFFFF9FF; ... flags = mask;`).  Written as an in-place
//    `&=`, MSVC folds it into `andl $imm,mem` and retail's hoisted load /
//    deferred store is lost.
//  * The final clear is a read-modify-write through a plain (non-`volatile`)
//    `uint32_t*`.  The direct `flags &= ~1u;` folds into the wrong in-place
//    `andl`, while a `volatile` pointer forces the coalesced entry
//    (resource in ESI) and loses retail's `push esi; mov esi,ecx`.  The plain
//    pointer keeps both retail's load/and/store shape and retail's entry.
