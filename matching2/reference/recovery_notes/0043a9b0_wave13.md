# 0x0043A9B0 — 116/116 bytes, 18 bytes out (wave 13)

2026-09-19, agent `FrameAdvanceShape`.  The track-reload leaf of the MIDI sound
manager, chosen as the smallest still-assembly region whose entry is the wave-12
shape (`push ebp; mov ebp,dword ptr [esp+8]`).  The model reaches retail's
*entry convention* and both of its privately-conventioned calls, but the
whole-program pass keeps `this` in **EBX** where retail keeps it in **EDI**, and
that one register choice is the whole of the remaining 18 bytes.

**Not landed.  Nothing was registered**: the emitted extent equals the declared
extent (116/116) yet 18 bytes differ, and a non-exact layout must never be
registered.  The maintained tree was never edited; every build ran against
`/tmp/FrameAdvanceShape/msvc`.

## The region

| field | value |
| --- | --- |
| region | `0x0043A9B0`, 116 bytes, `src/unidentified/FUN_0043a9b0_0043a9b0.cpp` |
| shape | manager in EAX, track index in ESI (never saved: it is an argument register), name as the only stack argument in EBP, `RET 4` |
| callees | `0x0043AE20` MIDI playback stop (receiver in EDI), `0x00452422` `free`, `0x0044B360` archive loader (name in EAX, `RET 8`), `0x0044B810` text-log report (object in ECX, caller-cleaned stack) |

Semantics: if the track being reloaded is the one playing, stop playback; release
the old backing store and republish the slot; load the new store through the
archive loader; report a failed load through the text log at `0x474F70` and
return -1.

## Where it was built

The region was modelled inside the **existing `load_archive_file` cluster**,
whose link already co-compiles `0x0044B360`, so the loader's private convention
(lever 5: a body whose own call graph is in the link decides the caller's
marshalling) is earned rather than declared:

* `additional_sources` gains `src/unidentified/FUN_0043a9b0_0043a9b0.cpp`;
* `functions` gains the region at `0x0043A9B0`/116 in section `.text$03zn9b0track`;
* the gap `.text$03zlayout` (`0x0043A28F` + 18241) splits into
  `.text$03zlayout` 0x0043A28F/1825, the function, `.text$03zolayout`
  0x0043AA24/1020, the MidiStop anchor, `.text$03zqlayout`;
* `absolute_symbols` gains `?Append@TextLog_0044b810@@QAAPADPADZZ` … no: the log
  entry is compiled as an anchor (below), so the binding is *not* added;
* the driver's synthetic caller gains one call line.

Adding the same source as an extra *function* of the cluster does not disturb
the six landed regions: every build of this shape re-emitted `LoadAsset` 106,
`ScriptFileLoader_Load` 95, `ComputeExecutableChecksum` 207, `MapResource_LoadMap`
228, `Archive_LoadFile` 360 and `ParameterLoader_Load` 229 **byte-identical to
retail** (checked against the oracle, not by size alone).

## What the recipe had to add for this region

### The log entry needs its body in the link (measured)

`?Append@TextLog_0044b810@@QAAPADPADZZ` is **variadic**, so its mangled ABI is
cdecl with `this` on the stack: declared externally, MSVC emits

```
push ebp        ; name
push 46F908h    ; format
push 474F70h    ; this
call 0044B810
add  esp,0Ch
```

retail emits `push ebp; push 46F908h; mov ecx,474F70h; call; add esp,8`.  A
two-argument *fixed* member declaration gets the ECX part but a callee-cleaned
`RET 8`, i.e. no `add esp` at all — neither declaration reaches retail.  Only
co-compiling the entry's own body makes the pass choose "object in ECX,
arguments on the caller-cleaned stack" (the same decision the landed
`bullet_manager_load_scripts_0040ae70` cluster relies on).  Because
`src/platform/text_log.cpp` already belongs to that cluster and a source may
belong to only one cluster, the body is supplied as an **ABI anchor**:
`src/unidentified/log_append_anchor_0043a9b0.cpp` compiles the log entry's own
shape (8 KiB staging buffer, critical section, `vsprintf`, ring append) into
`.text$09append`, the layout places it at `0x0044B810`, and it emits exactly the
retail size, 201 bytes.  It is never exported.

With that anchor in the link the failure path becomes, byte for byte,

```
push ebp
push 46F908h
mov  ecx,474F70h
call 0044B810
add  esp,8
```

and the whole function is 116 bytes — retail's extent.  A *minimal* anchor body
(a loop that consumes the varargs but calls nothing) is not enough: the pass then
keeps the cdecl form, and a 3-callee-saved-register anchor body does not change
that either.  The deciding property is that the log object stays live across the
anchor's own calls.

### The MidiStop anchor

`0x0043AE20`'s receiver arrives in EDI; retail's call site is a bare
`call 0043ae20` (no setup), so the anchor's receiver register *is* the caller's
home for `this`.  It is compiled as a second ABI anchor in
`.text$03zpanchor`; a body that keeps a cursor, a counter and a released count
live across the `free` call (55 bytes) earns EBX+EBP+ESI+EDI in this link, and
the bare `call` at `0x43a9bd` is reproduced.

## The 18-byte delta

| retail | model |
| --- | --- |
| `55` `push ebp` | `53` `push ebx` |
| `8B 6C 24 08` `mov ebp,[esp+8]` | `89 C3` `mov ebx,eax` |
| `57` `push edi` | `39 73 10` `cmp [ebx+0x10],esi` |
| `8B F8` `mov edi,eax` | `55` `push ebp` |
| `39 77 10` `cmp [edi+0x10],esi` | `8B 6C 24 0C` `mov ebp,[esp+0xc]` |
| 4 × `…84 B7 98…` (`[edi+esi*4+0x98]`) | 4 × `…84 B3 98…` (`[ebx+esi*4+0x98]`) |
| `5F` `pop edi` … `5D` `pop ebp` | `5D` `pop ebp` … `5B` `pop ebx` |

Differing offsets: `0x0, 0x2-0xa, 0x14, 0x28, 0x39, 0x4b, 0x65, 0x69, 0x6d,
0x70` — 18 bytes.  Everything else, including the two `mov dword ptr
[reg+esi*4+98h],0` stores, the loader call (`push 0; push 0; mov eax,ebp;
call`), and the log call, is byte-identical.

So the *entry convention* (EAX / ESI / `[ESP+4]` / `RET 4`) **is** retail's; only
the callee-saved home for `this`, and the prologue/epilogue shape that follows
from it, differ.  `ESI` is unsaved in both, i.e. the pass made the same
register-argument agreement as retail, and both save the same *number* of
registers (2), so the extent is identical.

The push order is ascending by register number in both builds
(retail `EBP(5), EDI(7)`; model `EBX(3), EBP(5)`), so flipping the home to EDI
should also restore the prologue order as a consequence, not as a second fix.

## Shapes tried against the home register

All of these re-emitted 116 bytes with the same 18-byte delta, except where
noted:

* **body** — base; `char*& slot = manager->tracks[index]` (lever 8/6 shape);
  `char* old = tracks[index]` hoisted; `tracks[index] != 0` test; the `== 0`
  comparison variant (127 bytes, rejected); two zero stores vs one.
* **model form** — member `LoadTrack(int,const char*)` and free
  `LoadTrack(SoundManager*,int,const char*)` are indistinguishable to the pass.
* **synthetic caller** (16 shapes) — array of pointers; array of objects by
  value; local `&managers[i]`; two call sites; single call outside a loop
  (127 bytes); `total += LoadTrack(...)`; descending index; `while` loop; loop
  containing only `LoadTrack`; separate loops per callee; archive calls in a
  `noinline` helper; a struct-of-arrays argument; global arrays;
  `LoadTrack` first vs last in the loop; a second `MidiStop` call site in the
  driver.  The caller shape is measurably *not* what decides the home: with the
  log anchor present, every one of these produced the identical 116-byte body.
  Without a loop at all the body grows to 127 bytes, so the loop *is* load
  bearing for the entry convention, just not for the home.
* **module arrangement** — with the modelled source included by the driver's own
  translation unit (`asset_buffer.cpp` demoted to an additional source, the
  arrangement the landed `win32_timer` cluster uses), the six landed regions stay
  exact but the function degrades to 127 bytes: the pass promotes `name` to EDI
  as a register argument and tail-duplicates the loader call (no stack argument,
  bare `RET`).  Launched from the driver's module it loses the `RET 4` shape, so
  that arrangement is strictly worse.
* **anchors** — a MidiStop body needing three other callee-saved registers
  (55 bytes) does not force its receiver out of EBX; the receiver simply
  follows the caller's home.  A second MidiStop call site does not change it.
* **fresh standalone cluster** — a new layout (`track_reload_0043a9b0.json`)
  hosting only this region with ABI anchors for *both* privately-conventioned
  callees (loader at `0x0044B360`, log at `0x0044B810`, MidiStop at
  `0x0043AE20`) builds as far as a 108-byte loader anchor; the context address
  then needs one more alignment iteration and the run was cut short by budget.
  This is the one arrangement left that has not been measured to completion.

## What this unblocks / what it costs

* `0x0043A9B0` is **not** recovered; the maintained `src/unidentified/
  FUN_0043a9b0_0043a9b0.cpp` assembly stands.
* It is a complete worked example of the log-entry problem: any region calling
  `0x0044B810` (there are ~40 call sites in the image) cannot express retail's
  `mov ecx,474F70h; add esp,8` with a declaration and needs the entry's body in
  its link — either through the `bullet_manager_load_scripts_0040ae70` cluster
  or through an anchor like the one above, which emits retail's own 201 bytes.
* `0x0044B360`'s private convention (`EAX name`, `RET 8`) is already reachable
  from the `load_archive_file` cluster and is reproduced here.
