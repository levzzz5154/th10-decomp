# 0x00443FB0 (643 bytes) and 0x00444580 (60 bytes) — wave 13

2026-09-19, worker `DispatchHelperB`. Work was done in `/tmp/DispatchHelperB/msvc`
(`cp -a matching2/msvc`); the maintained tree is untouched by these models, and
the maintained `regions.json`, layouts and sources were never hand-edited.

## The answer in one paragraph

**`0x00444580` is recovered EXACT (60/60)** and lands as a selected function of
the render-batch cluster, with its two callees earned by compiled ABI anchors.
**`0x00443FB0` is NOT exact**: it emits **654 bytes against retail's 643**, first
difference at `0x00443FB2` (the stack frame is `sub esp,0x1c` where retail's is
`sub esp,0x20`).  Everything structural about it is now retail's - the entry
convention (`entity in EDI, manager in ESI`), the `mov eax,edi; call` marshalling
of the billboard projection, the two-times-faded colour, the `__ftol2` channel
arithmetic, the four vertex colour stores and the mode-2 submission - but the
three-axis position/distance block is scheduled and spilled differently, which
is what the 11 bytes are.  **The dispatcher does change, by two bytes**, when the
real bodies replace its case-5/6 anchors: its size stays retail's 216 and every
other byte is retail's, but case 6's argument setup emits `mov esi,ecx; mov
edi,eax` where retail has `mov edi,eax; mov esi,ecx` (the same two registers,
the same target, the two moves swapped).

| region | size | state | emitted |
|---|---|---|---|
| 0x00444580 | 60 | **EXACT 60/60** | `_EntityDraw_00444580@8` |
| 0x00443FB0 | 643 | not exact: **654 emitted**, first difference `0x443FB2` | `_EntityDraw_00443fb0@8` |
| 0x004451C0 (dispatcher) | 216 | 216 emitted, **2 bytes differ** (offsets 96/98) | `_asm_FUN_004451c0_004451c0` |

No region is unblocked by this attempt: neither helper can land until
`0x00443FB0` is 643 bytes, and the anchors cannot be dropped before the
definitions that replace them land.

## What had to be true before either body could be written

1. **A callee whose convention no declaration names needs a compiled body in the
   same link, and that body must sit at the callee's retail address.**  The
   cluster's native link bakes call displacements into the region's bytes
   (`original_relocations` is empty for the dispatcher's 216 bytes), so an
   anchor parked in a spare gap would bake a wrong displacement.  `0x00443B60`
   (`BuildProjectedQuad`, source in EAX, no arguments) and `0x00444240`
   (`ProjectQuad`, source in EAX, manager on the stack with the callee popping
   it) therefore each get an anchor at their retail address.  A foreign cluster's
   source cannot be co-compiled (clusters demand distinct maintained sources),
   so the anchors are hand-written bodies in a new driver-side file.
2. **The anchor body's statement order is the convention it earns.**  For
   `0x00444240` the body `entry_free(manager); entry_free(this);` earned
   *manager in EAX, `this` on the stack* (`push eax; call; mov ecx,[esp+8];
   push ecx; call; ret 4`) and the caller marshalled `push esi; mov eax,edi`.
   Swapping the two statements to `entry_free(this); entry_free(manager);` earned
   retail's *`this` in EAX, manager on the stack* and the caller then emitted
   retail's `push edi; mov eax,esi`.  That single swap is what makes
   `0x00444580` exact.
3. **The declared parameter order of the helper is a caller-side lever that has
   to be flipped for `0x00443FB0`.**  Wave 12's anchors declared the ESI/EDI pair
   `(manager, entity)`.  With that order and the *real* body the pass assigned
   `entity ESI, manager EDI`, which is not retail's (`entity EDI, manager ESI`),
   and the dispatcher then collapsed to 212 bytes with re-homed code.  Declaring
   the helper - **and its two dispatcher lines** - as `(entity, manager)` gives
   retail's homes and leaves the dispatcher at retail's 216 bytes.

## The dispatcher's state, measured

The dispatcher's anchors for cases 5 and 6 were dropped from the layout and
their bodies deleted from the driver, so `0x00444580` and `0x00443FB0` are now
*definitions* in the dispatcher's link.  Measured on the same cluster build:

* emitted extent **216 bytes**, at its retail address, and the entry pair stays
  `(ECX manager, EAX entity)` - the guard, the `cmp edx,9 / ja / jmp [edx*4+…]`
  sequence, the jump table's `8d 49 00` pad and every case-5 body byte are
  retail's;
* **two bytes differ, at offsets 96 and 98** - case 6's argument setup.  Retail:
  `8b f8 8b f1` (`mov edi,eax; mov esi,ecx`); this link: `8b f1 8b f8` (`mov
  esi,ecx; mov edi,eax`).  The registers and the call target (`0x00443FB0`) are
  correct; only the order of the two moves is swapped;
* with the helper declared `(manager, entity)` instead the dispatcher also emits
  216 bytes but re-homes the *callee's* entry to `(entity ESI, manager EDI)`,
  which is worse, so `(entity, manager)` is the declaration to keep.

So the answer to the question asked: **yes, the dispatcher's bytes change when
the real bodies join** - by two bytes, in case 6's move order.  Everything else
in its 216 bytes is unaffected.

A plain `/O2` translation unit reproduces the x87 shape of every one of these in
about 0.25 s, which is how the operand-order rule was found: MSVC canonicalises
a linear three-term sum to `fld last; fadd middle; fadd first`, so only an
explicitly parenthesised pair (`(position + base) + render_offset`) emits
retail's `fld position; fadd base; fadd render_offset`.

## Levers that turned out to matter

1. **An anchor must sit at the callee's retail address**, because the cluster
   link bakes the call displacement into the caller's bytes (the extracted
   object has no relocation for it).  Parking an anchor in a spare gap to avoid
   splitting gaps does not work.
2. **For a `this`+stack-argument callee, the anchor body's statement order picks
   which parameter gets the register**: `entry_free(this)` first earns retail's
   `this in EAX, manager on the stack`; the reverse earns manager-in-EAX.
3. **The declared order of the modelled helper steers the caller**; for
   `0x00443FB0` retail's pair needs `(entity, manager)` in the model *and* in the
   dispatcher, while for `0x00444580` retail's pair needs `(manager, entity)`.
   The two helpers therefore declare their parameters in opposite orders.
4. **Passing the delta vector by value to a `__forceinline` helper is what
   creates retail's stack frame.**  With inline `sqrt(dx*dx+dy*dy+dz*dz)` on
   plain locals the FP optimiser fuses everything into x87 registers, the frame
   collapses to `push ecx` and the region comes out 43-50 bytes short.
5. `float span = data_00491e78 - data_00491e7c;` hoisted into a local makes the
   numerator survive to the division the way retail's `(data_00491e78 -
   data_00491e7c) / (data_00491e78 - distance)` does; inlining it re-computes
   the subtraction at the division.
6. A model that falls off the end of a non-`void` function is rejected
   (`error C4716`); `0x00444580` is `void` because retail's body never writes EAX
   after its last call, while `0x00443FB0` returns the submission's result.
7. `fld ... / fsub` and the integer guard interleave in retail because MSVC
   schedules the loads into the `test ah,ah / jns` shadow; the source does not
   have to place the subtraction there.

## What is still missing

The 11 bytes and the whole remaining 578-byte delta are the position/distance
block's schedule and spill slots.  Retail batches the three `position + base`
pairs before consuming them (`fstp [esp+0x20]`, `fxch st(1)`, then the three
`render_offset` additions and subtractions), and it computes the colour fade's
saturation with `jb` over `mov bl,al` where this model emits an extra
`jmp`/`movzx` pair per channel.  The next attempt should either find the source
shape that makes MSVC batch the pairs (the model's values are live across the
same `je` the retail slots straddle) or accept retail's slot usage explicitly.
