## Exact gates

Focused production probes were rerun after restoration for all eight sources;
each returned `EXACT` with exit code 0. This confirms restoration and preserves
the existing naked bodies as the production implementation. No proposal JSON
was retained because no semantic candidate passed both the current extent and
byte gate.

## Native LTCG attempt

A task-local cluster was compiled with the configured MSVC 13.10.6030 native
`/GL /LTCG` profile. It included all eight candidates plus a synthetic caller,
with fixed zero-filled layout gaps and absolute bindings for the malloc/free,
vector-destroy, `stricmp`, file-pointer, `ReadFile`, and archive-offset
dependencies. The compiler rejected `__thiscall` function-pointer typedefs;
the probe was adjusted to explicit object-parameter `__stdcall` adapters so
the native build could proceed. This adapter change is itself evidence that
the retail member-call ABI still needs a dedicated model.

The first linked map was rejected by the shared map reader because LINK emits
an empty `.text` contribution (`0001:00000000 00000000H .text CODE`) that the
current parser treats as invalid. The executable and map were nevertheless
manually checked, and a measured-extent rerun placed every candidate at its

## Next dependency

The next productive experiment should model the shared custom ABI as a native
cluster without substituting calling conventions: the codec key enters in AL
while five values arrive on the stack; archive read invokes member vtable
slots with the retail object register; cursor seek/read use ESI/EAX/EDX/AL;
and close depends on the compiler's vector-destructor callback shape. The
legacy semantic functions also need boundary reconciliation against the
current live regions before any proposal can state exact extents. A future
attempt should first isolate one ABI bridge (preferably `FindEntry` plus its
caller) and retain the linker/map parser issue as tooling evidence rather than
changing shared tooling in this lane.

## Focused FindEntry follow-up

Retail xrefs identify the only direct `FindEntry` call at `0x00434DE9`, inside
`DatArchive_Read` at `0x00434DD0`; the xrefs at `0x00435841` and `0x0044B410`
are callers of `Read`, not of `FindEntry`. The follow-up therefore owned only
`src/archive/dat_archive_find_entry_00434f30.cpp` and that direct caller
`src/archive/dat_archive_read_00434dd0.cpp`.

The caller-inclusive native-LTCG probe used C++ internal register selection for
the archive/name path and inline adapters for the retail ECX object plus stack
member calls and the codec key in AL. It placed `FindEntry` at `0x00434F30`
with the correct 53-byte extent, but the `Read` candidate was 331 bytes rather
than 281. Its first diagnostic mismatch was `+0x02`: candidate bytes
`55 8B EC 83 EC 18`, retail bytes `55 8B 6C 24 08 8B 45 0C`.

The `FindEntry` source was then independently probed in a one-function native
cluster. A nested source shape preserved the entry-first test, and native LTCG
selected the retail convention: archive/index in EAX, name in EBX, result in
EAX, plain RET. The final layout placed the 53-byte contribution at the exact
VA and emitted a 74-byte synthetic context at `0x00435000`. The result is
independently exact:
