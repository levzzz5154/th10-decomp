# ABI audit: `FUN_00412f70` (`0x00412F70`)

## Ghidra scope and extent

Audited the open Ghidra program `th10.exe` (x86:LE:32, image base `0x00400000`).
Reading memory at `0x00412F70` gives
`8b4c24048b5424088908895004c20800`. Forced disassembly covers exactly these
five instructions and 16 bytes, through the terminal `RET 0x8` at `0x00412F7D`:

```text
00412F70  MOV ECX, dword ptr [ESP + 0x4]  ; 8b 4c 24 04
00412F74  MOV EDX, dword ptr [ESP + 0x8]  ; 8b 54 24 08
00412F78  MOV dword ptr [EAX], ECX        ; 89 08
00412F7A  MOV dword ptr [EAX + 0x4], EDX  ; 89 50 04
00412F7D  RET 0x8                         ; c2 08 00
```

This matches the owned 16-byte manifest region ending at `0x00412F7F`. The
next byte is `0x00412F80`; it is outside this routine. The augmented listing
also shows the `RET 0x8` at `0x00412F7D`, followed by separate bytes at
`0x00412F80`.

## Register and stack contract visible in the body

- The first and second DWORD stack arguments are read from `[ESP+4]` and
  `[ESP+8]`, copied to `ECX` and `EDX`, then written to `[EAX]` and `[EAX+4]`.
- `EAX` is read as a destination pointer and is not modified by any instruction
  in the body. This is consistent with an incoming result/destination address,
  though the current Ghidra program has no caller evidence to establish its
  higher-level meaning.
- `RET 8` removes the two stack arguments. There are no calls or other control
  transfers in the body, so it has no direct callees.

## Callers, xrefs, and decompilation status

Live Ghidra queries for `get_function_by_address`, `get_function_callers`,
`get_function_callees`, `get_function_xrefs`, `get_xrefs_to`, and
`get_xrefs_from` at `0x00412F70` report no function or references. The
decompiler likewise reports that no function is defined at this address.
Therefore no Ghidra caller can confirm how `EAX` is initialized or consumed;
the register/stack contract above is limited to direct instruction evidence.

## Disposition

Keep the naked assembly body. A normal MSVC x86 C++ prototype can express the
two stack arguments and their cleanup, or a conventional register argument,
but not this independent incoming `EAX` destination together with two stack
arguments and the observed callee cleanup. The previous readable factory and
constructor-context experiments recorded in the source header did not match
the retail ABI. The assembly remains the faithful implementation until a
verified compiler context can emit this entry contract.

Integration aliases remain unchanged:

```text
_asm_FUN_00412f70_00412f70   -> 0x00412F70
_asm_FUN_00412f70_00412f70@8 -> 0x00412F70
@asm_FUN_00412f70_00412f70@8 -> 0x00412F70
```
