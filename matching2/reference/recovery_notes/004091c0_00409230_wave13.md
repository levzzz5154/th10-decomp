## The answer in one paragraph

Wave 9 and the `release_flagged_entities_00409230_cluster.md` note proved
`0x00409230`'s model byte-exact against a *stand-in* callee at the dispatcher's
address and were explicit that the real thing needed `0x004451C0` to be a
definition in the same `/LTCG` link, because its entry pair (ECX manager, EAX VM)
is a whole-program choice no MSVC declaration names.  That definition now exists:
the wave-12 landing made `AnmVmDrawDispatch` a function of the batch cluster.  So
both regions simply join that cluster.  `0x00409230` is a scheduler callback (its
address escapes at `0x004089EA`), so it is declared a member, added to the
layout's `roots` and keeps its public ECX/ESI receiver; with the dispatcher's body
in the link its two `lea eax,[esi+0x10]` / `lea eax,[esi+0x3BC]` and both call
displacements come out retail's.  `0x004091C0` is entered with the state in
**EBX** - the private receiver its only caller `0x00409270`
(`push ebx; mov ebx,ecx; call; pop ebx; ret`) supplies - so it is deliberately
*not* rooted (that would pin the declared `__thiscall` and grow it to 96 bytes,
see below); the synthetic batch context instead names one call to it, which is
enough for the pass to pick retail's EBX receiver, and both rotated loops
(including the first one's 16-byte alignment `jmp` over the `lea esp,[esp]`+`nop`
pad) fall out of the two `for` loops unchanged.

## What this unblocks

**`0x00409270` (10 bytes, `asm_RunArrayReleaseCallback_ScoreRuntimeState_00409270`)**
is one build away and was *measured* exact while taking the sibling's receiver
decision apart: with `0x004091C0` landed, a member

```cpp
#pragma code_seg(".text$001callback")
int ScoreRuntimeState_004091c0::RunArrayReleaseCallback() {
    return ReleaseFlaggedEntityArrays();      // 0x004091C0
}
#pragma code_seg()
```

in the same source, added to this layout's `functions` and to `roots`, compiles to
**10/10 bytes EXACT** (`53 8b d9 e8 .. 5b c3`, retail's `push ebx; mov ebx,ecx;
call; pop ebx; ret`) *and* leaves `0x004091C0` at 95 EXACT - the pair's private
convention reproduces from the caller side alone.  Landing it means giving that
member a source the `0x00409270` record can own (its own file, with the class
declaration shared, or the callee's file with the record's `source` moved) and
rooting it.  It is out of this wave's scope, which is why the two landed regions
use the synthetic context call instead.

`0x00409190` (46 bytes, the pass-generated receiver clone in
`src/unidentified/unassigned_00409190.cpp`) is *not* unblocked: nothing in the
image references it, so a semantic model has no root and would be dropped by
`/OPT:REF`, and rooting it would pin the public receiver - which is precisely the
register a *clone* does not use.

## Dead ends and negative controls (all measured)

* **Rooting `0x004091C0`** (`roots` = its symbol, nothing calling it): the pass
  pins the declared `__thiscall`, emits a `push ebx; mov ebx,ecx` prologue, 96
  bytes, and loses the 16-byte loop alignment -
  `53 8b d9 f6 83 8c 37 00 00 01 74 4d 56 57 8d b3 78 07 00 00 bf 08 00 00 00
  8d a4 24 00 00 00 00 8b 0d ...` against retail's 95.  A root is the caller-side
  device only for a function whose address escapes.
* **A caller *anchor* at `0x00409270`** (a compiled body in the same link) cannot
  replace the context call: anchors are kept by being referenced, `/INCLUDE` is
  passed only for gaps and `roots`, and `roots` accepts selected functions only -
  so the anchor would need the same driver reference anyway.  The rooted semantic
  member above is the cleaner form of the same device.
* **The dispatcher as an opaque `relative_code` binding** is wave 9's measured
  2-byte `lea edx` failure; nothing in this landing changes a binding, and the
  definition is what the two call sites use.
