## What the region is

GameStateInit stores this address as the `on_tick` routine of one of the twenty
scheduler records it builds — callback `0x448740` with priority `0x24` and the
manager in the record's `context` — and `include/th10/game/scheduler.hpp`
documents the convention: *"Callback context is passed in ECX by the original
scheduler"* (`typedef int (__fastcall *TaskRoutine)(void*)`). So the body enters
with the manager in ECX.

It clears the two shake offsets at `0x00491E64`/`0x00491E68` (the pair the camera
setup copies into the view's offset block at `[view+0x2B34]`/`[view+0x2B38]`, and
the pair the shake task `0x0043C710` writes from its sine terms), clears the
manager's own stored sprite origin `origin_x`/`origin_y` at `+0x5C`/`+0x60` — the
pair the quad pipelines add to every sprite corner — and then walks render-slot
14's entity list through `0x00448980`, returning that call's result. The slot
family is `0x4485F0..0x448810`: slot 0 (`xor eax,eax`) through slot 17, each
registered as its own scheduler task.

## The two load-bearing shapes

Both measured against retail's 48 bytes in the throwaway copy:

| shape | emitted | differing |
| --- | ---: | ---: |
| shake pair written directly through the two globals (`data = 0.0f`) | 48 | 29 |
| the same with the manager pointer held in a local | 48 | 29 |
| origin fields first, shake pair after | 40 | 37 |
| shake pair written as ints (`*(int*)&data = 0`) | 40 | 35 |
| literal absolute addresses for the pair (`*(float*)0x491E64 = 0.0f`) | 40 | 35 |
| chained `data_00491e64 = data_00491e68 = 0.0f` | 48 | 29 |
| the zero kept in a `float` local (frozen in an x87 register) | 48 | 29 |
| **shake pair written through a pointer to the record** | **48** | **0** |

1. **The pair goes through a pointer to its record.** Writing the two fields
   directly through the global emits the same *instruction multiset* but the pass
   sinks both stores past the argument setup, so they land immediately before the
   call: 29 bytes differ (the whole store order). With
   `ShakeOffset* shake = &data_00491e64; shake->x = 0.0f; shake->y = 0.0f;` the
   stores stay where retail has them. The split between the compiler's two store
   forms is retail's own and falls out of the same statement: the two absolute
   stores use the immediate form `C7 05 <address> 00 00 00 00` while the two
   `[eax+0x5C]`/`[eax+0x60]` stores use the shared zero register that `xor
   edx,edx` materialises — exactly as the sibling reset task at `0x004200D0`
   shows the same idiom.

2. **0x00448980 must be entered with the manager in EDI and the slot index in
   EAX.** No declaration names either register (`__cdecl`, `__fastcall`,
   `__thiscall` and argument-free spellings all put the manager somewhere else),
   so its body is compiled as **an ABI anchor** — a C++ body selected into the
   native `/LTCG` link, placed at the retail address by the gaps, validated as a
   complete contribution, and never exported: `masked_bytes 0`,
   `instruction_bytes_changed 0`. Only then does the pass choose retail's split,
   and the caller reproduces retail's `push edi` / `mov edi,ecx` / `pop edi`
   around the call (the anchor keeps EDI un-preserved, so its caller owns the
   save). The anchor's own 68-byte body:

scheduler record's `on_tick` store inside GameStateInit (`0x00445900`, still
