## The answer in one paragraph

**`0x00418810` is EXACT (64/64)** as `Vector3_00418810::OffsetPoint` of a
native-LTCG cluster: the whole body - the lazy-init guard, both x87 add pairs,
the `z` copy and the returned address - is byte-identical, sha256
`4992090266bf2f5b006464c8c2639d01c2c512b84caec3dc361d665b135d817e`. Retail's
entry is the *source point in EAX and nothing else*, which no declaration names,
so the body is compiled as a member of the point type with an array-walking
synthetic caller; the whole-program pass hands the receiver EAX on its own (the
guard's scratch comes out `DL`/`ECX` exactly as retail). **The x87 sum rule held
for this body in the half that applies to it**: both x87 sums are
`field + pooled literal`, and the emitted `fld [field]; fadd [pooled]` order is
what the rule predicts for the operand forms - it is decided by the *operands*
and not by the source spelling. The rule's other half (a `(X+Y)+Z` pair emitted
in ascending struct-offset order) cannot be exercised here, because no sum in
this body has two same-base fields; the follow-up on `0x0044C2A0` below shows
what happens where it can.

## How the three blockers of the 2026-09-18 attempt fell

That note's model reached the exact 64-byte extent with 30 differing bytes on
three sites; each one turned out to be a statement about the *operand form*:

| blocker (as measured 09-18) | what fixed it |
| --- | --- |
| flag test came out `84 d1` (`test cl,dl`) instead of retail's `84 ca` (`test dl,cl`) | the receiver is in **EAX** in the landed link, so the guard's scratch register allocation falls out as retail's `DL`/`ECX`. The pre-existing model had byte-for-byte the same guard source; the register the *pass* picks is what orders the operands. |
| x87 pair came out absolute-first (`fld [abs]; fadd [point]`) where retail is point-first | the addend must be a **pooled literal** aliased by `constant_aliases`, not an `extern float` object. With a literal, MSVC emits `fld [field]; fadd [abs]` - and it emits that for *either* source order (measured: `x + 224.0f` and `224.0f + x` compile to the identical pair, in the plain TU and in the cluster). |
| the second `fstp` sank below the two integer stores | the third component is a **float member copy** (`g.z = z;`), which emits `mov eax,[eax+8]; mov [g+8],eax`. The earlier model declared `z` as `int`, which re-ordered the stores. |

Measured along the way: the guard's *instruction sequence* is MSVC's per-function
lazy-init bit for a function-local static - a `static LazyInitFlag` whose empty
constructor the compiler folds leaves exactly this `mov dl,[$S1]; mov ecx,1;
test cl,dl; jne; or [$S1],ecx` with a `?$S1@?1??OffsetPoint@…@4IA` symbol in
`.bss` (verified by compiling that source shape). It cannot be *registered* that
way: a function-local static's symbol has internal linkage, so no `data_aliases`
binding can move it to retail's `0x497D8C` (the cluster link refuses with
"declared constant alias has no pooled definition to rebind"). The landed model
therefore declares the record and its flag externally and spells the guard as
the bit test it performs.

## What this unblocks

* The region itself: 64 bytes move from `asm` to `semantic` C++ (581 semantic).
* `0x00488DB0` and `0x00449350` are **not** unblocked - they are the same
  "(224, 16)" arithmetic with a different incoming register (EDI and
  ESI + ECX respectively) and their own callee conventions, but they can reuse
  this layout's `constant_aliases` (`__real@43600000` -> `0x470B4C`,
  `__real@41800000` -> `0x470B48`) verbatim, and the driver shape that earns a
  receiver register is now proven for a leaf with no calls.
* Nothing else: no anchor was dropped and no caller became a definition (the
  callers stay assembly and keep resolving through the manifest's `symbols` map).
