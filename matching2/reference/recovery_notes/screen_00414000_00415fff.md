# Screen of unpromoted rows at `0x00414000..0x00415FFF`

Date: 2026-09-23

## Result

No row in this screen was promoted. Live Ghidra confirms ordinary stack
arguments for some entries, but each of those bodies still relies on private
register inputs at direct helper calls. The remaining short entries inherit
their receiver or state from ESI, EDI, or EBX at the entry point. Translating
those rows as independent C++ routines would invent call contracts that the
current callers do not use.

This pass was read-only with respect to Ghidra. No build, probe, or test was
run, and `regions.json` and shared headers were not changed.

## `0x00414570` — recovery composite release (121 bytes)

Ghidra identifies one call site at `0x00417EED`. Immediately before that call,
the caller loads `0x0047770C` into EBX and supplies no stack argument. The
callee reads `[EBX+0x9EB8]`, then calls `0x004136C0` without setting ESI; the
release helper therefore depends on the retained register context. Later it
calls `0x00447810` without ordinary stack arguments while traversing the
manager-owned slot at `0x00491C10 + 0x3AD0DC`. This corroborates the blocker
already recorded in `src/game/recovery_release_composite_state_00414570.cpp`
and `animation_slot_release_004136c0_blocker.md`. A replacement needs the
manager teardown caller and both helper ABIs in one recovered context.

## `0x00414830` — item-manager factory (136 bytes)

Ghidra reports a no-argument `__stdcall` factory called from `0x00417AAB` and
`0x0040A37C`; both call sites consume the returned pointer in EAX. The body
installs an FS-based SEH registration, allocates `0x9ED0` bytes, calls the
`0x00413810` constructor, then initializes the front runtime through
`0x00413980`. On failure it calls the item-manager cleanup at `0x004145F0`
before freeing the allocation. The existing factory note records that the
prior standalone source candidate emitted only 1 of 136 comparable bytes and
that native exception registration plus constructor/destructor integration
is the next dependency. No new conversion path was found; see
`manager_factories_00408910_00413810_0041afd0.md` and the blocker comment in
`src/game/item_manager_create_retail_00414830.cpp`.

## `0x00415800` — front overlay draw (724 bytes)

The code xref at `0x00415AF1` is preceded by `push ECX`; Ghidra identifies the
body as a one-argument `__stdcall` routine and its pseudocode returns 1. The
draw path walks four fixed animation banks and calls `0x004451C0` at each
element. The live disassembly at those calls places the animation manager in
ECX and the entity pointer in EAX. Ghidra's analysis of `0x004451C0` confirms
the hidden EAX receiver; its C++ definition is already semantic, but callers
still need a compatible register context. The other direct helper,
`0x0043BDA0`, is called after the caller writes rectangle values into local
stack slots and uses the x87 unit for its draw calculations. The current
Ghidra signature does not fully describe that call's input contract. The
entry's ordinary stack ABI is therefore not sufficient to replace its current
body independently. Its source comment records the existing schema-2/LTCG
cluster path.

## `0x00415B00` — stage-slot initialization (683 bytes)

Ghidra confirms a conventional two-argument `__stdcall` entry returning the
allocated record. Its sole caller is `0x00415DB0`, which pushes the record and
script-data pointer. The body initializes a `0x90`-byte record, allocates and
registers animation entries, initializes their manager records, sweeps 2,000
stage entries at `0x7F0` stride, and runs the enemy-manager update.

The helper chain is not ordinary at the call sites: `0x004489D0` receives its
new node in EAX and manager in EDX; `0x00408030` is entered with its entity in
ESI; and the animation-pool allocator `0x00449950` is reached with its manager
in ESI. `0x004491C0` and `0x00449950` have semantic source now, but their
production calling contexts are coupled to these register conventions.
`0x00449870` and the two private-register helpers remain assembly. The
existing `stage_slot_state.cpp` blocker correctly calls for a caller-inclusive
LTCG recovery of `0x00410DDB -> 0x00415DB0 -> 0x00415B00` with the pool and
record layouts.

## `0x00415DB0` — stage-slot factory (124 bytes)

Ghidra reports no stack parameters. Its sole xref is `0x00410DDB`; the live
disassembly there loads EDI from `0x0047770C`, moves the resolved ECL index
from EAX into ESI, and calls this entry with both values live. The callee
registers an FS-based SEH frame, allocates `0x90` bytes, derives the script
pointer from `[EDI+0x9EBC]` and ESI, then calls `0x00415B00` with two stack
arguments. It stores the result at `[EDI+0x9EB8]` and records the index.
Because the entry ABI itself is the ESI/EDI tuple, it cannot be represented
as the apparent `void __stdcall(void)` Ghidra signature. Its source comment
already points to the required caller-inclusive constructor cluster.

## `0x00415E30` — unassigned tick fragment (93 bytes)

Ghidra still has no function at this address. The maintained source comment
records the live fragment: it enters with the state in ESI, calls
`0x00415E90`, updates the state fields at `+4`, `+8`, and `+0xC`, and invokes
the x87-input rounding helper at `0x00463B2C`. Existing compiler-context
attempts reached 92/93 bytes because the candidate used the receiver in ESI
where the retail bytes expect the EAX-entry flow. This agrees with
`named_callee_drops_wave20.md`, `ownerless_60_256_wave19.md`, and the maintained
`src/unidentified/unassigned_00415e30.cpp` blocker. Revisit with the real
caller and x87 helper in the same native-LTCG context.
