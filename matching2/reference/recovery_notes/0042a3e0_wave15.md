The model emits the same seven instructions, but **the two `ret`s swap roles**:
the four early returns (and the modulo's `je`) target the final `ret` at
`+0x43` inside the null path's materialising block, while the `mov eax,6` arm
keeps its own `ret` at `+0x3D`. In retail the `mov eax,6` arm falls *into* the
shared `ret` at `+0x3D` and the null path owns the last block.

So: retail has one shared epilogue for the value returns plus a *duplicated*
epilogue for the cold null path; the model has one shared epilogue for the null
path and a duplicated `ret` for the `mov eax,6` arm. Both are 68 bytes and both
are semantically identical (EAX already holds the right value on every path) —
this is purely MSVC's return-block placement.

Two details are load-bearing and were found by sweeping (both are needed for the
68-byte layout; drop either and the compiler folds the two return values into a
single epilogue and emits 62 bytes at different offsets):

1. the null check must be the **wrapper** `if (scene) { ... } return 1;`, not the
   flat `if (scene == 0) return 1;` — the flat spelling puts the null epilogue
   *inline* (`jne +6; mov eax,1; ret`), which is not retail's `je` to an
   out-of-line block;
2. `result` needs the **second `result = 1;` def** between the third check and
   the modulo test. With it the mid returns take retail's hoisted
   `mov eax,1` at `+0x0D` (so the compare is `cmp [ecx+0x10],eax`, the global
   test is `test al,dh`, the modulo lands in ECX and the arm is branchy
   `je; mov eax,6`); without it the constant is hoisted to the entry `+0x08`,
   the receiver moves to EDX and the modulo arm is the branchless
   `neg/sbb/and/inc` form.

The body bytes are identical whether this source is compiled as a plain TU
(ECX-entry thiscall already matches retail) or through the native-LTCG cluster;
the four displacements are the same in both.

the natural Ghidra reading

## Conclusion for this region

The body is *semantically* recovered and the extent is proven, but the four
`rel8` bytes are a return-block-placement choice that this MSVC build makes the
other way round. A `source_flags` entry cannot help (`/Os` is the only flag that
moves anything and it changes the whole schedule). Re-attempting it is only
worthwhile with a lever for MSVC's cold-block/split-epilogue decision, e.g. a
called-side caller that pins the null path cold, which the two sibling clones in
this family do not provide either (`0x00429A30` — same body without the
`flags_58 & 4` check — has the *single* shared epilogue shape and would need the
same treatment).

Not landed: a non-exact layout must never be registered, so no manifest record,
`translation_units` entry or `ltcg_clusters` entry was written in the maintained
tree.
