### What the wave-8 draft was missing (each measured)

1. **`data_00491c10` must NOT be `volatile`.** With `volatile` the pass reloads
   the manager in `ECX` per iteration *and* keeps the whole slot offset
   `4*index` in the cursor, so the addressing comes out
   `[edx+ebx*1+0x3ad06c]` (7 bytes) instead of retail's `[ebx+ecx*1]` (3 bytes).
   Without `volatile` the pass reloads the manager **because the two opaque
   callees may write the global** and builds retail's cursor exactly
   (`mov ebx,0x3ad090`) — 316/313 bytes fall to 305/302.
2. **The slot body needs the *slot pointer* idiom**, not the record:
   `AnimationResource_00447810 **slot = &data_00491c10->slots_3ad06c[index];`
   then `(*slot)->Release(); entry_free_004524a1(*slot); *slot = 0;` — exactly
   the idiom `recovery_release_pair_0041f930.cpp` uses. That is what gives
   retail's `lea esi,[ebx+ecx*1]` materialisation *and* the post-call reload
   `mov edx,[esi]` (the `free` argument is `*slot`, not the record).
3. **The counted trip counter** (retail's `mov [esp+0x10],0x4`, i.e. the
   `push ecx` slot) only appears when the loop carries *both* a counted index
   (`for (int i = 0; i < 4; ++i)`, 4 = retail's constant) **and** the derived
   `int index = 9 + i` used by the two bounds checks. With only the derived
   index (`for (slot = 9; slot < 13; ++slot)`) there is no trip counter, the
   prologue loses `push ecx`, and the function is 299 bytes.
4. **`blocks_054` must be cached in a pointer local** for the release block, or
   the `free` argument is re-read (`mov ecx,[edi+0x54]`) where retail pushes the
   live `ESI`.
5. **`_ReadWriteBarrier()` between `blocks_054 = 0;` and the `data_00474ca0`
   test** is what stops the scheduler from materialising the flag byte in `CL`
   and sinking the store; retail keeps `xor eax,eax / mov [edi+0x54],eax /
   test BYTE PTR ds:0x474ca0,0x9 / jne`. That single intrinsic is worth 2 bytes
   and the whole 0xE3-group (302 → 300).
6. **The scheduler local must be loaded before the null test** in both blocks
   (`Scheduler *scheduler = data_00491be4;` outside the `if`), which is what
   makes the pass hoist `mov ebx,ds:0x491be4` above `je` as retail does.

## Instruction-level delta (4 bytes, offsets 0x2E..0x31 and 0x62..0x65)

```text
+0x2E 0040D55D  8b d3  mov edx,ebx   | 8b ce  mov ecx,esi
+0x30 0040D55F  8b ce  mov ecx,esi   | 8b d3  mov edx,ebx
+0x62 0040D591  8b d3  mov edx,ebx   | 8b ce  mov ecx,esi
+0x64 0040D593  8b ce  mov ecx,esi   | 8b d3  mov edx,ebx
```

The two independent register copies that set up `Scheduler_Remove(task,
scheduler)` (ECX = task from ESI, EDX = scheduler from EBX) are emitted in the
opposite order. Extent, both blocks, both locks, both `ret` paths, the whole
slot loop, every branch displacement and every call displacement are identical.

Evidence that this is not a source-shape mistake (all measured, all in the
merged cluster unless noted):

* A whole-image scan finds **40** call sites of `0x449F60` with the pattern
  `mov ecx,reg / mov edx,reg / call` and **zero** with the reverse order, and
  no other callee in the image is reached with two register copies. Retail's
  own compiler emits this order at *this* callee only.
* My compiler emits `mov edx,ebx` then `mov ecx,esi` for this source in a plain
  (non-`/GL`) object too, with the same flags.
* The 3-argument fastcall `Recovery_LoadCachedResource_00447280(id, cache,
  name)` is **exact** in the same link with the order `mov edx,<cache> / push
  <name> / mov ecx,<id>`, i.e. retail's own order for that callee, so the
  toolchain is not globally shifted.
* `0x00404F...`-independent: wave 6 hit the identical residual at `0x00405620`
  (`entity_player_helpers_00401de0_00405d00_00405620_004059f0.md`), which
  records the same `8B D7 8B CE` vs `8B CE 8B D7` and concludes "the remaining
  blocker is the precise original source expression or compiler scheduling
  context that orders the two independent custom-ABI register
  materializations".

## What remains for landing

Nothing about the *layout* remains: the three-way merge, the section-name
assignment and every `code_seg` rename above were exercised, and the full merged
cluster builds and validates all 27 function extents with 26 of 27 exact. What
blocks the landing is the 4-byte argument-copy order, which is a
declaration-independent property of this toolkit's fastcall argument setup.

Landing therefore needs one of:

1. the original front-end expression/compiler context that orders the two
   materialisations `ECX` then `EDX` (the same open question wave 6 left at
   `0x00405620`), or
2. a toolkit build whose fastcall argument setup matches the retail build.

If that is found, the landing itself is one `apply_package.py` payload (the
merged layout replaces `bullet_manager_load_scripts_0040ae70.json`,
`animation_manager_mark_resource_for_removal_004493e0.json` and
`bullet_entity_release_resource_0040d680.json` in `ltcg_clusters`, the 9 sources
listed above plus the 18 bullet-layout sources get the new `code_seg` tags, and
two new regions `0x0040D530`/`0x0040D6B0` join it), because a single-source
`register_cluster.py --apply` cannot express a three-cluster merge.
