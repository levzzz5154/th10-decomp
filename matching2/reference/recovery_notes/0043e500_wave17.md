## Which lever applied — and which did not hold

The two levers the ticket named were applied deliberately and **neither held**;
the decisive lever was the x87 operand form of the scale.

| measured shape | emitted | differing | first difference |
| --- | ---: | ---: | --- |
| `extern float` scale (`data_00470b1c` bound absolutely) | 31 | 15 | `+0x01 05/44` — `flds [470b1c]` instead of `flds [esp+4]` |
| **literal `60.0f` + `constant_aliases` → 0x470B1C** | **31** | **0** | — |
| named temporary + two stores (landed) | 31 | **0** | — |
| `field_018 = field_014 = (int)(seconds * 60.0f);` | 31 | **0** | — |
| `field_014 = (int)(…); field_018 = field_014;` | 31 | **0** | — |
| two separate conversions of the same expression | 31 | **0** | — |
| flag store written *after* the two value stores | 31 | 22 | `+0x04 d8/c7` — the fmul is no longer scheduled into the window |
| `int` return instead of `void` (both spellings) | 31 | **0** | — |
| `roots: [<the symbol>]` | 35 | 28 | `+0x04 56/c7` — `push esi`, `mov ecx,esi`, `pop esi` reappear |

**The consumed-temporary lever did not hold.** The four genuinely different
spellings of the two stores — a named temporary stored twice, the chained
assignment `field_018 = field_014 = <expr>`, the plain reload
`field_018 = field_014`, and even two independent conversions of the same
expression — all emit retail's `mov [esi+14h],eax; mov [esi+18h],eax`. The
backend keeps the `__ftol2` result in EAX for both stores and reorders the
chained-assignment stores to ascending offset, so there is no consumed-temporary
residual to break here, unlike `0x00449950` where the argument and the result
home competed for the object's production register. The lever was applied and
measured; it is simply inert for a *store-twice* shape, which is the boundary
worth recording from this side.

**The `void`-return lever did not hold either.** Retail leaves EAX holding the
conversion result at both exits (with a `void` model that register is dead), yet
declaring the member `int` and returning the value — with the layout declaring
the matching `?SetSeconds@TimeValue_0043e500@@QAEHM@Z` symbol — emits the very
same 31 bytes, in both the `return frames;` and the
`return field_018 = frames;` spelling. As in `lazy_animation_resource_0040c540_wave11.md`
the lever matters when a *load* has to be coalesced into EAX at the end of the
body; here the value already lives there from the conversion, so the return type
has nothing to move.

**What did hold is the operand form of the scale.** With the scale declared as
an `extern float` object the compiler loads the *constant* into st(0) and
multiplies by the argument — `flds [470b1c]` / `fmuls [esp+4]` — and 15 of the
31 bytes differ. Both operands are memory operands, so this is not a length
effect (the two instructions are 6+4 either way): it is the operand *form* that
decides which side the x87 pair loads, exactly the boundary lever 3 of the wave-
17 contract records ("a field plus a pooled literal is decided by the operand
form"). Writing the scale as the float literal `60.0f` and aliasing the
compiler's pooled `__real@42700000` to retail's `0x470B1C` through the layout's
`constant_aliases` reproduces retail's load-then-multiply order with no byte
patched. Note the alias alone is not the fix and the literal alone is not
either: the alias pins the *displacement*, the literal form pins the *roles*.

Two further position decisions, both confirming levers already in the notes:

* **Empty `roots` earns ESI** (lever 4). With the symbol listed as a root the
  pass keeps the declared `__thiscall` ABI — `push esi` / `mov ecx,esi` /
  `pop esi` — and emits 35 bytes. Reachable only from the synthetic
  array-walking context, the record is promoted to the callee-saved ESI because
  it is live across the `__ftol2` call, and no prologue appears.
* **Statement order is load-bearing** here too (lever 8): the `[esi+1Ch] = 1`
  store must be written before the conversion so the scheduler can hoist it into
  the multiply's latency window, where retail has it. Written after the two
  value stores the body differs from the fourth byte on.

### `src/unidentified/unassigned_0043e500.cpp`

// record.
//
// Retail, in order (D9/D8 are the x87 pair, E8 the __ftol2 conversion):
//
//   D9 44 24 04      fld   dword ptr [esp+4]      ; the seconds argument
//   C7 46 1C 01..    mov   dword ptr [esi+1Ch],1
//   D8 0D <470b1c>   fmul  dword ptr [60.0f]
//   E8 <463b2c>      call  __ftol2               ; (int)(seconds * 60.0f)
//   89 46 14         mov   [esi+14h],eax
//   89 46 18         mov   [esi+18h],eax         ; the same result twice
//   C2 04 00         ret   4
//
// The record arrives in ESI and the one float argument on the stack, so the
// member is compiled as a native LTCG cluster.  ESI is what the pass picks
// because the record is live across the __ftol2 call, which needs a
// callee-saved register; the caller-supplied array walk in the cluster driver
// is what makes it a callee-saved register instead of ECX/EAX.  The result of
// the call is then used twice - the conversion value is stored straight out of
// EAX into both +0x14 and +0x18.
//
// Two spellings were measured against retail's bytes in the same link:
//
// * the scale as an `extern float` variable.  The compiler then loads the
//   *constant* into st(0) and multiplies by the argument - `flds [470b1c]` /
//   `fmuls [esp+4]` - and 15 of the 31 bytes differ.  Both operands are memory
//   operands, so this is not a length effect: the operand form of the scale,
//   not the expression's left-to-right order, decides which side the x87 pair
//   loads.  Writing the scale as the float *literal* 60.0f and aliasing the
//   compiler's pooled `__real@42700000` to retail's 0x470B1C (the layout's
//   `constant_aliases`) reproduces retail's load-then-multiply order exactly.
// * the two stores: a named temporary, `field_018 = field_014 = <expr>`, a
//   plain `field_018 = field_014` reload and two separate conversions of the
//   same expression all emit retail's `mov [esi+14h],eax; mov [esi+18h],eax`.
//   The conversion result stays in EAX for both stores whatever the spelling,
//   so no consumed-temporary lever is needed here, and a `void` or `int`
//   return is equally inert because retail's EAX at both exits is already the
//   conversion result.  What is load-bearing is the *statement order* the
//   0x1C flag is written in: with the flag store written after the two stores
//   it is no longer hoisted into the multiply's latency window and the body
//   differs from the second byte on.

};
