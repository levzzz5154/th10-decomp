## What the body is

Two scheduler links of the same previous/current/elapsed/speed/flags timer block
the score timer (`src/game/score_timer_leaves.cpp`, +0x2B0..+0x2C0) and the
recovery state (`src/game/recovery_initialize_timed_state_00423510.cpp`,
+0x10..+0x20) carry, at +0x3F8..+0x408 and +0x40C..+0x41C, plus the low half of
the record's scheduler counter at +0x446. Each link: while the running bit is
clear, arm previous with 0xFFF0BDC1, clear current and elapsed, point speed at
the shared float `data_00476f78`, raise the running bit; then unconditionally
clear current and elapsed and stamp previous with -1.

The ABI is the EAX-receiver family the twins `0x004050D0`
(`layout/ltcg/embedded_timer_reset_004050d0.json`) and `0x00412DB0`
(`layout/ltcg/recovery_timer_reset_00412db0.json`) already use: record in EAX,
nothing on the stack, plain `RET`. The array-walking synthetic caller in the
driver earns it; nothing else moved.

## The prediction, and whether it held

**Predicted from shape alone:** the store in front of the `test cl,1` sits in a
load-to-branch latency slot, so a direct member store modelled there should sink
into that slot; a store through a pointer to the field should not. **Held**, and
it was measured four ways, same layout, same driver, only the body text
changing (`cluster_attempt.attempt`, 158 bytes emitted in every case):

| body shape | differing bytes | first | instruction rows that move |
|---|---:|---:|---|
| direct `marker = 0;` + direct tails | 45 | +0x00 | 9 (two clusters) |
| `unsigned short* record = &marker; record[0] = 0;` (lead only) | 27 | +0x3D | 5 |
| **both leads and both 3-store tails behind a shared pointer** | **0** | **-** | **0** |
| `unsigned char* base = (unsigned char*)this;` + casts for everything | 45 | +0x00 | 9 (two clusters) |

Direct, retail vs emitted:

```text
  405be0  retail: xor edx,edx                        got: mov ecx,[eax+408h]
  405be2  retail: mov WORD PTR [eax+0x446],dx        got: xor edx,edx
  405be9  retail: mov ecx,[eax+408h]                 got: test cl,0x1
  405bef  retail: test cl,0x1                        got: mov WORD PTR [eax+0x446],dx   <- sank
  ...
  405c1d  retail: mov DWORD PTR [eax+0x3fc],edx      got: mov ecx,[eax+41ch]            <- load hoisted
  405c23  retail: mov DWORD PTR [eax+0x400],edx      got: test cl,0x1
  405c29  retail: mov DWORD PTR [eax+0x3f8],-1       got: mov DWORD PTR [eax+0x3fc],edx <- sank
  405c33  retail: mov ecx,[eax+41ch]                 got: mov DWORD PTR [eax+0x400],edx
  405c39  retail: test cl,0x1                        got: mov DWORD PTR [eax+0x3f8],-1
```

So the sink happens **twice** in one function, and the second one is the more
interesting: the shared tail of the first link (three stores executed on both of
its paths) is a perfect filler for the *second* link's compare slot, and the
second flag load is hoisted above it — 27 of the 45 bytes. Putting only the
leading store behind a pointer removes the first sink (rows 0-3 become retail's)
and leaves exactly that second one, which is why the lead-only form measures 27.

The fix is the same lever applied to the tail: the three clearing stores share
one pointer, as the pair write of `src/game/score_timer_leaves.cpp` shares one:

```cpp
    int* tail_1 = &link_1_current;
    tail_1[0] = 0;
    tail_1[1] = 0;
    tail_1[-1] = -1;
```

`tail_1[0]` is +0x3FC, `tail_1[1]` is +0x400, `tail_1[-1]` is +0x3F8, so the
emitted displacements are retail's order (current, elapsed, previous) while the
three stores now share one address value and stay in front of the next flag load.

**A measured refinement worth carrying forward:** the last row of the table is
the *legacy* form - one `unsigned char* base` for the whole record and casts at
every use. It does **not** behave like the lever; it measures exactly the
direct form's 45 bytes, store for store. The lever is not "any pointer
arithmetic": it needs a typed pointer to the field whose value is a distinct
local (`&marker`, `&link_1_current`), not a byte base the compiler folds back
into constant-displacement member accesses. This is the same distinction the
pair write in `score_timer_leaves.cpp` relies on.

## Regions this touches

- **The twins of the 50-byte family** have the same timer block but **no second
  link after the tail**, so there is nowhere for the tail to sink and no leading
  store to sink either — they are the control group that shows the sink is
  caused by the *following* compare, not by the stores. Measured, sha256 of the
  retail bytes over `[address, address+size)`:

  So `0x004421E0` and `0x0041AC40` are recoverable with an already-landed model
  and a new symbol: `0x0041AC40` is exactly
  `RecoveryTimer_00412db0::Reset` (`src/game/recovery_timer_reset_00412db0.cpp`,

  +0x10..+0x20.

- **`0x004050D0`-style embedded timers** elsewhere in the player can now be

  `test <flags>,1` follows it, and the trailing three stores need a shared
  pointer whenever another `test <flags>,1` follows *them*.

## Tooling note for the next reader

`matching2/tools/waves/cluster_attempt.py` still needs one local monkeypatch:
`_map_section` uses `_map_offset`'s regex, so it returns the **offset** column of
the map's contribution table instead of the **length** column
(` 0001:00000000 00004be0H .text$00layout`). On a first-build size mismatch its
adaptive retry then feeds offsets back as sizes. The sweep here replaced it with

```python
re.search(r'[0-9A-Fa-f]{4}:([0-9A-Fa-f]{8})\s+([0-9A-Fa-f]{8})H\s+' + re.escape(section) + r'\b', map_text)
```

and, with that, the first build already emitted the declared 158 bytes. The
driver's `context.symbol` must also be written **without** the leading
underscore the layout machinery adds (`PlayerResetSchedulerLinksContext@8`);
with `_PlayerResetSchedulerLinksContext@8` the link fails on
`__PlayerResetSchedulerLinksContext@8`. `cluster_attempt.attempt` also keeps
iterating over the remaining variants after one lands, so the *last* variant,
not the landed one, is what stays in the source file — write the landed body
back before registering.
