## Constructor dependency topology

### Live Ghidra contract for `0x00408910`

The live `th10.exe` analysis identifies the function entry as
`0x00408910` and the body as `0x00408910..0x004089BF` (176 bytes). Its
signature is `uint* __stdcall(uint*)`. Ghidra reports one direct caller,
`FUN_00408c90`, with the call site at `0x00408CC5`, and one direct callee,
the vector-constructor iterator at `0x0045252D`.

The caller allocates `0x37B0` bytes, pushes the returned storage pointer, calls
`0x00408910`, and consumes the result in EAX. The callee ends with `ret 4`,
confirming that it removes its one stack argument. The iterator has the
Ghidra signature `void __stdcall(void*, uint, int, constructor, destructor)`;
its body ends with `ret 0x14`. Its constructor callback is invoked with the
current element in ECX and the element address advances by the supplied
stride. The target passes constructor/destructor callbacks at `0x00402050`
and `0x00401FF0`, respectively, in three calls with counts 2, 8, and 5 and
stride `0x3AC`.

The target then clears the dword at manager offset `0x3744`, zeroes `0xDEC`
dwords starting at the manager base, sets bit 1 in the first dword, stores the
manager pointer at `0x004776F4`, restores the exception chain, and returns the
manager pointer. The C++ entry and callback types mirror the observed stack
cleanup and ECX receiver contracts. Its output code layout has not been
verified.

Ghidra/IDA show that `0x00408910` calls the shared
`0x0045252D` vector-constructor iterator three times and `0x00413810` calls
it six times. Every call passes the existing Entity constructor at
`0x00402050`, Entity destructor at `0x00401FF0`, and stride `0x3AC`.
The iterator's direct chain is:

```text
0x0045252D  -> 0x00454BBC, 0x00452577, 0x00454BF7
0x00452577  -> 0x004525A1
0x004525A1  -> 0x00454BBC, 0x00454BF7
```

Those helper source files have no concurrent worktree edits and are shared by
the game-state, archive, stage, and other manager constructors. They were
therefore confirmed as exact read-only dependencies rather than reclassified
or duplicated in a task-specific cluster. The existing semantic Entity
constructor/destructor in `src/game/entity.cpp` also remains exact and
unchanged.

## Recovered semantics

### `0x00408910` — `PlayerManager_ConstructRetail`

This is a `__stdcall` construction routine taking and returning the manager
storage pointer. The current source expresses the three calls to the
`__stdcall` vector-constructor helper at `0x0045252D` with typed
`__thiscall` entity callbacks: 2 entities at byte offset `0x10`, 8 at `0x778`,
and 5 at `0x24D8`, all with stride `0x3AC`. It then clears `0x37B0` bytes,
sets bit 1 in the manager word, publishes the manager address in
`DAT_004776F4`, and returns the storage pointer. The intermediate clear of
the word at `+0x3744` is preserved before the full clear.

The construction behavior is supported by the archived semantic source,
`reference/legacy_semantic/src/game/manager_factories.cpp`, the Ghidra
function `decompiled/ghidra_augmented/functions/00408910.c`, and the caller
`src/game/player_manager_create_retail_00408c90.cpp`.

### `0x00413810` — `ItemManager_ConstructRetail`

This is the corresponding `__stdcall` item-manager construction routine. It
constructs six entity banks with stride `0x3AC` at byte offsets and counts:

```text
0x0010: 10    0x24C8: 10    0x4980: 9
0x6A8C:  4    0x793C:  2    0x8094: 7
```

Before the final clear it performs the manager's embedded flag/sentinel
initialization (the word/dword locations identified in
`decompiled/ghidra_augmented/functions/00413810.c`), including clearing the
embedded sentinel array and setting its `0x2773` word to `0xFFFF`. It then
clears `0x9ED0` bytes, sets the live bit, publishes `DAT_0047770C`, and
returns the storage pointer. The final clear deliberately overwrites some of
the earlier object bytes; those stores are part of the observed legacy
layout, not an omission in the semantic reconstruction.

The archived semantic source and the caller
`src/game/item_manager_create_retail_00414830.cpp` corroborate the bank
layout. The Ghidra/IDA output is the authority for the extra pre-clear
sentinel stores.

### `0x0041AFD0` — `ItemManager_UpdateItems`

This is a `__stdcall` per-frame item-pool sweep. It clears the two pool
counters at offsets `0x21CEBC` and `0x21CEB4`, then visits 2198 records at
`manager + 0x14`, with record stride `0x3F0`.

The recovered state machine is:

* state 5 counts down and transitions to state 2, advances the item resource
  by `0x176`, and invokes the resource/effect helper at `0x00404F30`;
* states 1 and 2 integrate position and velocity using the frame delta,
  gravity, and the observed screen bounds; state 1 can attach to the player
  and enter steering, while state 2 can leave the pool and apply the
  `-4` player-power adjustment;
* states 3 and 4 steer toward the player's position using the x87 angle path
  and the helper at `0x0041BEB0`; player state 4 returns the item to state 1
  and clears velocity;
* the player collection rectangles can pull an item into state 4 and set its
  magnet speed;
* in-range item types run their type-specific gauge, power, score, timer,
  sound, effect, and HUD paths; point values use the archived mapping
  (`5000`, `8000`, or `10000` depending on the point tier);
* animation timing advances through `0x0043EE30`, and the full-power path can
  invoke the pending enemy-drop sweep at `0x0041BA50`;
* the routine returns `1`.

The archived `UpdateItems` model is useful for naming the states and broad
transitions, but it is explicitly a partial host/runtime model. It does not
cover all item types, state 5/resource behavior, exact animation timing,
the complete collection side effects, the enemy-drop path, or the original
x87 instruction schedule. Consequently it was not copied into production.

## Prior candidate mismatches and current verification limit

Readable constructor candidates were compiled in dedicated temporary
sources and discarded after comparison. Under the maintained native-LTCG
flags (`/O2 /Gz /MT /Gy /G6 /GF /GS /Zl`), member-array construction lowered
to inline/direct loops and did not emit the required EH vector-helper chain.
Adding `/EHsc` caused MSVC to emit the expected `??_L`/`??_M` vector-helper
references and an FS-based registration frame, but it also emitted
compiler-owned `.text$x` and `.xdata$x` contributions, extra EH handler
symbols, different state/save instructions, and non-target body extents.
The final stack-ABI candidate contributed 174 bytes and 276 bytes versus the
176-byte and 367-byte targets, while direct placement-array variants
contributed 207 bytes and 357 bytes and carried array-cookie behavior. None
passed an exact probe and none were promoted.

Those byte comparisons covered earlier C++ candidates and do not validate the
current source. The current source uses the Ghidra-confirmed typed helper and
callback contracts, but has not been built or probed. Its exact byte match,
generated section extent, and integration with the existing EH/vector-helper
layout remain unverified.
