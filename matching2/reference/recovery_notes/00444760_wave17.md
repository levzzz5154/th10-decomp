# 0x00444760 (929 bytes) — wave 17: the convention is cracked, 902/929

2026-09-19, worker `Case8Convention`. Work was done in `/tmp/Case8Convention/msvc`
(`cp -a matching2/msvc`, then the wave-16 model grafted back in); the maintained
`regions.json`, sources, layouts and drivers were never touched — this note is the
only file the tree gained. **The region is not landed**: the model now emits
**902 of the declared 929 bytes**, and the note below names the four remaining
instruction groups. A non-exact layout must never be registered, so nothing was
registered and no package was staged.

## The answer in one paragraph

Wave 16 left one blocker: with the real 929-byte body in the link, the
whole-program pass derives *both parameters on the stack* (`RET 8`) for
0x00444760 instead of retail's `(entity EAX, manager on the stack, RET 4)`, which
also re-homes the dispatcher's entity and moves 172 of its 216 bytes. **That
blocker is solved.** Adding a *compiled ABI anchor* for the sync callee
0x004423E0 — whose body keeps the entity live across two calls, so the pass gives
the entity **EBX** and the manager the stack — makes the caller's fixpoint retail's
again: the emitted body opens `sub esp,0xc0 / push ebx / mov ebx,eax /
mov eax,[ebx+0x35c] / test al,1 …` and closes `xor eax,eax / pop ebx /
add esp,0xc0 / ret 4`, both byte-identical to retail, and the dispatcher 0x004451C0
returns to its retail 216 bytes with `push ecx; call 0x444760`. On top of that,
door 2 from the wave-16 note is confirmed: modelling the entity's stored matrices
as *members* (`view->world_transform.m[0]`, `m[5]`) reproduces retail's addressing
forms exactly and recovers the 8 bytes of deltas #3/#4. The 27 bytes still missing
are the call site's marshalling form (-1), the mirrored `case 1` x87 evaluation
order with retail's gratuitous `fxch st(1); fxch st(1)` pair (-4 each) and the
duplicated `uv_scroll_x` comparison (-18).

## The lever: the anchor's live-range shape decides the caller's receiver

The anchor is a body at 0x4423E0 (a retail address, never exported as recovered
code) that the model calls as `SyncRenderState_004423e0(manager, entity)`. What
matters is only the register the pass gives each parameter; the anchor's own bytes
are compiler context. Measured here (the anchor's earned entry, and whether
0x00444760's own convention became retail's):

| anchor body shape (all `extern "C" __declspec(noinline) void f(manager, entity)`) | earned entry | caller |
| --- | --- | --- |
| entity used across two calls, two accumulators live across, manager used at the end | entity **EBX**, manager [esp+8], RET 4 | **retail** |
| the same with the manager's two reads written first | entity **EBX**, manager [esp+8], RET 4 | **retail** |
| entity live across, one accumulator, manager used after the last call | entity EDI, manager [esp+4], RET 4 | `RET 8` |
| entity live across two calls, manager only read at the very end | entity EDI, manager [esp+4], RET 4 | `RET 8` |
| both parameters dead at entry | entity EAX, manager [esp+4], RET 4 | `RET 8` |
| manager read and consumed first, entity live across | entity ESI, manager EAX | `RET 8` |
| manager consumed first, entity plus two accumulators live across | entity ESI, manager EAX | `RET 8` |
| manager's read consumed in the first call, entity live across | entity ESI, manager EAX | `RET 8` |
| a `Flush()` call with both parameters live across it | entity EDI, manager EAX→ESI | `RET 8` |
| two locals plus a `Flush()` call | manager EAX→ESI, entity [esp] | `RET 8` |
| the faithful 0x4423E0 body (mode switch, three `Flush()`, colour block) | entity EAX, manager ECX | `RET 8` |
| the faithful body as a member (`this` = entity) | entity ECX→EBX, manager EAX→ESI | `RET 8` |
| the faithful body, declaration `(entity, manager)` | entity ECX→EBX, manager EAX→ESI | `RET 8` |

Two observations come out of the table, and they are the wave-14/15 lever
applied to the *callee*. First, an anchor whose parameter dies before the first
call keeps a caller-saved register for it (EAX, or ECX with the declaration
`(manager, entity)`), while an anchor whose parameter is live across a call gets a
callee-saved register or the stack — so which parameter lands in a `push`-free
register is decided by the body's live ranges, not by the declaration order, which
only decides which declared parameter gets which register of the pair the pass
picks. Second, and this is the one that matters: **the caller adopts retail's entry
pair only when the anchor's entity lands in EBX.** With the anchor's entity in EBX
the pass homes the caller's entity in EBX too (`mov ebx,eax`, one push of the
manager at the dispatcher, `c8`-style frame) and the dispatcher keeps its retail
216 bytes; with the entity in EAX, ECX, ESI or EDI the caller instead collapses to
`RET 8` with the entity homed in EBP and the dispatcher loses 4 bytes. The anchor
that earns EBX is the one whose body keeps the entity live *across* a call while
two of the body's own values occupy ESI and EDI — i.e. the same "entity plus two
accumulators" shape in which the 0x443080 anchor earns ESI.

An anchor for 0x4423E0 also removes wave-16's delta #7 by itself: the call site
now carries a real parameter, so the pass emits a marshalling instruction where
the opaque `__cdecl` declaration emitted none.

## The remaining 27 bytes, instruction-aligned

Roles normalised (retail and emitted agree: entity EBX, manager EBP) and the two
streams LCS-aligned; the emitted stream is retail's apart from these groups:

| # | retail | emitted | delta |
| --- | --- | --- | --- |
| A | `mov eax,ebp` before the 0x004423E0 call (2 B) | `push ebp` (1 B) | **-1** |
| B | x `case 1`: `fld render_offset.x; fadd position.x; fadd base.x` (18 B) then the `fabsf` chain, `fxch st(1); fxch st(1)`, `fsubrp` | the `fabsf` chain first, then the sum, `fsubp` | **-4** |
| C | y `case 1`: identical shape | identical difference | **-4** |
| D | the duplicate `jp body` + `fld 0.0f; fld uv; fucompp; fnstsw ax; test ah,0x44` (18 B) | one comparison with `jnp skip` | **-18** |

Sum **-27**, and 929 - 27 = **902**. The only other aligned group is the `fstp
[esp+0x48]` / `[esp+0x4c]` slot shift that group A causes (0 net bytes). The
region's first 24 bytes and its last 12 bytes are byte-identical to retail
(`81 ec c0 00 00 00 53 8b d8 …` and `33 c0 5b 81 c4 c0 00 00 00 c2 04 00`), so the
frame, the guard and the epilogue are retail's; the honest raw comparison is
`differing 486` bytes with the first difference at `0x4448c2`, which is where
group B's shorter sequence starts.

Every one of the 21 differing bytes is a displacement or jump-table byte whose
value moves by exactly `+0x10` (or, for the table entries, by the section shift):
the linker aligns the 27-byte shortfall up to 16, so the case `call` rel32s, the
table jump and the ten table entries all shift together. Wave 16's 172-byte
displacement (the dispatcher's own entity re-homed to ESI, `push ecx; push esi;
call` and the section 4 bytes shorter) is gone; with the region at 929 bytes those
21 bytes resolve to retail's.

## What was tried for the three source-level groups

**Group B/C (the mirrored `case 1` order and the gratuitous `fxch` pair).** A plain
`/O2` translation unit reproduces every one of these shapes in 0.4 s, so it was
used as the screen and the results were confirmed in the cluster for the best
candidate. Four spellings were measured — the wave-16 baseline
`fabsf(...) - (a + b + c)`; the sum hoisted into a local before the subtraction;
the sum as an explicitly parenthesised pair; and the sum plus the `fabsf` as two
named locals. **All four emit the `fabsf` chain first** (894 bytes, zero `fxch`,
`fsubp` with no swap) and the cluster agrees: the hoisted-sum model (with the
member matrices) is 902 bytes too. MSVC 13.10's scheduler moves the sum's three
loads into the `fabsf` chain's shadow whatever statement order the source uses, so
retail's sum-first order and its cancelling `fxch` pair are not reachable from the
spellings tried.

**Group D (the duplicated `uv_scroll_x` comparison).** Twelve further spellings
were measured in this wave: the baseline `||`; the operands swapped;
a hoisted `void* const stage_source`; a hoisted `float uv_scroll`; the fully
negated `!(a == tex && uv == 0.0f)`; the same with the `&&` terms reversed; an
implicit `|| entity->uv_scroll_x`; `int refresh = (ptr != tex) | (uv != 0.0f)`
(with and without the local); `(int)(ptr != tex) + (int)(uv != 0.0f)`; the split
`uv > 0.0f || uv < 0.0f`; `!(ptr == tex) || uv`. **Every one emits a single
`fucompp` with `jnp`** — the bitwise/sum forms are 18 bytes *larger* but still
compare once. Together with wave 16's eight spellings that is twenty, and
retail's `jp body` + second identical `fld 0.0f; fld uv; fucompp` block remains an
artefact of the original whole-program build rather than of a source spelling.

**Deltas #3/#4 (the stored matrix's addressing).** The wave-16 note's suggestion
works: declaring the entity's three stored matrices as members of a typed view
(`local_transform` +0x23C, `world_transform` +0x27C, `texture_transform` +0x2BC)
and writing `view->world_transform = view->local_transform;
view->world_transform.m[0] *= entity->scale_x; view->world_transform.m[5] *=
entity->scale_y;` reproduces retail's forms exactly — the explicit
`fmul [ebp+0x0]` for `m[0]` and the entity-based `fmul [ebx+0x290]` for `m[5]` —
in the whole-program cluster even though the plain oracle emits the shorter
`[ebx]`/`[ebx+0x14]` forms. That is the whole +8 bytes (896 → 902) and removes
both deltas; the three `asm_D3DXMatrixMultiply_004521b2` calls take the same
expression (`&view->world_transform`) so the copy's `lea`/`rep movs` is unchanged.

## What would make the region exact

1. The remaining byte of group A: the anchor above earns `(entity EBX, manager
   [esp+8], RET 4)`, so the caller pushes the manager; retail's callee takes the
   manager in **EAX** and the entity in **EBX**. Every shape tried that gave the
   manager EAX (manager read-and-consumed before the first call, or the faithful
   0x4423E0 body) took the entity out of EBX (EAX, ECX, ESI or EDI), and every
   shape that gave the entity EBX put the manager on the stack. The pair
   `(EBX, EAX)` — the one retail's own build of 0x4423E0 has — was not reached by
   any of the thirty anchor bodies tried; a body that forces the entity's home to
   EBX through a *second* compiled consumer (an EBX sink) is the next thing to try.
2. Groups B/C and D: with twenty spellings screened for D and four for B/C,
   both look like original-build artefacts rather than source properties; if so
   the region can never be byte-exact and should stay `asm`.
