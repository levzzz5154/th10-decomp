## What the region is

`AnimationPool::Allocate` is the animation manager's object-pool allocator; all
twelve create-family members call it as `mov esi,[data_00491C10]; call
0x449950`. The manager owns

| offset | meaning |
| --- | --- |
| `+0x68` | 4096 slots of `Entity` (stride 0x3AC) |
| `+0x3AC068` | one busy byte per slot |
| `+0x3AD068` | the ring cursor |

The body: take `slot = cursor` and `object = &slots[slot]`; if that slot is
busy, advance the cursor once, publish it, take `&slots[next]`, and if *that*
slot is busy too fall back to the heap (`operator new(0x3AC)` →
`Entity_Constructor` → `Entity_Init`); otherwise mark the found slot busy; then
advance and publish the cursor once more and return the object. `Entity_Init` is
the region landed this wave as `src/game/entity_initialize_00401de0.cpp`, and
`Entity_Constructor` is the landed `?Entity_Constructor@@YIPAUEntity@@PAU1@@Z`
at `0x00402050` — both reached as ordinary bound callees.

Retail's modulo is the signed `% 4096` shape (`inc / and 0x80000FFF / jns / dec /
or 0xFFFFF000 / inc`), and both `0x449985` and the tail re-read the cursor from
the manager, which is why the model stores `slot` back before the second probe
and re-reads `next_slot` in the tail instead of reusing the local.

## The one shape insight: the object's production register

Retail's heap path is

```asm
4499a7  test eax,eax / je 4499bd
4499ab  mov  ecx,eax
4499ad  call 0x402050                 ; Entity_Constructor
4499b2  mov  edx,eax                  ; the initializer's argument
4499b4  mov  edi,eax                  ; the live result's home (returned at 4499ed)
4499b6  call 0x401de0
4499bd  xor  eax,eax / mov edx,eax / mov edi,eax   ; the null path
```

Both copies read the object's *production register* (EAX), the argument first.
Writing the heap path as "assign to the result variable, then pass that
variable" cannot produce it: the backend coalesces the argument with the home
and emits `mov edi,eax / mov edx,edi` (argument reloaded from EDI), and the null
arm shrinks from `xor eax,eax / mov edx,eax / mov edi,eax` (6 bytes) to
`xor edi,edi / mov edx,edi` (4 bytes) — the two-byte deficit. Splitting the heap
path into a temporary that is *consumed* by the initializer plus a separate
assignment to the live result variable

```cpp
Entity* created = block != 0 ? Entity_Constructor(block) : (Entity*)0;
object = created;
Entity_Init(0, created);
```

leaves `created` in EAX (its live range ends at the call) and `object` in the
callee-saved EDI (it is returned), so retail's two independent copies out of EAX
— argument first, home second — fall out of the scheduler unchanged. This is the
same lever wave 10's `argument_copy_order_residual_00401110_00405620_0040d530_wave10.md`
measures from the other side: that note's rule is about two *parameter* homes,
while here only one of the two copies targets a parameter register, so the copies
have independent sources and the toolkit's descending-home tie-break does not
apply.

Shapes tried (all with the manager already in ESI and the `% 4096` arithmetic
exact; emitted size against the declared 161):

// manager's object-pool allocator.  Every create family in the manager
// (0x00448D00/0x00448E30/0x00448F60/0x00449090, 0x00448D50/0x00448E80/
// 0x00448FB0/0x004490E0, 0x00448DB0/0x00448EE0/0x00449010/0x00449140) reaches
// it as `mov esi,[data_00491C10]; call 0x449950`, i.e. the manager arrives in
// ESI and the result in EAX.
//
// The manager owns a 0x1000-entry ring of Entity-sized (0x3AC) slots at +0x68,
// a per-slot busy byte array at +0x3AC068 and the ring cursor at +0x3AD068.
// Allocate starts at the cursor: a free slot is marked busy and handed out; a
// busy slot advances the cursor once, and only if the successor is busy too is
// a fresh 0x3AC-byte object taken from the heap and run through the landed
// Entity_Constructor (0x00402050) and Entity_Init (0x00401DE0).  Either way the
// tail advances the cursor past the returned slot, so the ring rotates.
//
// Retail's modulo is the signed `% 4096` shape (inc/and 0x80000FFF/jns/dec/or
// 0xFFFFF000/inc); the cursor is re-read from the manager in the tail, which is
// why the source stores `slot` back before the second probe and re-reads
// `next_slot` at the end rather than reusing the local.
//
// The heap path keeps two variables: the constructed object in `block`'s
// ternary result (`created`) and the value returned through `object`.  Retail
// emits `mov edx,eax / mov edi,eax` - the initializer's argument and the
// result home both copied out of the object's production register - and only
// the separate temporary reproduces that; assigning straight into `object` and
// passing `object` makes the backend copy the argument out of the home
// register instead (`mov edi,eax / mov edx,edi`, two bytes short).
//
// The manager's registers are not expressible in a plain translation unit, so
// the body is compiled in the native-LTCG cluster
// layout/ltcg/anim_pool_alloc_00449950.json, whose driver also carries the
// compiled ABI anchor for the Entity_Init call.
#include "th10/game/entity.hpp"

void* __cdecl operator new(unsigned int size);
Entity* __fastcall Entity_Constructor(Entity* self);

struct AnimationPool {
    char header[0x68];
    Entity objects[4096];
    unsigned char occupied[4096];
    int next_slot;
    __declspec(noinline) Entity* Allocate();
};

#pragma code_seg(".text$03allocate")
Entity* AnimationPool::Allocate() {
    int slot = next_slot;
    Entity* object = &objects[slot];
    if (occupied[slot]) {
        slot = (slot + 1) % 4096;
        next_slot = slot;
        object = &objects[slot];
        if (occupied[slot]) {
            Entity* block = (Entity*)operator new(sizeof(Entity));
            Entity* created = block != 0 ? Entity_Constructor(block) : (Entity*)0;
            object = created;
            Entity_Init(0, created);
        } else {
            occupied[slot] = 1;
        }
    } else {
        occupied[slot] = 1;
    }
    next_slot = (next_slot + 1) % 4096;
    return object;
}
#pragma code_seg()
