## Why no declared binding can work

`0x449950` resumes with `this` in ESI, `0x43E710` with `object` in EAX and `index` in
EBX, `0x4489D0` with `object` in EBX and `out` in EAX. MSVC x86 has only ECX and EDX
as parameter registers (`__fastcall`, `__thiscall`); ESI/EBX/EAX are never argument
registers of any declarable convention, and the `/GL` pass only re-conventions
functions compiled into the same LTCG scope. Measured to confirm the mechanism, not
just assert it:

| callee binding | emitted size | differing (emitted window) | first |
|---|---:|---:|---:|
| `__cdecl` free functions (the model above; the manifest's own spellings) | 93 | 84 | `+0x00` |
| `__thiscall` members (`manager->CreateObject()`, `object->LoadScript()`, `manager->RegisterPrimaryBack()`) | 91 | 82 | `+0x01` |
| `__fastcall` (manager->ECX, out->EDX, object/index->stack) | 89 | 80 | `+0x00` |

(Counted over the full 95-byte retail window every variant differs in 86 bytes; the
window counts above are the honest ones the probe reports.)

The `__fastcall` build moves the values into ECX/EDX and never into ESI/EAX/EBX, and
it is *worse* than `__cdecl` because retail's stack shape (three stack arguments plus
EDI) is what `__cdecl` already produces.

The *spelling* of the binding is not what blocks either variant, and saying so would
be wrong: the cluster exports its validated bodies as a relocation-free byte image
(`normalization.regions[].relocation_count == 0` in every build above; call
displacements are resolved in the cluster's own `/LTCG` link through
`absolute_symbols`), so the outer link copies the bytes verbatim and never has to
resolve the callee name. The manifest's spellings for the three callees are cdecl
only

```
0x00449950 ['_asm_FUN_00449950_00449950']
0x0043E710 ['_asm_AnimationObject_LoadScript_0043e710']
0x004489D0 ['_asm_AnimationManager_RegisterPrimaryBack_004489d0']
```

but that only happens to match what `__cdecl` needs. A `__fastcall` binding is
linkable; it is simply 89 bytes of the wrong registers instead of 93.

## Shapes tried

Every shape was built as a native-LTCG cluster in the throwaway copy; the emitted
body was read back out of `cluster.exe` at `0x448D50` and compared with retail.

1. four-parameter `__stdcall` free function, `__cdecl`-bound callees (the model
   above) - 93 bytes, 84 differing; entry convention and position copy correct.
   The same body reaches 89 bytes with `__fastcall` bindings (80 differing, first
   `+0x00`: `mov 0x491c10,%esi` becomes a push of the manager) and 91 bytes with
   `__thiscall` members (82 differing, first `+0x01`: the manager is parked in EBX
   and copied to ECX at each call). All three miss; none is exact.
2. the same body with the manager held in an explicit local across both calls
   (`void* manager = data_00491c10;`) instead of re-read from the global - 91
   bytes, 82 differing, first `+0x01`: the manager is parked in EBX (`push %ebx`,
   `mov 0x491c10,%ebx`) and pushed per call. The reload form stays closer.
3. `0x40C540`'s model with `void* handle = 0;` and with an explicit `void** slot`
   - the caller grows (83 and 77 bytes); only the wave 7 shape keeps 75.
4. `0x40C540`'s model using the out slot directly (`assign_direct`) - 77 bytes.
5. two-region cluster with the same four-argument model and the `0x40C540` model -
   identical 93-byte body (md5 `dc8ac31d6dc14655aa69bc001818a242`, the same as the
   standalone build), so the result does not depend on the caller.
6. three contexts for the two-region cluster (array loop, single call, two calls per
   thread) - the 93-byte body and the `0x40C540` 2-byte residual are identical in
   all three.

## What would land this region

One cluster holding the four remaining closure regions co-compiled as byte-exact C++
plus this model (and, if `0x40C540` is to convert with it, that model too). This
model needs no change: its entry convention already reproduces retail, and with the
callees' real conventions the seven deltas above are exactly the register setup the
