Retail's callers are one tail-call thunk and the interpreter. The thunk `0x00412A70`
(`mov eax,[eax+14D8h]; mov eax,[eax+4]; jmp 450070`) turns the interpreter in EAX
into the **VM** in EAX and leaves the operand in **ECX**; `0x40C660` and the nine
call sites in `ecl_vm.cpp` / `ecl_core_interpreter.cpp` assemble the same pair. So
the region enters with **EAX = VM, CL = index** and returns `float*` in EAX with a
plain `ret` — a pair only a native `/LTCG` link chooses, exactly like the integer
sibling at `0x00412A10` (EAX = interpreter, ECX = index). Modelling the function as
a **member of the VM** and giving the driver the same array-walk context shape the
integer sibling uses reproduced that ABI without any context tuning.

## The model (verbatim, as measured)

`src/script/ecl_resolve_float_destination_00450070.cpp`:

```cpp
// 0x00450070..0x004500CC: hand back where the float variable selected by the
// index in CL lives. The variable table marks the live slots with a 16-bit
// mask; a slot's displacement is stored as a float and is either a
// non-negative offset into the pooled frame or a negative one the value owner
// resolves through its fourth virtual. The VM arrives in EAX and the index in
// ECX, a convention only a native LTCG link chooses, so this region is
// compiled as a cluster.

struct EclVarTable_00450070 {
    unsigned char pad_000[8];
    unsigned short valid_mask;  // +0x0008
    unsigned char pad_00a[6];
    float displacements[1];     // +0x0010
};

struct EclValueOwner_00450070 {
    virtual void Reserved0();
    virtual void Reserved1();
    virtual void Reserved2();
    virtual void Reserved3();
    virtual float* ResolveExternalFloat(int displacement);
};

struct EclFrame_00450070 {
    unsigned char pad_000[0x1004];
    int frame_base;                 // +0x1004
    unsigned char pad_1008[4];
    EclValueOwner_00450070* owner;  // +0x100C
};

struct EclVm_00450070 {
    void* field_000;
    EclVarTable_00450070* table;  // +0x0004
    EclFrame_00450070 frame;      // +0x0008
    __declspec(noinline) float* ResolveFloatDestination(int index);
};

#pragma code_seg(".text$01accessor")
float* EclVm_00450070::ResolveFloatDestination(int index) {
    if (table->valid_mask & (1 << index)) {
        const float& displacement = table->displacements[index];
        if (displacement >= 0.0f) {
            EclFrame_00450070* frame = &this->frame;
            return (float*)((char*)frame + frame->frame_base + (int)displacement);
        }
        return this->frame.owner->ResolveExternalFloat((int)displacement);
    }
    return 0;
}
#pragma code_seg()
```

## What decided the bytes

- **The convention is inherited, not argued.** The member form plus the
  array-walking context (below) is the same combination the integer sibling uses,
  and the whole-program pass made the identical choice: `this` in EAX, the operand
  in ECX. No context variant was needed.
- **The float slot is a *float*, and clearing the sign needs x87.** `raw >= 0.0f`
  with `raw` used again in both arms is what emits retail's
  `fld / fcomp [zero] / fld / fnstsw / test ah,1 / jne`: the first load feeds the
  compare, the compare pops ST(0), and the reload feeds the arm. Spelling the test
  as `if (!(displacement < 0.0f))` was not needed; the `>=` form puts the negative
  arm out of line after the positive one, which is retail's `jne 4500b2`.
- **`const float&` into the table, not a `float` local.** The wave-5 note on
  `0x00412A10` showed that an lvalue reference into the table makes c2 order the
  adds *displacement first, frame second*; the value-local spelling reorders them.
  The same spelling here gives retail's `add eax,ecx` / `add eax,esi` order, and it
  is what keeps the two `fld dword [edx+ecx*4+10h]` loads (retail's re-read after
  the compare) instead of one.
- **The positive arm adds the frame *last*.** `return (float*)((char*)frame +
  frame->frame_base + (int)displacement)` reaches c2 as `(frame_base + offset) +
  frame`, i.e. retail's `mov eax,[esi+1004h]` / `add eax,ecx` / `add eax,esi`.
  `add esi,8` materialises `&vm->frame` before the `__ftol2` call because the frame
  expression is pointer-valued and c2 hoists it.
- **`__ftol2` is bound absolutely, not linked.** `(int)displacement` emits
  `call __ftol2`; the cluster link is `/NODEFAULTLIB`, so the layout binds
  `__ftol2` to retail's `0x463B2C` as `relative_code`, plus `__fltused` as
  `metadata` because the body is float-bearing. `0x463B2C` is the CRT truncating
  float→int cast (`fistpll`/`fildll`/two-way `fsubrp` fixup).
- **The pooled `0.0f` is aliased to retail's own pool slot.** `fcomp dword
  [470b04h]` is an absolute operand pointing at retail's `0.0f` in `.rdata`. The
  compiler pools a copy of `__real@00000000` wherever the cluster's `.rdata` lands,
  which is not `0x470B04`, so `constant_aliases` binds the compiler's own literal
  symbol at `0x00470B04` (value `0.0`); the link tolerates the discarded pooled
  copy (LNK4006, asserted by the loader) and the surviving definition is the
  absolute one, which is what the emitted body references. No byte is patched.
- **The owner interface has four virtuals ahead of the resolver.** Retail calls
  `dword ptr [edi+10h]`, i.e. vtable slot 4, and passes the owner in ECX with the
  truncated displacement on the stack (thiscall). The model therefore declares four
  reserved virtuals before `ResolveExternalFloat(int)`; declaring only the resolver
  would have emitted `[edi+0]`. The receiver (`this->frame.owner`) and its vtable are
  loaded *before* the `__ftol2` call, which is what retail does and what c2 does for
  a virtual call whose argument needs a helper call.

## Regions this touches

- **`0x00412A70` (14 bytes, `src/unidentified/FUN_00412a70_00412a70.cpp`)** and
  **`0x0040C660`** are the interpreter→VM tail thunks into this region. They are
  not unblocked by this landing (their `jmp` operand already binds to `0x450070`),
  but their target is now a compiler-visible definition, so either can be
  recompiled as a real tail call instead of inline assembly.
- **`0x0044E1A0` (7,020 bytes, `src/script/ecl_core_interpreter.cpp`)** holds nine
  of the call sites (`0x44E4F6`, `0x44F984`, `0x44F999`, `0x44F9D0`, `0x44F9F2`,
  `0x44FA61`) and is still an asm region; with this body landed it can co-compile
  `0x450070` as an ABI anchor (levers 1-2 of the wave contract) rather than
  inventing a convention for the call. This landing does not by itself unblock it.
- **`0x00450030` (58 bytes)**, **`0x0044FE40` (183 bytes)** and **`0x0044FF80`
  (171 bytes)** — the remaining ECL resolvers — now have a third independent
  measurement of the frame expression. `0x450070` pins, in one exact body:
  `vm->table` at `+0x0004`, the valid mask at table `+0x0008`, the per-variable
  floats at table `+0x0010` scaled by 4, the frame by value at `vm+0x0008`,
  `frame_base` at frame `+0x1004` and the value owner at frame `+0x100C`, with the
  address assembled as *(frame + frame_base + displacement)* in that order.
  `0x0044FE40` in particular is the same query one level up (interpreter instead
  of VM, per the `0x412A60` thunk `mov eax,[eax+14D8h]; mov eax,[eax+4]; jmp
  44fe40`), so it should take this model with `this` = VM reached through
  `handle->vm` exactly as `0x00412A10` does.
