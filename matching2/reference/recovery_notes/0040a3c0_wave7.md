## Disposition

**NOT EXACT — not landed.** The source-level model is complete and its *shape* is
right, but the region is blocked on two callees whose argument registers no C++
declaration can express:

| callee | bytes | retail ABI | why a declaration cannot reach it |
| --- | ---: | --- | --- |
| `0x0040A040` | 234 | object in **EDX**, ECX *unused*, result in EAX, plain RET | `__fastcall(void *, T *)` fixes EDX, but the caller then materialises the dead ECX slot (`xor ecx,ecx`, +2 bytes); only callee-visible IL drops it |
| `0x0040A130` | 106 | object in **EBX** (no stack argument), result in EAX, plain RET | no MSVC declaration passes an argument in EBX; only a co-compiled callee gets EBX from the whole-program pass |
| `0x0040A1A0` | 412 | object on the stack, `ret 4` | **not a blocker** — a plain `__stdcall(T *)` declaration reproduces it |

Both blockers are the `0x0041C030` situation recorded in
[`0041c290_wave5.md`](0041c290_wave5.md) (object in EDX with an unused ECX slot)
and in [`ltcg_cluster_lessons.md`](ltcg_cluster_lessons.md) lesson 12 (receiver in
a register MSVC never assigns). Both callees are **still assembly regions**
(`src/unidentified/FUN_0040a040_0040a040.cpp`, `src/unidentified/FUN_0040a130_0040a130.cpp`),
so co-compiling them means recovering them as C++ first; a cluster cannot carry
them as assembly, because `load_cluster` requires every selected function's region
to be `kind: "semantic"` and every selected body is exported into the image.

## What retail does, and what the calls need

Retail's body (annotated, `mov` targets abbreviated):

```asm
53            push ebx
68 88060000   push 688h
e8 ...        call 0x452493          ; operator new(0x688), __cdecl
83 c4 04      add  esp,4
85 c0         test eax,eax

8b d0         mov  edx,eax           ; initializer argument in EDX, ECX untouched
e8 ...        call 0x40a040
8b d8         mov  ebx,eax           ; the state's home is EBX for the whole body
eb 02         jmp  0x40a3df
33 db         xor  ebx,ebx
e8 ...        call 0x40a130          ; registration receives the object in EBX

85 db         test ebx,ebx

5b            pop  ebx

8b c3         mov  eax,ebx
5b            pop  ebx

```

* `0x0040A130` itself reads **EBX** from its caller (`mov [esi+0x20],ebx`,
  `mov [ebx+8],esi`, `mov [ebx+0xc],esi`) and never sets it, so EBX is a
  whole-program agreement: the state's home is EBX *because* that callee takes it
  in EBX. The same function's own locals are ESI (the task) and EDI (the
  registration priority, 5 and 0x27), which is what leaves EBX for the receiver.
* `0x0040A040` reads **EDX** as its base throughout its 234 bytes, uses EAX as a
  zero scratch, and returns EDX in EAX.
* `0x0040A1A0` reads its argument from `[esp+4]` and ends `ret 4`.

Retail's callers of this region: the disassembly index records **no** reference to
`0x0040A3C0` (neither a call nor a data-table entry in
`decompiled/ghidra_augmented/`), so no caller-side constraint exists beyond the
region's own `ret`; it starts `push ebx` with no live-in register.

## Shapes tried (all measured against the 67 retail bytes)

The model source is the same in every shape; only the callee declarations and the
compilation path change. `differing` counts every byte that is not retail's.

| # | shape | emitted | differing | 0x0040A040 call site | 0x0040A130 call site | state home |
| -: | --- | ---: | ---: | --- | --- | --- |
| 1 | plain translation unit, callees opaque (`--source` probe) | **69** | 34 | `mov edx,eax; xor ecx,ecx; call` | `call` (no setup) | ESI |
| 2 | cluster, both callees opaque | 70 | 49 | `mov edx,eax; xor ecx,ecx; call` | `push esi; call` (stack arg) | ESI |
| 3 | cluster, `0x0040A040` co-compiled as a **naked asm** body declared `__fastcall(void *,T *)` | 70 | 49 | `mov edx,eax; xor ecx,ecx; call` | `push esi; call` | ESI |
| 4 | cluster, `0x0040A040` co-compiled as a **C++ model** (IL visible, retail-shaped 234-byte body) | 68 | 37 | **`mov edx,eax; call`** | `push esi; call` | ESI |
| 5 | cluster, both callees co-compiled as throwaway C++ models | **67** | 21 | `call` (pass moved the receiver to EAX) | `mov eax,esi; call` (receiver EAX) | ESI |
| 6 | cluster, both callees co-compiled, retail-shaped bodies | 65 | 48 | `call` (receiver EAX) | `call` (pass chose EDI) | EDI |

Shape 1 is the honest single-unit result: 69 bytes against retail's 67, the extra
`xor ecx,ecx` at `+0x12` (`33 c9`, retail has `8b d0 e8 ...` there), and the
remaining 32 differing bytes are the ESI↔EBX register byte in
`push/pop/mov/test`, i.e. the same instructions with a different callee-saved
register.

Shape 4 is the decisive measurement: with the initializer's **IL** in the same
`/GL` scope and a retail-shaped body, the pass drops the dead ECX argument and
keeps `mov edx,eax; call 0x0040A040` — bytes `+0x01..+0x19` are byte-identical to
retail, including that call. Only the state's home (ESI) and the registration
call's stack argument are left, because `0x0040A130` is still opaque there.

Shape 3 shows a naked body is **not** enough: `/GL` leaves the declared convention
of a `__declspec(naked)` function untouched, so the dead ECX argument is
materialised exactly as for a declaration-only callee. The elimination needs IL.

Shape 5 shows that co-compiling *any* body is not enough either: with small
throwaway bodies the pass re-chooses both receivers to EAX (the register the value
already occupies) and keeps the home in ESI. Shape 6 shows the pass will move a
receiver into a callee-saved register (EDI) when the body holds it across calls —
so EBX is reachable, but it comes from the callee's own allocation, which is why
the callee must be modelled faithfully, and its own callers (the scheduler
registrations, ESI/EDI) must be visible too.

## The route to EXACT (validated, not yet executed)

1. Model `0x0040A130` (106 bytes) as C++ and co-compile it. Its body holds the
   state across two `SchedulerTask` creations and two registrations whose own
   conventions are *task in ESI, priority in EDI, scheduler on the stack*
   (`Scheduler_RegisterPrimary` `0x00449AE0`, `Scheduler_RegisterSecondary`
   `0x00449B70`; both `ret 4`). Those conventions already exist as models in
   `src/game/scheduler_tasks.cpp`, which is owned by
   `layout/ltcg/bullet_manager_load_scripts_0040ae70.json` — so this landing is a
   **merge into that cluster** (lesson 5), not a new cluster: it is the only link
   in which the scheduler conventions, and therefore EBX for the state, are
   derivable.
2. Model `0x0040A040` (234 bytes) as C++ with the `__fastcall(void *, T *)`
   declaration of `score_object_initialize_0041c030.cpp`, so its base is EDX by
   declaration and the pass only has to drop the dead ECX slot. A first draft of
   this model already reproduces retail's register use (EDX base, EAX zero
   scratch, ESI/EDI scratch, `mov eax,edx; ret`) and its first 12 instructions
   (0x24 bytes) are byte-identical in the cluster; the residue is statement
   scheduling — the draft emits 295 bytes in the cluster against retail's 234
   because MSVC groups the same-valued stores instead of keeping retail's
   interleaving, which is the one open modelling question for this region.
3. Merge the three units into the scheduler cluster with an
   `apply_package.py` payload (the `results10/ScoreManagerCreate` shape), because
   that cluster legitimately claims more than one source.
4. The region then flips to `semantic` and this source lands unchanged.

## Registers retail's callers use, and what the emitted body keeps

* There is no direct caller; the region is a factory reached indirectly, so its own
  ABI is `__cdecl`, argument-free, result in EAX, plain `ret` — **kept** by every
  shape.
* `0x0040A040` is reached with the object in **EDX** and ECX free. Shape 4 keeps
  that exactly (`mov edx,eax; call`); shapes 1-3 pay the extra `xor ecx,ecx`;
  shapes 5-6 lose it to EAX because the callee body was not retail-shaped.
* `0x0040A130` is reached with the object in **EBX** and nothing on the stack.
  No measured shape keeps it; the pass needs the callee's own body (and the
  scheduler conventions its body depends on) in the same `/GL` link.
* `0x0040A1A0` is reached with the object on the stack and `ret 4` — **kept** by
  the `__stdcall` declaration in every shape.
* The state's home: retail **EBX**, shapes 1-5 **ESI**, shape 6 **EDI**. The home
  follows the registration callee's receiver, so it becomes EBX exactly when that
  callee is co-compiled with a retail-shaped body inside the scheduler cluster.
