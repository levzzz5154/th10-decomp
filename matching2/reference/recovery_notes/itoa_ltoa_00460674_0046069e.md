# `_itoa` and `_ltoa` semantic models

The manifest rows at `0x00460674` (42 bytes) and `0x0046069E` (39 bytes) now
use ordinary C++ and are marked `semantic`. Their original ASM records remain
in `previous_record`, and the linker symbol names are unchanged. The shared
header records their cdecl signatures.

## Ghidra evidence

Ghidra identifies both as VS 2003 CRT formatting functions:

- `0x00460674`: `char* __cdecl __itoa(int value, char* destination, int radix)`.
  Its body ends in a plain `RET`; the one direct caller is at `0x0045CBF2` in
  `FUN_0045CA50`.
- `0x0046069E`: `char* __cdecl __ltoa(long value, char* destination, int radix)`.
  Its body ends in a plain `RET`; Ghidra reports no references to this entry in
  the current binary.

Both wrappers originally passed the value in EAX, destination in ECX, radix
and a negative flag on the stack to `xtoa` at `0x00460636`. That helper has a
private register interface and remains ASM. The C++ wrappers implement the
formatting directly through their standard stack interfaces.

## Recovered behavior

The functions emit the value in the requested radix, produce at least one
digit for zero, use lowercase letters above digit nine, and append a NUL byte.
Only base 10 prints a leading minus sign. Negative base-10 values are converted
to their unsigned magnitude with 32-bit wraparound, which handles `INT_MIN` as
retail does. `_ltoa` delegates to `_itoa`; both integer types are 32-bit on
this x86 target, and their Ghidra control flow differs only in how the sign
flag is computed.

## Limits

These are behavioral models; their emitted byte sequences have not been
compared with retail. Inputs outside the CRT's valid radix range are outside
the C contract. No build, probe, or test was run.
