## The answer in one paragraph

`0x00443290` is recovered **EXACT (486/486, 0 differing bytes)**. It is the
missing body of the render-batch cluster, `BuildAnchoredQuad_00443290`
(`_EntityDraw_00443290@8`, entity in EAX, manager on the stack, `RET 4`), so the
dispatcher's case-2 ABI anchor at its address is dropped and `0x004451C0` keeps
its 216 bytes. The eight bytes that stood in the way (four load-order pairs of
the y switch) are fixed by **writing each y edge as its own stepwise
accumulation** instead of one expression per edge. The rule the earlier attempt
recorded is real but incomplete: it describes what the compiler does to a
*shared* pair node, and a shared node cannot be spelled into retail's order -
the sharing itself has to go.

## The eight bytes, and the lever that removes them

Retail's y switch (four chains, `0x350` = `render_offset.y`, `0x338` =
`base_position.y`, `0x344` = `position.y`):

```text
0x00443394  fld [eax+0x350] ; fadd [eax+0x338] ; fadd [eax+0x344] ; fsub [esp]      case 2 near
0x004433b5  fld [eax+0x350] ; fadd [eax+0x338] ; fadd [eax+0x344]                  case 2 far
0x004433c9  fld [eax+0x350] ; fadd [eax+0x338] ; fadd [eax+0x344]                  case 1 near
0x004433e7  fld [eax+0x350] ; fadd [eax+0x338] ; fadd [esp] ; fadd [eax+0x344]     case 1 far
```

The model emitted the first two loads in the other order (`0x338`, then `0x350`)
in all four chains. What the sweep of wave 14 could not see is that the order is
a property of the **pair node's use count**, not of the sum's spelling:

| context | shape | first loads emitted |
| --- | --- | --- |
| isolated TU, pair used once | `g = (R + B) + P;` | `0x350, 0x338, 0x344` (= retail) |
| isolated TU, pair used twice | `g = (R + B) + P; g2 = ((R + B) + h) + P;` | `0x338, 0x350, 0x344` |
| whole model (wave 14's baseline) | edges as `(R+B)+P` and `((R+B)+height)+P` | `0x338, 0x350, …` |
| whole model, linear edges | edges as `R+B+P` and `R+B+height+P` | `0x344, 0x350, 0x338` |
| whole model, materialised pair | `float base = R + B;` per case | reuses `ST(0)` (`fld st(0)`), frame changes |
| whole model, stepwise accumulator | this landing | `0x350, 0x338, 0x344` in all four chains |

Twelve spellings were swept for the case-1 near edge alone, keeping the rest of
the body (pair `(R+B)+P`, `(B+R)+P`, nested `R+(B+P)` and `P+(R+B)`, `(R+P)+B`,
`(P+B)+R`, the three linear permutations, `R*1.0f+B+P`, `1.0f*(R+B)+P`,
`(R+B)*1.0f+P`): every one keeps `0x338, 0x350` as its first two loads, because
the pair is shared with the far edge of the same case - sharing, not spelling,
decides the order. That is also why wave 14's linear-permutation sweep came out
identical for all six permutations.

The fix is to give every chain a **single-use accumulator**, which is what the
twins and the honest source style look like anyway:

```cpp
        float near = entity->render_offset.y;
        near = near + entity->base_position.y;
        near = near + entity->position.y;
        data_004978c0[0].y = data_004978c0[1].y = near;
```

Now no pair node has a second use, each statement's result is folded into the
next, and the emitted order is the source order - retail's. The far edge
adds `height` before `position.y`, reproducing retail's `0x350, 0x338, height,
0x344`; case 2's near edge subtracts `height` from its own accumulator to get
`fsub [esp]` at the end of the chain. The frame (`sub esp,8`, `height` at
`[esp]`, `half_height` at `[esp+4]`), the x switch, the case-0 chain, the z
placement and the `push 0; call 0x00442670; add esp,8; ret 4` tail were already
retail's and do not move.

## What this unblocks

* The region itself: 486 bytes move from `asm` to `semantic`, and the four
  load-order pairs of the y switch are retail's.
* The dispatcher's case 2 is a definition. Five of its ten cases (1, 2, 3, 4, 9)
  are definitions now; the three that still keep an anchor at their callee's
  address are case 0 (`0x00443080`, 515 bytes `asm`), case 7 (`0x004445C0`, 402
  bytes `asm`) and case 8 (`0x00444760`, 929 bytes `asm`).
* **No other region is unblocked.** `0x00443080` is the third body of this
  family but is *not* the same shape: its receiver is ESI, its four y chains are
  emitted `0x344, 0x350, 0x338` (`P, R, B`), and it reads `0x354`, a byte this
  body never touches ([INFERENCE]: a different source spelling of the same
  structure, and the stepwise-accumulation lever above is available to whoever
  takes it). `0x004436C0`/`0x00443910` are unaffected (both still EXACT).
