## What the two instructions actually are

Both builds execute the same 111-instruction stream in the same order; the
fadd's memory operand is the same *slot* (`width`, the first spill) and it is
addressed relative to whatever `esp` is at that point. The `sub esp,8` argument
area exists in both; only the **release's slot in the schedule** differs, and the
fadd's offset follows from the release's position:

```text
retail x-case-0, 0x443149..0x443166            model x-case-0
fstp dword [0x4978f8]                          fstp dword [0x4978f8]
mov  eax,[0x4978f8]                            mov  eax,[0x4978f8]
fld  dword [0x4978f8]                          fld  dword [0x4978f8]
fadd dword [esp+0x8]   ; width, pre-release    add  esp,0x8
add  esp,0x8                                   fadd dword [esp]   ; width, post-release
mov  dword [0x4978c0],eax                      mov  dword [0x4978c0],eax
```

Our build already reproduces retail's *relative* order of the fadd and the GPR
sink store in **both** floor blocks (x: fadd before the store; y: store before
the fadd). The only difference is that retail's x block sits the release
*between* the fadd and the store, and our build sits it one slot earlier.

Structural finding that explains the y block (and shows the x block has no such
anchor): the y-case-1 far edge **tail-merges into the y-case-0's `+ height`** —
`0x4431e6..0x4431f8` computes `position.y + render_offset.y + base_position.y`
and jumps to `0x443236`, the `fadd [esp+0x4]` that the y-case-0 path also reaches
(y-case-2 jumps past it to `0x44323a`) — so the `add esp,0x8` at `0x44322d` is
the *last instruction of its block* and its fadd lives in the shared join block
after it. The x switch's join (`0x44316b`, `fst [0x497914]` / `fstp [0x4978dc]`)
is a plain store pair shared by cases 1/2 and case 0, and case 0's own
`mov [0x4978c0],eax` sits inside the block, so its release has one more legal
slot and the scheduler chose differently.

Corpus check (`matching2/msvc/src/**/*.cpp`, the retail asm, label-aware): the
*adjacent* form `fadd dword ptr [esp+N]` immediately followed by `add esp,8`
occurs **exactly once** in the entire game — this region's `0x44315f` — and
`add esp,8` immediately followed by a frame-reading fp instruction occurs **zero**
times, i.e. the arrangement our model emits is not attested anywhere in retail,
while retail's is a one-off. That is consistent with a scheduler tie-break
rather than a source-controlled shape.

**Verdict: a definitive negative.** Across the free-shape space of the x block
(4 distinct byte-identical spellings, including one that changes the block's IR
order), four free IR-order changes in the other blocks and their combinations,
the module-shape levers (address, a dummy function, a second caller) and the
statement-permutation and spelling screens, the release never leaves the slot
before the fadd. Since every free variant emits the identical 111-instruction
stream, the scheduler is being fed the same list and the decision is a tie-break,
not a shape the source controls. The region stays assembly; the dispatcher's
case-0 anchor (`EntityDraw_00443080_abi_anchor`, 56 bytes, `layout/ltcg/
render_batch_context.cpp`) stays as it is and the dispatcher keeps its exact 216
bytes.

//
// The third of the unrotated quad builders (0x00443290, and 0x004436C0/

// independently: (entity->flags >> 18) & 3 for x and (entity->flags >> 20) & 3

// addend of the far edge are swapped in the schedule (see 00443080_wave16.md).

                                                       AnimationManager_00442F50* manager) {
    float width = entity->sprite_width * entity->scale_x;
    float height = entity->sprite_height * entity->scale_y;

        data_004978c0[1].x = data_004978c0[3].x = data_004978c0[2].x + width;
