Cause of each: (1)-(4) and (8)-(10) are the **entry triple** — retail's head is
`push ebp; push esi; mov esi,ecx; push edi; mov edi,eax` (7 bytes) and this build
emits `push ebp; push edi; mov edi,eax` (4 bytes) because the resource arrives in
ESI instead of ECX, so there is no `mov esi,ecx` and no `push esi`/`pop esi`;
(5)-(7) are the same fact one level down: retail's flags scratch is ESI (the
resource's home, dead at that point) while this build still holds the resource in
ESI as the argument register and uses EAX as the scratch. Nothing else differs:
the two call targets, the 16-bit stores, the flags load/and/store *order*, the
single script-table reload, the shared element load for the base/cursor stores,
the whole frame-state block and the manager bump are byte-identical to retail.

Structural facts that had to be discovered for this and that any later attempt
should keep:

* **The flags clear must be a `volatile` read-modify-write.** With
  `object->AnimationFlags() &= ~1u;` MSVC emits the in-place `andl $imm,mem`
  (9 bytes, wrong shape) and, more importantly, the whole-program pass then
  picks a different entry triple; a `volatile uint32_t*` RMW forces retail's
  load/and/store shape and keeps EAX=object / EBX=index (167 → 125 differing on
  the same source, 173 aligned after the remaining fixes).
* **The first flags mask must be a named local written later**, i.e.
  `uint32_t mask = object->AnimationFlags() & 0xFFFFF9FFu; … object->AnimationFlags() = mask;`.
  As an in-place `&=`, MSVC folds it into `andl $imm,mem` and retail's hoisted
  load / deferred store (15 bytes at `0x43E72D..0x43E750`) is lost.
* **The call to `0x0043EE30` is stdcall.** Retail's site is `push edi; call`
  with no stack cleanup, so the declaration must be `__stdcall` (binding
  `_asm_FUN_0043ee30_0043ee30@4`); a `__cdecl` declaration adds a stray
  `add $4,%esp`.
* **The dead leading slot of `Entity_Init` must be given a live value.**
  `Entity_Init(0, object)` materialises `xor ecx,ecx` (2 bytes retail does not
  have, and the reason this build's tail needs `add $4,%esp`); passing the
  already-live script pointer into the slot the callee ignores removes it and
  reproduces retail's `mov edx,edi; call` exactly. (Retail leaves the script
  pointer in ECX there too — the slot is dead in the declaration.)

## The wall: the entry triple

Retail's incoming registers are a whole-program agreement; the pass re-decides
it from the callee's own IR and every lever tried here left it on a different
fixed point. Measured:

| lever | shapes | incoming triple |
|---|---|---|
| declaration | free `__stdcall` (both parameter orders), `__fastcall` (both orders), member of the object, member of the resource, wrapper over a `__forceinline` helper, 4-parameter form with a dead third slot | unchanged |
| body | two direct `resource->scripts[index]` evaluations; a fresh local; a `void**` local; an index local; guard orders; guard split; a `memset` loop; flags RMW via pointer/reference/union/volatile; `|=`/`&=` masks; `stop_frame` instead of the flags word; `FrameState&`/object/resource reference locals (the wave-9 recipe); `nullptr` for the dead slot | unchanged (only the flags-clear and mask forms moved it) |
| caller | array walk, pointer walk, two calls per iteration, nested loops, constant index, resource reloaded per call from a global chain (retail's `0x4093D0`/`0x413CB0`/`0x41402B` shapes), callers with 3-4 live values across the call, three retail-shaped *caller anchors* compiled into the same link | unchanged |
| link composition | 1, 3, 6 extra unrelated functions in the same `/GL` scope | unchanged |
| ABI anchors | the landed `0x401DE0` `Entity_Init` body as an anchor; a scaffolding anchor whose IL clobbers EDX | triple moves, never to retail's |

Anchor results, for the record: the landed anchor + a fresh-element local gives
`EAX=index, ECX=resource, EDX=object` (160 differing, resource slot correct);
an anchor whose IL clobbers EDX gives `EAX=object→EBX, ECX=resource→EDI,
EDX=index→ESI` (166). Neither reaches `EAX=object, ECX=resource, EBX=index`.

The one body statement that *does* move the fixed point is the flags clear:
removing it (semantically incomplete) gives `EAX=object, ESI=resource,
EBX=index` — retail except the resource's incoming register — and reordering it
after the call gives the same at 155 differing (with wrong byte order). So the
remaining residual is exactly "resource arrives in ESI instead of ECX", and it
is the same wall the wave-8 note records for `0x448D50`'s callees.

## Effect on 0x448D50

**0x448D50 does not land from this work.** A cluster holding the 448D50 wave-8
model plus this region's model cannot produce the retail pair: the pass chooses
this region's triple from its own IR and then re-shapes every caller around it,
so a compiled 448D50-model caller ends up loading `objects[slot]` into the
callee's register, copying the index and staging the resource where the callee
wants it — a self-consistent agreement that is not retail's. The 448D50 model's
own `mov ecx,[esp+10h] / mov eax,esi / mov ebx,[esp+18h]` call sequence only
appears once its callee actually wants EAX/ECX/EBX, which this region refuses to
do in a synthetic scope. The closure (0x449950, 0x43E710, 0x4489D0, 0x401DE0)
therefore stays open; 0x0043E710 remains the blocker it was.
