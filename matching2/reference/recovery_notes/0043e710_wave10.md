insensitive to everything this wave could vary (declaration shape, body shape,

## What the wave established

**1. Retail's internal allocation is what the pass picks on its own.** In every
one of the ~40 builds, the body used EDI for the object, ESI for the resource,
EBX for the index and EBP for the zero — retail's home registers — and the two
call displacements, the 16-bit stores and all the constant stores are retail's
bytes. What differs is only *which incoming register* carries each of the three
parameters.

**2. The incoming triple is a callee-IR fixed point, not a caller-driven one.**
Measured insensitivity:

| lever | shapes built | incoming triple |
|---|---|---|
| declaration | free `__stdcall` with (object, resource, index), with (resource, object, index), `__fastcall` with both orders, a member of the object, a member of the resource, a wrapper around a `__forceinline` internal helper, a 4-parameter form with a dead third slot | unchanged |
| body | two direct `resource->scripts[index]` evaluations; one fresh local after the call; a `void** scripts` local; an index local; the guard reordered; the guard's two tests separated; a `memset` loop instead of `memset`; the flags RMW via a pointer local, a reference local, a union member, `flags_early`, and `|=`/`&=` masks; `stop_frame` instead of the flags word; a `FrameState&`/object/resource reference-local rewrite (the wave-9 recipe); `nullptr` for the dead slot | unchanged |
| caller | array walk, pointer walk, two calls per iteration, nested loops, a constant index, the resource reloaded from a global chain each call (mimicking retail's `0x4093D0`, `0x413CB0`, `0x41402B`), a caller holding three/four live values across the call, and retail-shaped *caller anchors* compiled into the same link (`0x448D50`'s wave-8 model, and three loop shapes) | unchanged |
| link composition | 1, 3, 6 extra unrelated functions in the same `/GL` scope | unchanged |
| ABI anchors | the landed `0x401DE0` `Entity_Init` body as an anchor; a scaffolding `Entity_Init` anchor whose IL clobbers EDX | triple changes, see below |

**3. The one statement that moves it is the flags clear.** Ablating the model
group by group (all 203 bytes emitted in every case) shows a single trigger:

| body | incoming triple | differing bytes |
|---|---|---|
| full body | EAX=index, ECX=object, ESI=resource | 167 |
| minus the `AnimationFlags() &= ~1u` statement | **EAX=object, ESI=resource, EBX=index** | 157 |
| minus the `0043EE30` call + manager bump | EAX=object, ESI=resource, EBX=index | 143 |
| minus the `Entity_Init` call | EAX=object, ESI=resource, EBX=index | 195 |
| minus the frame-state block | EAX=object, ESI=resource, EBX=index | 190 |
| the flags clear *after* the call (byte order now wrong) | EAX=object, ESI=resource, EBX=index | 155 |
| a plain `AnimationFlags() = 0;` store instead of the RMW | EAX=object, ESI=resource, EBX=index | 161 |
| the RMW on a different word (`stop_frame = 0;`) | EAX=object, ESI=resource, EBX=index | 160 |

So an *RMW on the object immediately before the `0043EE30` call* flips the
fixed point from retail's `EAX/ECX/EBX` to `EAX/ECX/ESI`-family triples; a plain
store, a later RMW, or a different target word does not. Retail has exactly that
RMW in exactly that position, so this is a decision of the full retail
translation unit, not of the region.

**4. Co-compiling `Entity_Init` changes the triple but not towards retail.**
With the landed `0x401DE0` body as an ABI anchor (the `anchors` field the
`0x0041C480` landing added), the dead `xor ecx,ecx` disappears — the call
becomes a bare `call 00401DE0` with the object already in EDX (the anchor's
re-convened argument register), and with the "fresh element local" field shape
the triple becomes **EAX=index, ECX=resource, EDX=object** (160 differing): the
resource reaches ECX, retail's slot, but the object and the index move. A
scaffolding anchor whose IL clobbers EDX (a division plus a call with the entity
live across it) gives **EAX=object→EBX, ECX=resource→EDI, EDX=index→ESI**
(190-196 differing): the object and resource slots become retail's, the index
gets EDX, and the homes permute. No anchor shape tried produces
`EAX=object, ECX=resource, EBX=index`.

**5. Nothing can be registered.** The emitted extent already equals retail's 203
in every build, but the bytes differ, so the region stays `asm` and the
maintained `regions.json` was not touched (all registration ran with
`--project /tmp/anmload/msvc`).

## Effect on the 0x448D50 closure

**0x448D50 does not land from this work, and this region is still its blocker.**
The wave-8 note lists the closure `0x448D50 → {0x449950, 0x43E710, 0x4489D0,
0x401DE0}` and states that `0x448D50`'s own 95 bytes are settled but need the
callees' real conventions. This wave measured that co-compiling `0x43E710` as
C++ does **not** hand its callers retail's agreement: the pass decides the
callee's incoming triple from the callee's own IR, then re-shapes every caller
around it (the compiled caller anchors here all load `objects[slot]` into ECX,
copy the index into EAX, and stage the resource in ESI — a self-consistent
agreement that is *not* retail's). So a cluster holding the 448D50 model plus
this region's model would produce a byte-exact *pair of a different convention*,
not the retail pair; the 448D50 model's own `mov ecx,[esp+10h]` /
`mov eax,esi` / `mov ebx,[esp+18h]` call sequence can only come out when its
callee actually wants EAX/ECX/EBX, which this region refuses to do in a
