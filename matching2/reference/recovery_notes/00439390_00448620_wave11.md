### The three measured levers

1. **The camera store must go through a local pointer.** Storing
   `data_00491fac = (RenderTargetViewport*)&data_00491d7c;` straight from the
   address produced the 10-byte immediate form
   (`movl $0x491d7c,0x491fac`, +4 bytes) where retail has `mov %edi,0x491fac`.
   `RenderCamera* camera = &data_00491d7c; data_00491fac = (RenderTargetViewport*)camera;`
   makes the address a register value and emits retail's 6-byte store, with the
   address already in EDI for the recovered `ApplyDefault`.
2. **The state fields must be read and written through the modelled state
   object, not through bare `extern "C"` globals.** With `data_00492378` and
   `data_00491fb0` declared as globals the flush block scheduled as
   `mov (%eax),%ecx / push %edi / push $0x1c / push %eax / mov %edi,0x492378`
   (12 bytes out); with `data_00491c28.fog_dirty` / `.stage_index` it schedules
   exactly as retail (`push %edi / push $0x1c / mov %edi,0x492378 / mov (%eax),%ecx / push %eax`).
   This is the same modelling style `0x00448770` uses, and it is a *scheduling*
   lever, not an encoding one — the two spellings emit the same store.
3. **Argument order of the bucket renderer.** An anchor declared
   `(int index, void* manager)` sets the two arguments up in retail's *reverse*
   order (`mov %edi,%ebx / mov $0x3,%eax`); `(void* manager, int index)`, called
   as `f(this, 3)`, sets up `mov $0x3,%eax / mov %ebx,%edi`, retail's bytes.

## 0x00439390 — not landed

* everything that does not depend on the entry pair matches: the stage-1 camera

### The shapes tried

*Three compiled callee anchors* (bodies in the payload source, placed by the
layout at the retail addresses, never exported):

| callee | required | achieved |
| --- | --- | --- |
| `0x00420CD0` | state in EDI | **EDI** — emitted body is retail's (`mov 0x750(%edi),%eax` …) |
| `0x0044C150` | object in ESI | **ESI** (`mov 0x4(%esi),%eax`) |
| `0x0043DDF0` | mode EBX, camera EDI, task ESI, parameters stack | **EBX/EDI/ESI/stack**, but only with the second body: the first (`camera` and `parameters` both live across the loop) gave mode EBX, task ESI, **parameters EDI**, camera on the stack |

*Three synthetic-caller shapes* for the entry convention (the pass must choose
EBX for `mode`; none did):

1. call once after the loop with a literal `0` → both arguments on the stack;
2. call inside the loop, result compared against `0` (retail's caller keeps the
   live zero in EBX: `cmp %ebx,%eax`) → unchanged;
3. the same with `frame` carried out of the loop → unchanged.

The register pair is *earned* by the callee's own body (both anchors above show
that), but the function's entry convention is chosen from the caller's shape,
and with a synthetic context the pass finds it cheaper to keep `mode` on the
stack and load it into EBX at the single call site (`mov 0x1c(%esp),%ebx`) than
to keep it live in EBX across the five calls that precede the dispatch.  The
real caller is the landed assembly region in `src/platform/window.cpp`
(`push 0x4924F0; call`, EBX already 0 and live across the call), which is what
makes EBX free there; reproducing that needs either that region's own recovery or
a context whose live set matches it — the three shapes above are not enough.

Next step for whoever picks this up: land `0x00439390` through its *own* source
recovery after `0x00438AD0` (window.cpp) is modelled, so the real caller's
register state is in the link, or keep searching the caller shape with the frame
limiter's own body shapes fixed first (the `RET 4` and the entry registers are
consequences of the body's live set: retail's EBX never appears in the body).
