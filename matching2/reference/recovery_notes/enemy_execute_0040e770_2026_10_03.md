# Enemy ECL instruction handler at 0x0040E770: equivalent recovery, not byte-exact

The 14,416-byte region (13,760 bytes of code, a 108-entry case table, a
181-byte opcode index, and two 5-entry difficulty tables) is registered under
`equivalent_recoveries`. The default build compiles the C++ below into the
executable (14,280 of the 14,416 bytes, the rest padding) after
`tools/matching/equivalence.py` has checked it against the exact bytes. The
assembly in `msvc/src/script/ecl_vm.cpp` is kept for the exact link that check
compares against and for `make EXACT=1`.

This is the loosest of the three equivalent recoveries. Read "How close it is"
before relying on it.

## Files

- `msvc/equivalent/script/enemy_execute_0040e770.cpp`: `Enemy::Execute_0040e770()`,
  opcodes 0x100 to 0x1B4.
- `msvc/equivalent/script/enemy_execute_0040e770.hpp`: enemy, shooter, laser,
  spell-card, and manager types. Names carrying an `_XXXXXXXX` suffix are bound
  to that retail address.
- `msvc/equivalent/script/enemy_execute_0040e770_context.cpp`: models of the
  callees and a caller. They exist only so the checking `/GL` + `/LTCG` link
  derives the private register conventions retail has; none of their code
  ships. Several contain deliberate steering (a dummy call that clobbers a
  register, a parameter whose address is taken, a duplicated use) with no
  claim to being the original source. `ext_*` functions are placeholders that
  only the context calls.
- `msvc/layout/equivalent/enemy_execute_0040e770.json`: bindings and the
  recorded differences.

`Angle_Normalize` (0x0044BC70), `Motion_SetAngle` (0x00413170), and
`D3DXVec3Project` (0x0045218E) are bound as absolute symbols rather than
modelled: retail spills x87 values around them, which the compiler only does
for callees it cannot see.

## How close it is

| Instructions | Count |
| --- | --- |
| Total | 3,926 |
| Identical | 3,174 (80.8%) |
| Same instruction, stack slot shifted (`frame-offset`, by rule) | 457 (11.6%) |
| Recorded differences | 295 (7.5%), in 143 places |

The order of the opcode cases, the contents of all four tables apart from one
entry (item 5), every call target, and every callee convention match. What
differs:

1. **Frame size.** Retail reserves 0x2C4 bytes, the model 0x2B4. Retail has
   12 bytes at `[esp+0x44]` and 4 at `[esp+0xC]` that nothing reads or
   writes; the source construct that leaves them was not found (an unused
   local with an empty constructor does not). Every slot therefore sits 4 or
   16 bytes lower in the model. The checker accepts an otherwise identical
   instruction whose `esp` offsets differ by exactly those distances and
   counts them (457); the layout records the count.
2. **`code-shape`** (182 retail instructions in 76 places). Same values to the
   same places through other instructions: opcode 0x11D copies its goal through
   x87 in retail and through an integer register in the model; opcode 0x106
   uses a load/`or`/store where the model folds to `or [mem],imm`; the rank
   and difficulty selectors (0x15D to 0x164, 0x1A6 to 0x1AA, 0x1B4) share
   tails across cases differently, so an operand index is loaded before the
   jump on one side and after it on the other.
3. **`block-order`** (43 instructions in 4 places): a shared tail emitted once
   in one build and twice in the other, or placed elsewhere.
4. **`register-choice`** (30 in 15) and **`evaluation-order`** (27 in 35,
   counted on the retail side): scratch registers and the order of
   independent loads, in opcodes 0x103, 0x10D, 0x118, 0x119, 0x11C, 0x15B,
   0x190, 0x191, 0x199, 0x19D, 0x1A8, 0x1AC to 0x1AE.
5. **`branch-target`** (12): eleven branches and one difficulty-table entry
   whose destinations are the differently merged tails of item 2. The checker
   first tries to show that both destinations run the same instructions to a
   return or an aligned pair; these twelve it could not, and they are listed
   with both destinations.
6. **`alignment-padding`** (1).

The classes were assigned by a script from the shape of each difference and
spot-checked by case; the differences were not each proved by hand. No runtime
test was performed; the claim rests on the instruction comparison.

## Checker changes this needed

- `frame_shift` in a layout: distances and expected count for item 1.
- Branch targets are also accepted when the code from both runs identically
  (tails merged differently where no instruction differs).
- `listed_branch_targets`: opt-in; without it an unproven branch target is
  still a failure, as for the other two recoveries.
- Class `code-shape`.

## What the source had to look like

- Operands go through two inline layers (`Enemy::Int` to `EnemyFull::Int` to
  `EclVm::IntOperand`), which reproduces the early load of the VM pointer.
- The dispatch reads `ecl->active` through a volatile lvalue; otherwise the
  load is shared with the first case and the head differs.
- `RngState::NextAngle`, `SquaredLength`, and `DistanceSquared` are inline
  helpers: the boundary stops constant folding and gives right-to-left
  evaluation.
- Rank chains are separate `if (...) { ...; return 0; }` blocks ending in an
  if/else that shares `return 0`; difficulty cases assign a value per branch.
- Shooter fields are spelled `shooters[index].field` with no pointer local.

## Open

- The dead 16 bytes of frame (item 1).
- The cross-case tail merges of the rank and difficulty selectors.
- The x87 copy in opcode 0x11D and the unfused `or` in 0x106.

## 2026-10-17: state reviewed; parked

The 143 hunks are the note's open items plus their follow-on scheduling: the
dead 16 bytes of frame (the stack-slot weight family), the cross-case tail
merges of the rank and difficulty selectors (the distinct-argument merge
family), and the x87 copy in opcode 0x11D / the unfused `or` in 0x106. Each

Region stays equivalent (12139 differing bytes).

## 2026-10-17: the dead 16 bytes measured; closing them needs purposeless state

The frame-size survey's fourth entry: `retail sub esp,0x2c4` (708) against
`model sub esp,0x2b4` (692), 16 bytes short. Supplying that frame space is
measurably good — for `item_update` the same move improved the match by 214
differing bytes — so this measured whether it holds here. Diagnostics only,
against the baseline 3,174/3,926, 143 hunks, 12,139 differing bytes:

| variant | identical | hunks | differing bytes |
| --- | --- | ---: | ---: |
| baseline | 3,174/3,926 | 143 | 12,139 |
| `home-2x8` (two `double` locals) | **3,178/3,926** | **134** | **12,023** |
| `home-4x4` (four `unsigned int`) | 3,178/3,926 | 137 | 12,024 |
| `home-16` / `home-struct` / `home-volatile` | 3,174/3,926 | 143 | 12,003 |

So the gap is real and worth about 9 hunks. But every spelling that supplies
it is a declaration with no purpose in the code — the note's own description
is "the **dead** 16 bytes of frame", which is what retail's allocation
carries and what the visible body does not use. Adding unused locals to hit a
frame size is padding, and this pass will not ship it.

Worth recording for whoever picks this up: two `double` locals are the shape
that moves it most, which is the same signature as `item_update`'s missing
8-byte home. If the real source turns out to have carried a 16-byte aggregate
here, that is where it goes. Region stays equivalent.

## 2026-10-18: the 16 bytes are real state; count-selector tails merge late

Baseline 3,174/3,926, 143 hunks, 12,139 differing bytes (12,003 code +
136 tail). Now 3,682/3,926, 115 hunks, 9,457 differing bytes (9,453 code +
4 tail), `frame_offset` 2, gate clean. Frame is retail's 0x2c4 and every
stack slot sits at retail's offset (the slot map is identical entry for
entry).

**The dead 16 bytes are the three `AnmHandle` out-variables of the kind-5
`Anm_CreateFront` calls (opcodes 0x103/0x106/0x10d).** Retail passes three
distinct stack slots (`lea edi,[esp+0x50/0x54/0x58]`, frame +0x38/+0x3c/
+0x40) to `AnimationManager_CreatePrimaryFront`'s out pointer and reads the
result through the returned pointer; the model reused one shared temporary
for all seven handle sites. Declaring one function-scope `AnmHandle h3[3]`
and passing `&h3[0]` (0x103), `&h3[1]` (0x10d), `&h3[2]` (0x106) gives the
three contiguous slots, and the frame then lands on 0x2c4 with the 4
unreferenced bytes at the frame bottom appearing by themselves (the slot
pool is 8-aligned). The kind-6 sites (0x107/0x108/0x110/0x111) stay
per-case locals: retail shares one slot for them. This is the same shape
as `item_update`'s home: address-taken aggregate, not padding. Every
padding spelling is ruled out again (plain and `volatile double` locals
are inert on the current base; `home-2x8`'s 2026-10-17 movement was the
same missing aggregate, not doubles).

**The cross-case tail merges of the distinct-argument selectors are the
merge-survivor lever, not the copy shape.** The five per-argument copies
(`*IntDest2(0) = IOP(n)` / `*FloatDest(0) = FOP(n)`) already merged in the
model, but the merged tail kept the *last* copy's position; retail keeps
the first copy's and leaves `push N; jmp tail` stubs behind it. Ending the
copies with `goto done` to a label at the function end flips the survivor
to the first copy (the 0x00420670 addition of
`msvc-c2-tail-merge-and-cluster-section-tricks`), and the merge runs late
enough to reach across cases. Applied to 0x163/0x164/0x15D/0x15E/0x160/
0x161 and the count family 0x1A9/0x1AA/0x1B4; 0x1ab's copies must `goto`
the *first-defined* of two co-located labels at the shared return
(`done2:` before `done:`), which is what keeps its copy where retail
keeps it. The label name is inert (`d2`/`x`/`done2` measure identically
when the definition order is fixed); the definition order alone decides
the survivor and is worth 2,538 differing bytes (9,457 vs 11,995).

Ruled out this pass: case reordering and `goto advance` (inert, as the
2026-10-17 sections record); converting the speed family 0x1A6/0x1A7/
0x1B3 — every spelling either replaces a call inside one hunk (gate
failure at 0x1e4b/0x1ffd) or overshoots the region; `1A9`/`1AA`/`1B4` as
the first label (worse or draft); the x87-copy family in 0x11D (goal
temps, `Float2` constructor, field-wise `interp->goal.x` writes, volatile
goal fields — all measured worse; retail merges the three goal.x arms into
one `fstp` at the join and keeps the goal.y copies in x87 where the model
RISCifies them to integer moves); the unfused `or` in 0x106 (`volatile`
cast and `flags = flags | 0x1000` — the cast overshoots, the explicit
form folds back).

Open: the 115 hunks are the register-choice/evaluation-order families
(0x103/0x106/0x10d, the 0x118-0x11f x87 region and its slot order,
0x199/0x19b shooter-ex addressing, 0x1ae atan2), the speed selectors'
tail splits, the x87 copy in 0x11D, the unfused `or` in 0x106, and 4
bytes of code length (model 14,412 vs retail 14,416). The switch case
sets were re-verified against the retail dispatch: 124 outer labels plus
the 5 inner `g_difficulty` labels (129 distinct), and the 57 unlabeled
opcodes reach the shared return exactly as retail's shared case block
does; the source-only labels 10/15/20/25/30/35 are the context file's
steering switch (real opcode values 0x164/0x167/0x16A/0x16D), not
transcription errors.

## 2026-10-18 (session 2): 115 → 71 hunks; ex addressing, the `or`, and the
## x87 phi land together

State: **3,771/3,926 identical, 71 recorded hunks** (was 3,682/115), model
code 14,396 (20 short of the region), gate clean.

**0x199 shooter-ex: the `ex` pointer local was the wrong shape.** Retail's
block is `lea esi,[ebx+eax*8]` (scaled base, the `0x2e4` field base kept in the
stores, and the last store re-derived as `lea ecx,[edi+edi*2+0x5d]; fstp
[ebx+ecx*8]`). A `ShooterEx* ex = &shooters[index].ex[entry]` local is
forwarded — the field base folds into the lea. Spelling the six stores as
`shooters[index].ex[entry].<field> = …` reproduces retail byte-identically and
also splits the `EnemyCtrl_SweepDeaths` tail of 0x152/0x159 into two copies as
retail has (the pointer spelling merged them). This is the
`msvc-c2-field-address-pointer-forwarding` rule seen from its other side.

**The 0x106 `or` is the read-modify-write form.** `(volatile unsigned int&)flags
|= 0x1000;` gives `mov eax,[flags]; mov edx,[ebx+0xe8]; or eax,0x1000; mov
[flags],eax` with the `anm_file` load interleaved; the fused `or [mem],imm` is
17 bytes short there.

**The x87 phi of 0x11D lands only together with the `or`.** The declared temp
shape (`float gx; gx = <ternary>; goal.x = gx;`, sequential, tight scopes)
produces retail's block (hoisted `fld`, shared `fstp`, x87 goal.y copies) but
rotates the register picks of the following copy-tail by one step, which breaks
the `interp->initial/goal + Restart3` tail-merge with 0x121/0x123 (+16 code
bytes). The volatile `or` alone reshuffles the other way. Together the
register pressure lands and the merge survives: x87-cluster hunks 30 → 5.

Also closed: 0x163's stub survivor (its copies must `goto` the first-defined of
the two co-located exit labels) and 0x1A6's tail (`return 0` → `goto done`).

Byte-count caveat recorded in `STATUS.md`: the raw differing-bytes column is
dominated by instruction-length drift (first divergence at 0x630: `mov
eax,[0x477704]`'s 5-byte A1 form against retail's 6-byte `mov ecx` form); the
shipped state's lower byte count is accidental cancellation of its deltas. The
identical/hunk counts are the honest measures at this stage.

Ruled out this session: 0x199 second-assignment/array-pointer forms (no
effect); goal-phi order/ctor-first/mode-invert/one-temp spellings (all break
the copy merge or the mode==7 registers); the speed family 0x1A7 (gate failure
at 0x1ffd) and 0x1A6→done2 (+124); `flags = flags | 0x1000` (folds back);
0x103 argument-evaluation splits (no-op or worse).

## 2026-10-18 (session 3): 71 → 61 hunks; the label lever generalizes and the
## polar struct was the slot-order bug

State: 3,788/3,926 identical, 61 recorded hunks, `frame_offset: 0`.

- The first-defined exit label flips tail-merge survivors per group: 0x15E and
  0x1A9 joined 0x163/0x1AB on `done2` (before `done`). The 0x1A9 flip is what
  places the 22-instruction block of 0x2110/0x2233 exactly as retail does.
- 0x11C/0x11E: `Float2 polar` → two scalars `float px; float py;` (assigned in
  FOP(0), FOP(1) order). The struct's field slots came out x-low/y-high; retail
  keeps y at the lower slot. x87-cluster hunks 5 → 1 and the last
  frame-shifted instructions vanish (`frame_offset` 0). Declaration order is
  irrelevant; the struct-vs-scalars split is the lever.

Ruled out: every other single-group label toggle (0x164/0x1b4/0x1a6/0x1aa/
0x15d/0x160/0x161), 3-label structures, the 0x1A7/0x1A8/0x15F/0x162
conversions, and the 0x630 named-local variants (`AnmLoaded* res`, `int s2`).
The 0x630 residual is a scheduling question: retail hoists the
`g_enemy_ctrl->anm[…]` loads above the `push 0x5`/`push eax` pair, which also
gives `mov ecx,[abs]` (6-byte form) instead of `mov eax,[abs]` (A1, 5 bytes) —
the first instruction-length divergence in the region.

## 2026-10-18 (session 4): code length exact; 0x1AE's pointers need the CSE
## broken across the call

State: 3,808/3,926 identical, 53 recorded hunks, model code 14,416 bytes —
the region's exact length (`tail 0`), `frame_offset 0`.

The 0x1AE atan2 block: retail materializes `&g_player->position` twice (esi
before the FOP(1) call, edi before FOP(2)) and reads `[esi]`/`[edi+0x4]`
after both. Since `&g_player->position` = `g_player + 0x3c0` and an opaque
call may change the `g_player` global, two computations separated by a call
cannot CSE. Spelling the two pointers around the call
(`const Float3* p1 = &g_player->position; float t1 = FOP(1);
const Float3* p2 = &g_player->position; …atan2(p2->y - FOP(2), p1->x - t1)`)
reproduces both materializations and the x87 argument order exactly. This is
the inverse of the 0x199 fix: there a forwarded pointer folded the field base
into the lea and direct field accesses kept it in the stores; here the two
reads must NOT be forwarded into one register.

The exit-label hill-climb (0x163/0x15E/0x1A9 on the first-defined label, the
rest on the second) is the only configuration found whose code length lands on
14,416 exactly; putting the 0x1AE exit on the first label closes its shared
`*FloatDest` tail merge but adds six 0x164 stub/table hunks and 40 bytes of
length, and that trade is recorded as open.

## 2026-10-19: two call-argument orders (46 → 42 differences)

- Case 0x191 (+0x1B42): retail loads `g_bullet_manager`, forms the shooter
  address (`lea eax,[edx+0x2c4]`), and only then pushes. The member call
  `shooters[index].Shoot(g_bullet_manager)` pushed first. The context's
  `Shooter::Shoot` is replaced by a stdcall stand-in
  `ShooterShoot(BulletManager*, Shooter*)` bound to 0x004073E0 (cdecl could
  not bind). Right-to-left evaluation forms the shooter address before the
  manager. Forceinline wrappers in either order, a named shooter pointer and
  a named manager local did not change the order.
- Case 0x149 (+0x172E): `Drops_Flush` declared `(drops, position)` makes the
  caller form the position address (EAX) before the drops address (EDI).
  The convention keeps the same registers, and the binding moved to the new
  mangled name.
- Case 0x195 (+0x1CA2, `mov ecx,0x2` scheduled before the operand loads) did
  not move with a shooter reference/pointer, named float locals or an
  indexed store.

## 2026-10-19 (later): arguments read through accessors (42 → 39 differences)

c1 evaluates call-containing arguments first and plain field/array reads at
their use. Retail evaluated some plain-looking arguments in strict
right-to-left order between the operand calls, so in retail they were not
plain.

- Case 0x15B: `g_front->SetMarker(IOP(0), MaxLife(), FOP(1), IOP(2))`.
  Through the inline `Enemy::MaxLife()` accessor, `max_life` is read and
  stored before the `IOP(0)` call, as retail does (+0x14F7). Changing
  SetMarker's own body (a named denominator, a marker pointer) or using a
  pointer argument, a cast, `+ 0`, a comma or `this->` did not.
- `Anm_CreateFront(g_enemy_ctrl->Anm(file), ...)` at the four
  `IOP(1)`-script sites. The accessor loads the resource before the pushes
  (+0x630). Converting only the first site flips the case-0x191
  `shoot_offset[index] + position` x87 operand order. All four together
  keep it, but they flip one `shoot_offset[0] + position` site (+0x28AE,
  recorded operand-order). Swapping any of the four `params.position` sums
  is worse. The `h3[2]`/`h3[1]` sites (computed scripts) collapse the
  function when converted.

Retail loads the element into EAX, reusing the index register, right after `mov ecx,g_enemy_ctrl`. The model loads it into EDX after `push edx`.

- Named `file`/`script` locals after the release: 73-75 hunks.

### 2026-10-19: case 0x190 shooter reset, angle store first (39 -> 38 differences)

In case 0x190, `shooters[index].angle_1 = 0.0f;` is now written straight after the memset, before the two `count = 1` stores. The 0.0f store then shares the memset's zero in EAX, the 1 moves to ECX, and the extra `xor eax,eax` goes away. That closes 0x19e0 and gives 3842/3926 identical. c2 still emits the stores in retail's order (counts first). The other changes are the same branch-target hunks shifted by one byte, and the padding hunk moved from 0x272f to 0x35bf.
