# Enemy ECL instruction handler at 0x0040E770: equivalent recovery, not byte-exact

The 14,416-byte region (13,760 bytes of code, a 108-entry case table, a
181-byte opcode index, and two 5-entry difficulty tables) is registered under
`equivalent_recoveries`. The default build compiles the C++ below into the
executable (14,280 of the 14,416 bytes, the rest padding) after
`tools/matching/equivalence.py` has checked it against the exact bytes. The
assembly in `msvc/src/script/ecl_vm.cpp` is kept for the exact link that check
compares against and for `make EXACT=1`.

This is the loosest of the three equivalent recoveries. Read "How close it is"
before relying on it.

## Files

- `msvc/equivalent/script/enemy_execute_0040e770.cpp`: `Enemy::Execute_0040e770()`,
  opcodes 0x100 to 0x1B4.
- `msvc/equivalent/script/enemy_execute_0040e770.hpp`: enemy, shooter, laser,
  spell-card, and manager types. Names carrying an `_XXXXXXXX` suffix are bound
  to that retail address.
- `msvc/equivalent/script/enemy_execute_0040e770_context.cpp`: models of the
  callees and a caller. They exist only so the checking `/GL` + `/LTCG` link
  derives the private register conventions retail has; none of their code
  ships. Several contain deliberate steering (a dummy call that clobbers a
  register, a parameter whose address is taken, a duplicated use) with no
  claim to being the original source. `ext_*` functions are placeholders that
  only the context calls.
- `msvc/layout/equivalent/enemy_execute_0040e770.json`: bindings and the
  recorded differences.

`Angle_Normalize` (0x0044BC70), `Motion_SetAngle` (0x00413170), and
`D3DXVec3Project` (0x0045218E) are bound as absolute symbols rather than
modelled: retail spills x87 values around them, which the compiler only does
for callees it cannot see.

## How close it is

| Instructions | Count |
| --- | --- |
| Total | 3,926 |
| Identical | 3,174 (80.8%) |
| Same instruction, stack slot shifted (`frame-offset`, by rule) | 457 (11.6%) |
| Recorded differences | 295 (7.5%), in 143 places |

The order of the opcode cases, the contents of all four tables apart from one
entry (item 5), every call target, and every callee convention match. What
differs:

1. **Frame size.** Retail reserves 0x2C4 bytes, the model 0x2B4. Retail has
   12 bytes at `[esp+0x44]` and 4 at `[esp+0xC]` that nothing reads or
   writes; the source construct that leaves them was not found (an unused
   local with an empty constructor does not). Every slot therefore sits 4 or
   16 bytes lower in the model. The checker accepts an otherwise identical
   instruction whose `esp` offsets differ by exactly those distances and
   counts them (457); the layout records the count.
2. **`code-shape`** (182 retail instructions in 76 places). Same values to the
   same places through other instructions: opcode 0x11D copies its goal through
   x87 in retail and through an integer register in the model; opcode 0x106
   uses a load/`or`/store where the model folds to `or [mem],imm`; the rank
   and difficulty selectors (0x15D to 0x164, 0x1A6 to 0x1AA, 0x1B4) share
   tails across cases differently, so an operand index is loaded before the
   jump on one side and after it on the other.
3. **`block-order`** (43 instructions in 4 places): a shared tail emitted once
   in one build and twice in the other, or placed elsewhere.
4. **`register-choice`** (30 in 15) and **`evaluation-order`** (27 in 35,
   counted on the retail side): scratch registers and the order of
   independent loads, in opcodes 0x103, 0x10D, 0x118, 0x119, 0x11C, 0x15B,
   0x190, 0x191, 0x199, 0x19D, 0x1A8, 0x1AC to 0x1AE.
5. **`branch-target`** (12): eleven branches and one difficulty-table entry
   whose destinations are the differently merged tails of item 2. The checker
   first tries to show that both destinations run the same instructions to a
   return or an aligned pair; these twelve it could not, and they are listed
   with both destinations.
6. **`alignment-padding`** (1).

The classes were assigned by a script from the shape of each difference and
spot-checked by case; the differences were not each proved by hand. No runtime
test was performed; the claim rests on the instruction comparison.

## Checker changes this needed

- `frame_shift` in a layout: distances and expected count for item 1.
- Branch targets are also accepted when the code from both runs identically
  (tails merged differently where no instruction differs).
- `listed_branch_targets`: opt-in; without it an unproven branch target is
  still a failure, as for the other two recoveries.
- Class `code-shape`.

## What the source had to look like

- Operands go through two inline layers (`Enemy::Int` to `EnemyFull::Int` to
  `EclVm::IntOperand`), which reproduces the early load of the VM pointer.
- The dispatch reads `ecl->active` through a volatile lvalue; otherwise the
  load is shared with the first case and the head differs.
- `RngState::NextAngle`, `SquaredLength`, and `DistanceSquared` are inline
  helpers: the boundary stops constant folding and gives right-to-left
  evaluation.
- Rank chains are separate `if (...) { ...; return 0; }` blocks ending in an
  if/else that shares `return 0`; difficulty cases assign a value per branch.
- Shooter fields are spelled `shooters[index].field` with no pointer local.
