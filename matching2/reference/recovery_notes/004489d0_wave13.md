## A mechanism probe: the copy itself is a pressure artefact

One probe goes after the cause directly: keep the else block's successor temp
live *across* the id block (declare it outside the branch and use it after the
final stores, which of course changes the bytes). The result is not "counter
moves to ESI" but a full re-convention:

```text
448a1d: mov %edx,0x72dad8(%ecx)      ; the MANAGER has moved from EDX to ECX
448a23: mov 0x732454(%ecx),%edx      ; the counter takes the first free register (EDX)
448a29: inc %edx
448a2a: test %edx,%edx               ; and the copy is GONE: no mov %edx,%r2
448a2c: mov %edx,0x732454(%ecx)
448a41: mov %edx,(%ebx)              ; the entity is still in EBX, the out slot in EAX
448a4a: cmp $0x1,%esi                ; `keep` occupies ESI
```

Two things follow. (a) The counter takes the first free register in the backend's
canonical order, and that order puts ESI before EDI (retail and this model both
load the head into ESI with the pool {ESI, EDI} free) — so the leaf's counter in
EDI is not a plain free-register pick; the value must carry something that makes
the backend prefer EDI at that point. (b) The `mov %esi,%ecx` copy and the
`test %ecx,%ecx` on a second register are *pressure artefacts*: with one fewer
free register the copy disappears and the test uses the stored register, i.e. the
non-folded 18-instruction tail is what a *two-register* pool produces. Adding
liveness at the id block therefore re-conventions the leaf first (here the manager
moves from EDX to ECX), which is exactly the failure mode every "keep a second
value live" row above shows.

Two of these rows are the new information:

* **The schedule is separable from the register.** The "tail read up front" row
  emits the tail store *before* the counter load (retail's order) and still homes
  the counter in EDI. So the reorder is not the cause of the register choice —
  wave 12's folded/`+0x4b` shapes and this row are the two independent halves of
  the delta.
* **Anything that touches the list code re-conventions the leaf.** Adding one
  live pointer, writing the head/tail pair through one base, marking the tail
  store `volatile`, reading the tail early, or swapping the else's last two
  statements all move the entry registers off EDX/EBX/EAX, and they move
  `0x00448D50` with them (`first=+0x1`, d50=1). Only the wave-10 list spelling
  reproduces retail's list bytes and retail's convention.

This is the same conclusion wave 12 reached, restated with the schedule
separated out: ~45 further spellings (on top of wave 12's ~200 builds) always
land the counter in **EDI** for the 18-instruction non-folded tail, and only the
folded spellings avoid the second register (and they collapse the tail to 49
bytes, i.e. 117 emitted).

## Two new measurements that bound the problem

**1. Anchor vs selected function does not change the body.** Flipping the
scratch manifest's region record for 0x004489D0 to `semantic`, writing the
candidate into `src/render/animation_manager_register_primary_back_004489d0.cpp`,
and declaring it as a *selected function* of the same cluster (no anchor,
`additional_sources` naming that file) emits

```text
0x004489d0 emitted=118 want=118 differing=40 first=+0x1c got=57 want=75
0x00448d50 emitted=95  want=95  differing=0
```

i.e. the identical body. So the anchor is *not* what homes the counter in EDI and
the anchor/function distinction is not the lever. **Answer to the assignment's
question:** today the 0x00448D50 anchor cannot be dropped — with an absolute
`relative_code` binding at 0x004489D0 (which removes the body from the link) the
pass re-decides the caller and 0x448D50 loses 78 of 95 bytes (wave 12's
measurement, reproduced in spirit by every re-conventioning row above). If and
when the body is exact, the anchor *can* be dropped by declaring the region as a
selected function of the 0x448D50 cluster, and I have measured that this route
emits the very same body — so the switch costs nothing once the register is
right.

**2. A cluster with no other animation bodies changes nothing either.** The same
body in a standalone cluster (its own `source` + a synthetic loop caller, layout
`rb_solo.json`, no 0x448D50 caller in the link) still comes out with the
EDX/EBX/EAX triple, retail's list bytes and the counter in EDI. The register is a
property of the body, not of the link's other bodies — consistent with wave 12,
and it means `0x00448980`/`0x004451C0` being recovered cannot be what unblocks
this region.

## Why the counter's home matters for more than this region

Retail's own census of this idiom (all 18 sites in `th10.exe`, found by scanning
`inc %r` preceded by a load of `0x732454`):

```text
R1,R2 counts: {('ecx','eax'): 10, ('edx','eax'): 4, ('esi','ecx'): 4}
```

The four `(ESI, ECX)` sites are exactly the four registration leaves
`0x004489D0` (primary back), `0x00448A50` (primary front), `0x00448AC0`
(secondary back), `0x00448B40` (secondary front) — they are the only ones with a
`test %ecx,%ecx` self-comparison. The other 14 instances compare the id against a
*variable* (`cmp %ebx,%eax`, with EBX zeroed), so they are a different source
shape and are not inlined copies of the leaf.

I also built the **front twin** (`0x00448A50`, a head insert) with a retail-shaped
body (112 bytes) into its own cluster
(`layout/ltcg/rb_front.json`, the maintained `positioned_primary_front_00448e80_wave12`
layout with the 97-byte folded anchor raised to 112):

```text
0x00448a50 emitted=112 want=112 differing=99 first=+0x4  got=57 want=89
0x00448e80 emitted=95  want=95  differing=0
```

So the whole leaf family shares the blocker, and this attempt unblocks **nothing**:
`0x00448A50`, `0x00448AC0` and `0x00448B40` cannot be recovered by the same route

and `0x00448D50` keeps probing EXACT with its 103-byte stand-in anchor.
