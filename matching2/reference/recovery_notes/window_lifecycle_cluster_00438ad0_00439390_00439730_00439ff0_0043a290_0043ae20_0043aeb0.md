## Semantic and retail evidence

The archived
`matching2/reference/legacy_semantic/src/platform/window.cpp` supplies the
readable behavior for the main window and MIDI/COM helpers:

* `0x00438AD0` is the WinMain lifecycle.  It allocates/clears the game arena,
  initializes the process/instance state, saves system settings, creates the
  game window and device-dependent subsystems, runs the message/frame loop,
  and performs the IME/cursor, window, worker, and system-setting teardown.
  The maintained retail body is a large inline call graph rather than a
  normal function boundary, with stack locals and security/SEH-sensitive
  transitions.
* `0x00439730` registers the `BASE` class, installs the WndProc at
  `0x004390E0`, chooses the 640x480 windowed or borderless fullscreen style,
  publishes the handle to both `0x004924F0` and `0x00491C70`, then sends the
  minimize/restore messages.  Retail carries `HINSTANCE` in `EBX`, builds a
  0x28-byte stack `WNDCLASSA` image, and calls the User32 IAT directly.
* `0x00439FF0` creates the single-instance mutex, checks
  `ERROR_ALREADY_EXISTS`, gathers module/console/startup strings, follows
  chained `.lnk` paths through `0x0043A290`, compares the resolved path, and
  sets/clears the replay flag.  Retail owns a 0x258-byte security-cookie stack
  frame and returns `0` or `-1` after the mutex check.
* `0x0043A290` resolves a shortcut through `CoInitialize`,
  `CoCreateInstance`, ShellLink/PersistFile QueryInterface/Load/GetPath,
  UTF-8/ANSI-to-wide conversion, COM releases, and `CoUninitialize`.  Retail
  receives the target buffer/capacity in `EBX`/`EDI` and the shortcut path at
  the stack ABI position, with a 0x150-byte cookie-protected frame.
* `0x0043AE20` stops MIDI playback, scans 0x20 active headers, delegates each
  completed header to `0x0043AEB0`, resets/closes the MIDI output, ends the
  period, closes the timer event, and sets the MIDI state to `-1`.  Its manager
  arrives in `EDI` and the function returns plain `RET`.
* `0x0043AEB0` searches the manager's 0x20 header slots at `+0x14` for the
  header in `ESI`, clears the slot, calls `midiOutUnprepareHeader` through the
  IAT, frees/clears the header data, and frees the header.  Its manager is in
  `EDX`, header in `ESI`, and it returns the slot/not-found status in `EAX`.

The maintained retail disassembly additionally identifies the adjacent
owners:

* `0x00439390` updates the frame-clock doubles using x87 comparisons, flushes
  animation/camera state, services scheduler/worker state, and returns a
  small status through `RET 4`.  Its timing object is loaded from the stack
  into `EBP`; this address is not the WndProc itself and has no separate
  semantic body in the archived `window.cpp`.
No exported Ghidra C-function files were present in this checkout.  The
instruction-level evidence used for this pass is the maintained retail
disassembly in each live source plus the checked-in legacy semantic source;
the note makes no unsupported claim about an absent Ghidra export.

## Best next dependency

First recover a bounded Win32 ABI context for the smaller COM/MIDI pair:
`CoCreateInstance`/ShellLink vtable calls, the 0x150-byte `/GS` frame, and
the `EDI` manager / `EDX` manager-plus-`ESI`-header callback convention.  The
next window subcluster needs a native compiler context that keeps `EBX` as
the `HINSTANCE` through `RegisterClassA`/`CreateWindowExA`, reproduces the
dual-handle publication, and binds the WndProc callback at `0x004390E0`.
Only after those are exact should the 1389-byte WinMain and the adjacent
`0x00439390` x87 frame/scheduler helper be attempted together.
