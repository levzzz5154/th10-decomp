## What moved the count (873 -> 1,144)

Most residuals were the EAX/ECX/EDX rotation of expression temporaries
running one step off from an early point. The rotation is global, so each fix
below also realigned later cases.

- **`CREATE_INTO` resource as a named local** (873 -> 894). Retail allocates
  the resource apart from the rotating temporaries. Exception: the stage
  transition in opcode 20's last branch passes `stage->resource` directly.
- **Opcode 20 replay test as the else arm** (`if (replay_mode != 1) {...}
  else SetInputMode(4);`, 894 -> 906). Retail branches `je` to an out-of-line
  `SetInputMode(4)` block, and the stage 6 and 7 copies then merge as whole
  blocks after an unconditional jump. Explicit `goto`s to shared labels do not
  survive: c2 duplicates the small blocks again.
- **`ScoreState::AddScore` (0x409D90) not visible** (906 -> 909). Retail
  reloads `ecx = &g_globals` before each call, so its compiler did not know
  the callee keeps ECX. Bound as an absolute code symbol instead of compiled.
- **Plain `while` loop** instead of `if (...) do {...} while (...)`. Retail's
  bottom test is the compiler's rotated copy of the top test (forwarded
  `mov eax,edx` copy, `cmp [mem],reg`).
- **0x4492F0 parameter order `(context, id, position)`** (1,017 -> 1,027).
  Retail computes `lea esi,position` before pushing the id: the position is
  the rightmost argument. A stand-in `SetAnimationPosition` with that order is
  bound to 0x4492F0. The previous `(position, context, id)` declaration stays
  in the shared header for the other clusters.
- **Opcode 9 is a bitfield store** (1,027 -> 1,052). `mov eax,esi; xor
  ecx,esi; and ecx,1; xor eax,ecx` is MSVC's 1-bit field insert, not a
  hand-written xor.
- **Opcode 13: resource local assigned before each call, operand inline**
  (`SELECT_PAIR`, 1,052 -> 1,132). Retail evaluates the resource before the
  index for both calls. Index locals, inline resources, or separate second
  locals all score lower (927 to 1,052).
- **Opcode 20 transition slot through a pointer** (`int* transition =
  &stage->transition_animation.value`, 1,142 -> 1,144). The store of 0 then
  stays ahead of the `stage->resource` load.

## 2026-10-17: the ESI preference's owner is named

The preserved traces under
`matching2/build/experiments/allocator_oracle_2026_10_17/front_script_tick/`
answer the question this note left open. Parsing `named/events.jsonl`
(164 ChoosePhysReg, 46 Spill) and `temporary/events.jsonl` (197 RegAssign
picks):

- **No `_g_globals_difficulty` candidate carries a negative ESI cost.** They
  are num 86 (prio 88) -> ECX and num 87 (prio 80) -> EAX, both with every
  register cost zero, exactly as recorded above.
- The negative ESI costs belong to **`_animation`** candidates (num 154/157/
  160/164/166) and to **a run of ~20 anonymous candidates** (num 207-222,
  188-189, prio 84-120) each with `costs = {7: -2}`, plus num 225 with
  `costs = {4: 200, 7: -1}`. These are the inlined animation values.
- In the temporary trace there are exactly **two** ESI picks, matching what
  this note found: temp `0x643` (ir_opcode 0x1) and temp `0x7ac` (ir_opcode
  0x12). Across the function ir_opcode 0x1 is a memory read (102 of 173 carry
  a stack source displacement); `0x643` is one of the **71 with no stack
  displacement**, i.e. a read from an absolute address — the shape of a
  `g_globals_*` load. `0x12` never carries a displacement (15 instances).

So the difficulty load is most likely temp **`0x643`**, not one of the named
global candidates: the global candidates were allocated happily to ECX/EAX and
the load that ends up in ESI is an unnamed absolute-address read. The lever is
still not a source change — the oracle note records that forcing either
temporary to EDX at RegAssign's late point crashes c2 at 0x1079C09F, so the
change has to reach the earlier priority computation (the reference structure
that gives `0x643` its benefit count), not the selection point. Region stays
equivalent.

## 2026-10-18: closed at 1,147/1,147 — the count expression written out twice

The last 25 differing bytes (0xfd5-0xfed, the stage-7 clear-count copy) are
gone: variant.py reports `final 1147/1147 0 0 0 0 *EXACT*` and
equivalence.py gives `"differences": []`, `"not_equivalent": []`,
`base_index_order: 0`, `frame_offset: 0`.

The lever (msvc-c2-what-adds-a-register-candidate, "an expression written
twice and merged late"): both clear-count sites write the count expression
out a second time, at the test —

    if (*ClearCount() < 99999)
        ++*ClearCount();

The second write-out leaves a temporary plus the variable in the block.
That extra structure is what lets the `g_globals_difficulty` load sit in the
EAX/ECX/EDX rotation at the stage-7 copy: it reuses EDX after the shot
temporary dies, exactly as retail (retail: `mov edx,[0x474c74]` after the
`lea`). With the single `int* count = ClearCount();` form the load falls
through the rotation to ESI, and because ESI introduces no anti-edge the
list scheduler then hoists it above the `lea` and moves the score load
early — the recorded evaluation-order/register-choice hunks were all one
downstream symptom of that one register assignment. The scheduler order is
fully forced by anti-edges once the difficulty load has EDX (retail's
order: lea -> difficulty -> add -> imul -> add -> score), so the register
assignment was the only thing to fix.

Both copies must carry the double write-out: applied to the stage-7 site
alone it scores 1,140/1,147 (560 differing bytes) — the two copies of the
same expression must not disagree in shape. Every double-write-out spelling
tested (recompute at the test, at the increment, no local at all) compiles
byte-identical.
