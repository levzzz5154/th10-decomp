# 0x00443080 (515 bytes) modelled to one byte — wave 15

2026-09-19, worker `DispatchCases`. Work was done in `/tmp/DispatchCases/msvc`
(`cp -a matching2/msvc`); the maintained `regions.json`, layouts and sources were
never touched. **The region is not landed**: the model emits **514 of the
declared 515 bytes**, and the one byte it misses is an instruction-form
difference, so nothing was registered (a non-exact layout must never be).

## The answer in one paragraph

The dispatcher's case-0 target is a complete, structurally faithful model: the
entry, the guard, the x switch, the y switch, the z placement and the
`SubmitSpriteQuad(entity, 1)` tail all emit **retail's instruction stream
instruction for instruction** — 111 instructions against retail's 111, including
the two CRT `floor` calls (0x00452FF0), the `sub esp,8` argument areas, the
spill slots `[esp]/[esp+4]/[esp+8]` and the `mov eax,esi` marshalling. It is
**one byte short** because MSVC's stack-adjustment pass moves the floor call's
`add esp,8` one instruction earlier than retail's build did and retargets the
following `fadd` from `[esp+0x8]` to `[esp]` (3 bytes instead of 4). The single
differing instruction is

```text
                       retail                          model
0x0044315f  d8 44 24 08  fadd dword [esp+0x8]   d8 04 24  fadd dword [esp]
0x00443163  83 c4 08     add  esp,0x8           (one byte earlier, at 0x443162)
```

Everything else that the byte diff reports (273 differing bytes) is the
one-byte address shift this causes: the region's four rel8 jump displacements
(`0x4430B5`, `0x4430EE`, `0x443123`, and the case-0 store tail) all move with it.
Aligning the streams shows 111 instructions on both sides and exactly one
differing instruction.

The y-switch load order, which is what defeated wave 14's sibling, **is solved**
here: retail's four `case 1/2` sums load `position.y (0x344)`,
`render_offset.y (0x350)`, `base_position.y (0x338)`, and that order is reachable
by choosing the *x-case-1* spelling — see the lever table below.

### `src/render/entity_quad_anchored_00443080.cpp` (the model, scratch copy)

```cpp
// 0x00443080..0x00443283 (515 bytes): build one anchored sprite quad.
//
// The third of the unrotated quad builders (0x00443290, and 0x004436C0/
// 0x00443910's unrotated sibling).  Two placement flags anchor the quad
// independently: (entity->flags >> 18) & 3 for x and (entity->flags >> 20) & 3
// for y, each selecting a centred case (the placement less half the extent,
// snapped down with the CRT's floor), the placement itself, or the placement
// less the whole extent.  The z of all four vertices is the placement's z.
//
// Retail enters this body with the entity in ESI and the manager on the stack
// (the callee pops it): the dispatcher 0x004451C0 marshals `push ecx; mov
// esi,eax; call 0x00443080`, so the model is kept in the render-batch cluster
// where the whole-program pass can derive that pair from the body.
//
// The two centred cases call the CRT's floor (0x00452FF0), bound absolutely in
// the layout; the finished quad goes to the submit pipeline with mode 1.
//
// The declaration must be written `double __cdecl f(double)`: with `__cdecl
// double` MSVC 13.10 takes the return value from EAX and converts it with fild
// instead of leaving it in st(0).
#include "th10/render/quad_batch.hpp"

extern "C" double __cdecl FUN_00452ff0(double value);

#pragma code_seg(".text$07scratchquad")
extern "C" __declspec(noinline) int EntityDraw_00443080(RenderEntity* entity,
                                                       AnimationManager_00442F50* manager) {
    float width = entity->sprite_width * entity->scale_x;
    float height = entity->sprite_height * entity->scale_y;
    float half_height = height * 0.5f;
    float left, top;

    switch ((entity->flags >> 18) & 3) {
    case 0:
        left = (float)FUN_00452ff0(entity->render_offset.x + entity->position.x
                                   + entity->base_position.x - width * 0.5f);
        data_004978c0[0].x = data_004978c0[2].x = left;
        data_004978c0[1].x = data_004978c0[3].x = data_004978c0[2].x + width;
        break;
    case 1:
        left = entity->base_position.x + entity->position.x + entity->render_offset.x;
        data_004978c0[0].x = data_004978c0[2].x = left;
        data_004978c0[1].x = data_004978c0[3].x =
            entity->base_position.x + entity->position.x + width + entity->render_offset.x;
        break;
    case 2:
        data_004978c0[0].x = data_004978c0[2].x =
            entity->base_position.x + entity->position.x + entity->render_offset.x - width;
        data_004978c0[1].x = data_004978c0[3].x =
            entity->base_position.x + entity->position.x + entity->render_offset.x;
        break;
    }

    switch ((entity->flags >> 20) & 3) {
    case 0:
        top = (float)FUN_00452ff0(entity->render_offset.y + entity->position.y
                                  + entity->base_position.y - half_height);
        data_004978c0[0].y = data_004978c0[1].y = top;
        data_004978c0[2].y = data_004978c0[3].y = data_004978c0[1].y + height;
        break;
    case 1:
        top = (entity->position.y + entity->render_offset.y) + entity->base_position.y;
        data_004978c0[0].y = data_004978c0[1].y = top;
        data_004978c0[2].y = data_004978c0[3].y =
            ((entity->position.y + entity->render_offset.y) + entity->base_position.y) + height;
        break;
    case 2:
        data_004978c0[0].y = data_004978c0[1].y =
            (entity->position.y + entity->render_offset.y) + entity->base_position.y - height;
        data_004978c0[2].y = data_004978c0[3].y =
            (entity->position.y + entity->render_offset.y) + entity->base_position.y;
        break;
    }

    float bottom = entity->render_offset.z + entity->position.z + entity->base_position.z;
    data_004978c0[0].z = data_004978c0[1].z = data_004978c0[2].z = data_004978c0[3].z = bottom;

    return manager->SubmitSpriteQuad(entity, 1);
```

### Declaration lever that cost a build

The floor declaration must be written `double __cdecl f(double)`. With
`__cdecl double f(double)` MSVC 13.10 takes the return value from EAX and
converts it with `fild` (`mov [esp+N],eax; fild [esp+N]`) instead of leaving it
in st(0); the same spelling under C++ linkage is fine. Measured with the plain
oracle:

```text
extern "C" __cdecl double h(double);   -> call; mov [esp+0xc],eax; fild [esp+0xc]
extern "C" double __cdecl h(double);   -> call; (result stays in st(0))
```

## Measured levers (all in the batch cluster or the plain /O2 oracle)

1. **The y-switch load order is a whole-function artifact and is steerable from
   another block.** With the x-case-1 body written as an explicit pair
   (`left = (base.x + position.x) + render_offset.x;`) the four y `case 1/2` sums
   emit `render_offset.y, position.y, base_position.y`; with the *linear*
   spelling (`left = base.x + position.x + render_offset.x;` and the right edge
   `base.x + position.x + width + render_offset.x`) they emit retail's
   `position.y, render_offset.y, base_position.y`. The x region is byte-identical
   under both spellings, so the linear one is free. Wave 14's sibling had the
   same problem and no such lever was looked for.
2. **The x region is itself invariant** under every x spelling tried (pair,
   linear, all six permutations, address-form loads
   `*(const float*)((const char*)entity + 0x344)`, casts, references, compound
   assignments): each x trio emits its canonical order whatever the source says.
3. The plain `/O2` oracle reproduces the cluster's choice for these two
   questions exactly (it was used for the 256-combination screen; the cluster was
   then rebuilt for every candidate that matched).
4. **The remaining byte is not reachable by any spelling tried.** Measured on the
   model, each keeping the rest byte-identical:
   `inner_paren`, `no variable` (call result stored straight into the quad),
   `left + width` versus `data[2].x + width`, `width + data[2].x`, split chains,
   four separate stores, `width * 1.0f`, `(float)width`, `1.0f * width`,
   `width * 2.0f * 0.5f`, `(float)((double)width)`, `*(float*)&width`, `+ 0.0f`,
   `(width + 0.0f)`, named switch temporaries, four separate z stores, guard
   re-reads, and eight further x-case-0/1/2 combinations. All emit the pop before
   the `fadd`. The plain oracle shows the same for all of them, and the *y*-case-0
   floor call in retail *does* pop early, so retail's build is inconsistent
   between the two blocks — the choice looks like a scheduler tie-break, not
   something the source controls.
